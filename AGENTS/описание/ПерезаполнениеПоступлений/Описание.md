# Перезаполнение поступлений

Обработка **`ГКСК_ПерезаполнениеПоступлений`** (подсистема `ГКСК_ДополнительныйИнструментарий`).
Назначение — перезаполнить документы «Приобретение товаров и услуг», у которых не установлен
признак «Поступление по заказам», по заказам поставщику и перепровести их.

Перенесена из внешней обработки `ExternalDataProcessor.ПерезаполнениеПоступлений`
(проект `R:\EDTProjects\GGKKSS\ПерезаполнениеПоступлений`). Исходный проект оставлен
без изменений как источник миграции; рабочей является обработка расширения.

## Состав объектов

| Объект | Назначение |
|---|---|
| `DataProcessor.ГКСК_ПерезаполнениеПоступлений` | Обработка; основная (и единственная) форма — `Форма`. |
| `DataProcessor.ГКСК_ПерезаполнениеПоступлений.Form.Форма` | Форма: два динамических списка (поступления и заказы), две таблицы товаров, две команды. |
| `CommonModule.ГКСК_ПерезаполнениеПоступленийСервер` | Вся серверная логика: подготовка задания, перезаполнение одного документа, пакетная обработка, журнал регистрации. |

## Реквизиты формы

| Реквизит | Тип | Назначение |
|---|---|---|
| `Поступления` | `ДинамическийСписок` | `Документ.ПриобретениеТоваровУслуг`, построен по основной таблице с динамическим считыванием (без произвольного запроса). Колонки: номер, дата, партнёр, контрагент, цена включает НДС, сумма документа, поступление по заказам, склад, договор. |
| `Заказы` | `ДинамическийСписок` | `Документ.ЗаказПоставщику`, по основной таблице с динамическим считыванием. Колонки: номер, дата, партнёр, склад, цена включает НДС, направление деятельности, сумма документа, менеджер. |
| `ТоварыПоступления` | `ТаблицаЗначений` | Товары выделенного поступления: `Номенклатура`, `Количество`, `Цена`, `Сумма`. Заполняется на сервере при активизации строки. |
| `ТоварыЗаказа` | `ТаблицаЗначений` | Товары выделенного заказа: `Номенклатура`, `Количество`, `Цена`, `Сумма`. Заполняется на сервере при активизации строки. |

## Логика

### Отборы

- `ПриСозданииНаСервере`: у списка `Поступления` фиксированный отбор
  `ПоступлениеПоЗаказам = Ложь`; отборы `Заказы` очищаются.
- `ПоступленияПриАктивизацииСтроки`: отборы `Заказы` очищаются и устанавливаются заново —
  `Партнер`, `СуммаДокумента` и `Склад` равны значениям текущей строки поступления.
  Склад участвует в отборе так же, как в пакетном запросе.

### Товары выделенных документов

Под каждым списком выводится таблица товаров выделенной строки (`ТоварыПоступления`,
`ТоварыЗаказа`). Реквизиты — `ТаблицаЗначений` с колонками `Номенклатура`, `Количество`,
`Цена`, `Сумма`; колонки только для чтения (`LabelField`).

Заполнение: при активизации строки списка клиентский обработчик
(`ПоступленияПриАктивизацииСтроки`, `ЗаказыПриАктивизацииСтроки`) вызывает серверную процедуру,
которая грузит в реквизит результат `ГКСК_ПерезаполнениеПоступленийСервер.ТоварыДокумента(Ссылка)`
(запрос к `Документ.ПриобретениеТоваровУслуг.Товары` или `Документ.ЗаказПоставщику.Товары`).
После перезаполнения поступления таблица товаров обновляется повторно.

Примечание: вложенную таблицу по ТЧ строки динамического списка
(`ТекущиеДанные.Товары`) инструментами создать нельзя, поэтому используется схема
«ТаблицаЗначений + серверное заполнение».

### Одиночное перезаполнение

Команда «Перезаполнить поступление по заказу» берёт текущие строки обоих списков, спрашивает
подтверждение и вызывает `ГКСК_ПерезаполнениеПоступленийСервер.ПерезаполнитьПоступление`:
`Товары.Очистить()`, `Заполнить(Заказ)`, `Записать(РежимЗаписиДокумента.Проведение)`.
Результат (успех или текст ошибки) возвращается структурой; ошибка дополнительно пишется
в журнал регистрации.

### Пакетный режим

Команда «Перезаполнить точные совпадения» сначала готовит задание
(`ПодготовитьЗадание`), показывает количество найденных документов и после подтверждения
выполняет `ПерезаполнитьТочныеСовпадения`.

Запрос задания:

```sql
ВЫБРАТЬ
	ПриобретениеТоваровУслуг.Ссылка КАК Поступление,
	МАКСИМУМ(Заказ.Ссылка) КАК Заказ
ИЗ
	Документ.ПриобретениеТоваровУслуг КАК ПриобретениеТоваровУслуг
		ВНУТРЕННЕЕ СОЕДИНЕНИЕ Документ.ЗаказПоставщику КАК Заказ
		ПО ПриобретениеТоваровУслуг.Партнер = Заказ.Партнер
			И ПриобретениеТоваровУслуг.СуммаДокумента = Заказ.СуммаДокумента
			И ПриобретениеТоваровУслуг.Склад = Заказ.Склад
ГДЕ
	НЕ ПриобретениеТоваровУслуг.ПоступлениеПоЗаказам
СГРУППИРОВАТЬ ПО
	ПриобретениеТоваровУслуг.Ссылка
ИМЕЮЩИЕ
	КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Заказ.Ссылка) = 1
УПОРЯДОЧИТЬ ПО
	Поступление
```

Берутся только однозначные совпадения: если по партнёру, сумме и складу подходит больше
одного заказа, документ не обрабатывается.

Обработка построчная: каждый документ — в своей `Попытке`, ошибка не прерывает остальные,
попадает в результат (`Ошибки`: поступление, заказ, текст ошибки) и подробно пишется
в журнал регистрации. Итог выводится пользователю: «Обработано документов: N из M» и перечень
необработанных.

## Автопривязка документов (страница «Автопривязка»)

Две команды страницы запускают фоновое задание (`ДлительныеОперации.ВыполнитьВФоне`,
метод `ГКСК_ПерезаполнениеПоступленийСервер.ВыполнитьЗаданиеАвтопривязки`) с окном ожидания
и прогрессом; ошибка по документу не прерывает обработку.

### Этап 1 — по заказам поставщику

Для каждого заказа поставщику, **к которому ещё не привязано ни одного поступления**
(нет документов `ПриобретениеТоваровУслуг` с `ЗаказПоставщику` = заказ), не помеченного
на удаление:

1. Подбирается поступление среди «бесхозных» (не заполнен `ЗаказПоставщику`): партнёр, сумма
   документа и склад равны заказу. Если у поступления склад пустой — он допускается;
   при нескольких кандидатах сравнивается состав (номенклатура + количество + сумма).
2. Найденное поступление перезаполняется по заказу и проводится: табличная часть `Товары`
   очищается, ставится `ПоступлениеПоЗаказам = Истина` и заказ в шапке, после чего строки
   добавляются напрямую из `Документ.ЗаказПоставщику.Товары` вместе с `КодСтроки`
   (`ЗаполнитьТоварыИзЗаказа`); склад берётся из заказа;
3. Подбирается приходный ордер по составу: сначала проход «номенклатура + количество + сумма»
   (сумма ордера считается по ценам основания), затем «количество + сумма». Сравниваются только
   ордера без основания (`Распоряжение` пусто).
4. Найденный ордер получает основание (`Распоряжение` = поступление), строки перезаполняются
   из регистра `ТоварыКПоступлению` (`ЗаполнитьТоварыПоТоварамКПоступлению`), ордер проводится.
   Если в регистре по основанию пусто, строки ордера сохраняются как были.

Остаток регистра `ЗаказыПоставщикам` при отборе **не используется**: его списывают приходные
ордера, в том числе оформленные без распоряжения, поэтому у заказов с безхозными ордерами
остаток «К поступлению» равен нулю, хотя документы требуют привязки.

Если поступление не найдено, поиск не останавливается: ордер подбирается по составу заказа и
привязывается к заказу. Если не найден и ордер — обработка переходит к следующему заказу.

### Этап 2 — по поступлениям и ордерам

1. Для каждого «бесхозного» поступления ищется заказ без привязанных поступлений по партнёру,
   сумме и складу (при нескольких кандидатах — по составу), затем поступление привязывается
   и проводится.
2. Для каждого приходного ордера без основания ищется поступление по составу (два прохода),
   затем ордер привязывается к поступлению.

Заказы, к которым уже привязано поступление, и документы, уже имеющие основание,
не изменяются.

### Проверка связанных документов перед привязкой

Перед попыткой привязки поступления к заказу проверяется, чем заказ уже занят:

- `ПоступленияПривязанныеКЗаказам` — один запрос на этап: проведённые
  `ПриобретениеТоваровУслуг` с `ЗаказПоставщику` = заказ. Если к заказу привязано
  **другое** поступление (не текущее), привязка не выполняется: в журнал пишется
  «Пропуск» с перечнем этих поступлений — заказ уже закрыт, второе оформление
  ERP не примет, и перезаполнять документ незачем.
- `ТекстСвязанныхДокументовЗаказа` — информационная строка, которая пишется **до**
  попытки проведения: «Связанные документы — привязанные к заказу ордера: …;
  израсходовали заказ: …». Так перечень виден и при остановке фонового задания.

Расход по заказу собирает `РасходныеДокументыЗаказов` — по **всем** регистраторам
регистра `ЗаказыПоставщикам` с `КОформлению < 0` ИЛИ `КПоступлению < 0`: заказ
списывают не только приходные ордера, но и поступления, и корректировки поступлений.
Фильтр по типу стоит у потребителя: `ПеренестиОрдераНаПоступление` снимает проведение
только у `ПриходныйОрдерНаТовары` (поступление — учётный документ, его не трогаем).

Контекст этапа (`ОрдераЗаказов`, `ТоварыОрдеров`, `РасходЗаказов`,
`ПоступленияЗаказов`) передаётся в `ПривязатьПоступлениеКЗаказу` одной структурой
`КонтекстПривязки`.

### Статус заказа после привязки

Найденный документ подтверждает заказ: `УстановитьСтатусПодтвержден` переводит заказ
поставщику в статус «Подтвержден» (`Перечисления.СтатусыЗаказовПоставщикам.Подтвержден`)
и записывает его с проведением. Вызывается в трёх точках: при привязке поступления
к заказу (этапы 1 и 2), после привязки ордера прямо к заказу (этап 1) и после привязки
ордера к поступлению — тогда статус ставится заказу этого поступления (этап 2).

**Порядок важен:** при привязке поступления заказ подтверждается **до**
`Заполнить(Заказ)` — платформа разрешает ввод на основании только из статусов
«Подтвержден» и «Закрыт», иначе падает «Документ находится в статусе "Согласован".
Ввод на основании разрешен только в статусах "Подтвержден", "Закрыт"».

Правила:

- при выключенной функциональной опции `ИспользоватьСтатусыЗаказовПоставщикам` статус
  не меняется;
- заказ в статусе «Закрыт» не понижается — в журнал пишется строка «Пропуск»;
- повторный прогон уже подтверждённый заказ не перезаписывает;
- перед записью заполняются пустые `ДатаОтгрузки`/`ДатаПоступления` (шапка при
  `ПоступлениеОднойДатой` и строки `Товары`): в статусе «Подтвержден» они проверяются
  на заполнение, без этого заказ не записывается; признак «Согласован» и `ДатаСогласования`
  проставляет штатный `ПередЗаписью` документа;
- ошибка установки статуса не отменяет уже выполненную привязку — она попадает
  в журнал диагностики строкой «Ошибка».

**Склад — перекрёстно.** Заказ, поступление и приходный ордер передают склад друг другу
(`СкладДокумента` + `ЗаполнитьСкладДокумента`), чтобы ни у одного документа цепочки
не осталось пустого места хранения:

- при привязке поступления: если у заказа склад пуст, а у поступления заполнен — склад
  записывается в заказ; затем в поступление ставится склад заказа (или его собственный,
  если заказ не дал);
- при привязке ордера: пустой склад основания заполняется складом ордера, пустой склад
  ордера — складом основания; если основание — поступление, склад передаётся и его заказу;
- уже заполненный склад не перезаписывается: документ, где склад есть, считается источником.

Заполнение товаров берёт склад из строки заказа (`Товары.Склад`), а при пустом складе
строки — склад поступления. Если у заказа склад пуст, без этого обмена склад поступления
обнулялся бы и документ падал «Ошибка при получении набора регистра сведений
АналитикаУчетаНоменклатуры: … место хранения не заполнено». Если склада нет ни в одном
документе цепочки — документ не записывается, в журнал диагностики попадает понятная ошибка.

**Перезаполнение товаров по заказу.** Состав пересобирается вручную, как это делается
в форме поступления: табличная часть `Товары` очищается, ставится `ПоступлениеПоЗаказам = Истина`
и заказ в шапке, после чего строки добавляются из `Документ.ЗаказПоставщику.Товары`
(`ЗаполнитьТоварыИзЗаказа`) с переносом всех реквизитов строки, включая `КодСтроки`
и `ЗаказПоставщику`. Штатный `Заполнить(Заказ)` для этого не используется: ERP заполняет
строки по остаткам регистра `ЗаказыПоставщикам` и теряет строки, которые заказом уже
оформлены. Строки заказов загружаются одним запросом на этап, до циклов
(`СтрокиЗаказовДляЗаполнения`), — запрос внутри цикла запрещён (SU95). Отменённые строки
заказа и строки с пустой номенклатурой пропускаются. Если в заказе не осталось ни одной
строки — документ пропускается с сообщением «В заказе … нет ни одной строки товаров —
заполнять нечем». Сумма документа пересчитывается штатным `ПередЗаписью` документа
(`СуммаДокумента = ПолучитьСуммуДокумента()`), вручную её считать не нужно. В журнал пишется,
что реально изменилось: признак «Поступление по заказам», заказ в шапке и количество строк
до и после.

После проведения документ перечитывается объектом (`ПолучитьОбъект`) и сверяются
`ПоступлениеПоЗаказам`, `ЗаказПоставщику` и `Проведен`: платформа или подписка может
отменить запись (`Отказ` в `ПередЗаписью`/`ПриЗаписи`), и тогда объект в памяти изменён,
а документ в базе остаётся прежним. При расхождении в журнал пишется состояние в базе,
а не ложный «успех». Кроме того, `ПровестиДокумент` проверяет текст исключения раньше
флага `Проведен`: у уже проведённого документа при отмене записи `Проведен` остаётся
Истина, и раньше ошибка платформы молча проглатывалась — теперь она попадает в журнал
как «Документ … не записан. Ошибка: …».

**Предварительной сверки с остатком заказа нет.** Собственная проверка по остатку регистра
`ЗаказыПоставщикам` (была до 1.0.30.19) давала ложные пропуски «Поступление больше
заказанного: … по заказу осталось 0»: остаток в регистре не совпадает с тем, что видит ERP
при проведении (другой склад, заказ проведён уже после снятия остатков, остаток списан
приходными ордерами без распоряжения). Состав берётся из заказа целиком, а соответствие
остатку проверяет сама ERP при проведении; её отказ обрабатывается как пропуск.

**Отказ ERP по превышению — это «Пропуск», а не ошибка.** Если заказ уже оформлен другими
документами (в том числе приходными ордерами без распоряжения), ERP при проведении отказывает:
«Оформлено больше, чем указано в распоряжении <заказ>, на N». Такой документ привязать к этому
заказу нельзя, поэтому `ТекстПревышенияЗаказа` распознаёт этот отказ, и в журнал пишется
«Пропуск» с перечнем позиций от ERP (номенклатура, склад, сколько лишнего) — без стека вызовов.
Счётчик ошибок при этом не растёт. Остальные отказы проведения остаются «Ошибкой».

**Диагностика виновника.** После циклов `ДописатьДиагностикуПревышений` одним запросом читает
расходные движения регистра `ЗаказыПоставщикам` по заказам, которые пропущены, и дописывает
в журнал отдельную строку «Пропуск»: «Заказ-основание: … Заказ уже оформили: <документ>
(<количество>), …». Так сразу видно, какие документы израсходовали заказанное количество.
Запрос один на все пропуски — обращений к базе в циклах нет (SU95).

**Освобождение заказа от ордеров.** Частая причина превышения — приходный ордер, который
раньше был привязан к заказу (например, этой же обработкой), из-за чего поступление уже
нельзя провести по заказу. В этом случае обработка пробует убрать причину сама:

1. `ОрдераПривязанныеКЗаказам` одним запросом собирает проведённые приходные ордера,
   привязанные к обрабатываемым заказам (`Соответствие`: заказ → массив ордеров),
   а `РасходныеОрдераЗаказов` — ордера, которые **фактически израсходовали** заказ:
   отбор идёт по расходным движениям регистра `ЗаказыПоставщикам`
   (`КОформлению < 0` или `КПоступлению < 0`), поэтому в выборку попадают и ордера
   **без распоряжения** — именно они чаще всего и держат остаток заказа. Состав товаров
   ордеров читается отдельным запросом (`ТоварыОрдеров`), а не в цикле.
2. При отказе по превышению вызывается `ПеренестиОрдераНаПоступление`: отбираются ордера
   заказа, израсходовавшие заказ **по той же номенклатуре**, что и строки поступления
   (склад и характеристика не сверяются: они в движениях и строках ПТУ могут не совпадать,
   и тогда настоящий виновник отсекается), у них снимается проведение
   (`Записать(РежимЗаписиДокумента.ОтменаПроведения)`), затем поступление очищается,
   заполняется по заказу и проводится, после чего ордера переносятся на поступление
   через `ПривязатьОрдерКРаспоряжению` и проводятся заново. Отказ записи при отмене
   проведения (`Отказ` в `ПередЗаписью`, подписка) исключения не даёт, поэтому после
   записи документ перечитывается: если он остался проведённым, ордер не считается
   освобождённым и в журнал пишется «Проведение ордера не отменено».
3. Если поступление привязать всё же не удалось, `ВернутьОрдерНаЗаказ` возвращает
   снятые с проведения ордера в исходное состояние — восстанавливается **исходное
   распоряжение** (у безхозного ордера оно пустое) и ордер проводится снова; заказ
   остаётся в прежнем состоянии.
4. Успешный перенос пишется в журнал как «Успех» (счётчик успехов растёт), неудачный —
   обычным «Пропуском» с причинами от ERP и диагностикой виновников.

**Виновники видны сразу.** `ТекстРасходаЗаказа` строит перечень документов, израсходовавших
заказ по составу поступления — «<документ> от <дата> (оформлено N, поступило M)» — из уже
загруженных движений (без запроса), поэтому строка пишется **в момент неудачи освобождения**,
не дожидаясь конца задания. Это важно при остановке фонового задания: диагностика после
циклов (`ДописатьДиагностикуПревышений`) в таком случае не выполняется. Проведение снимается
только у приходных ордеров (`ТипЗнч`), поступления не трогаются.

Так решается случай, когда ордер мешает привязать поступление: сначала освобождается
заказ, потом поступление занимает его место, а ордер переезжает на поступление.

## Диагностика (страница «Диагностика»)

Журнал автопривязки — реквизит `ЖурналДиагностики` (`ТаблицаЗначений`) с колонками `Дата`,
`Этап`, `Объект`, `Операция`, `Результат` («Успех», «Ошибка», «Пропуск»), `Комментарий`.
Источник данных — независимый регистр сведений `ГКСК_ЖурналАвтопривязки` (измерение
`Порядок`, ресурсы `Дата`, `Этап`, `Объект`, `Операция`, `Результат`, `Комментарий`).
Фоновое задание после каждого обработанного документа перезаписывает журнал целиком
(`СохранитьЖурналВРегистр`: номер строки — её позиция, запись идемпотентна), а форма читает
его запросом `ЖурналАвтопривязкиИзРегистра` в `ОбновитьЖурналДиагностикиНаСервере`.
Кнопка «Очистить журнал» очищает и таблицу, и регистр (`ОчиститьЖурналАвтопривязки`).
Параллельно каждая операция пишется в журнал регистрации (`ГКСК.АвтопривязкаДокументов`):
успехи — с уровнем «Информация», ошибки — «Ошибка».

**Документ-основание в записи.** В колонке `Объект` — документ, который привязывается
(поступление или приходный ордер), а документ, **к которому** его привязывают, пишется
в комментарий: «Заказ-основание: …» для привязки поступления к заказу и «Основание: …»
для привязки ордера. Это относится ко всем результатам (успех, пропуск, ошибка), поэтому
по журналу регистрации видно, к какому заказу или поступлению шла привязка.

**Причины отказа проведения.** Все проведения идут через `ПровестиДокумент`: перед записью
очередь сообщений пользователю очищается (`ПолучитьСообщенияПользователю(Истина)`), а сама
запись обёрнута в `Попытка` — исключение из `Записать(РежимЗаписиДокумента.Проведение)`
не теряется. После записи, если документ не проведён, тексты сообщений платформы и ERP
собираются в одну строку (`ТекстСообщенийПроведения`) и попадают в исключение:
«Документ … не проведён. Причины: …». Если очередь сообщений пуста, в текст добавляется
подробное представление ошибки (стек) — «Документ … не проведён. Ошибка платформы: …».
Так настоящая причина (нехватка остатков, незаполненный склад, запрет по статусу и т.п.)
видна и в журнале диагностики, и в журнале регистрации, а не только «Не удалось провести "…"!».
Прямые вызовы `Записать(Проведение)` в модуле не используются: `ПерезаполнитьПоступление`
тоже идёт через хелпер.

**Остатки по заказу в диагностике.** Если ERP отказала по превышению, а расходных движений по заказу нет, причина почти всегда в расхождении ключа: позиции документа нет в заказе либо не совпадают характеристика или склад. `ДописатьДиагностикуПревышений` после циклов одним запросом читает `ЗаказыПоставщикам.Остатки(,)` по пропущенным заказам и строки `ЗаказПоставщику.Товары`, а затем по каждой позиции документа пишет: «в заказе N, остаток — заказано A, оформлено B, к поступлению C; в документе D». Позиции берутся из состава ПТУ после заполнения (`ЗапомнитьПропускПревышения` → `ПозицииДокумента`), поэтому видно, какую именно строку ERP считает лишней.

**Журнал виден в любой момент.** Пока задание выполняется, форма обновляет страницу
по обработчику ожидания (2 с, `ОбновитьЖурналДиагностики`): серверная процедура читает
регистр и перезагружает таблицу только при изменении числа строк. При завершении и при
отмене задания обработчик снимается, журнал читается ещё раз — строки, записанные до
остановки, остаются на странице. Окно ожидания открывается независимым
(`РежимОткрытияОкнаОжидания = РежимОткрытияОкнаФормы.Независимый`), чтобы форма
не блокировалась.

Временное хранилище для журнала не используется: по документации данные, помещённые
в фоновом задании, не видны родительскому сеансу до завершения задания, а адрес без
идентификатора формы удаляется после первого же серверного вызова из формы — живой
журнал на этом механизме не построить. Регистр сведений этих ограничений не имеет.

Если фоновое задание прервано (остановка), результата нет, но журнал уже в регистре,
поэтому обработанные строки остаются на странице «Диагностика». Если журнал всё же пуст,
выводится сообщение с указанием события журнала регистрации `ГКСК.АвтопривязкаДокументов`.

## Ограничения и дальнейшие шаги

- Чистится только табличная часть `Товары`; `Услуги`, `Тара`, `Серии`, `ВидыЗапасов`
  остаются от прежнего заполнения. Поведение сохранено как в исходной обработке.
- Динамические списки построены по основной таблице с динамическим считыванием (как в исходной
  обработке): произвольный запрос снят, поэтому поля списка — стандартные реквизиты документа
  (`Number`, `Date` и т.д.). Товары выводятся не вложенной ТЧ строки, а отдельными
  `ТаблицаЗначений` — см. раздел «Товары выделенных документов».
- В форме остаётся предупреждение SU115 («реквизит "Ссылка" динамического списка не выведен
  в таблицу»). Снимается в редакторе форм снятием признака «Использовать всегда» у поля «Ссылка»
  динамических списков; инструментом это свойство не меняется.
- Реквизиты приходного ордера (`Распоряжение`, `Склад`) EDT помечает предупреждением SU239
  «Свойство объекта не обнаружено»: объект `ПриходныйОрдерНаТовары` не заимствован в расширение.
  Предупреждение ложноположительное — реквизиты существуют в основной конфигурации.
