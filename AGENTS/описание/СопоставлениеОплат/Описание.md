# Сопоставление оплат по заявкам

Обработка **`ГКСК_СопоставлениеОплатПоЗаявкам`** (подсистема не выделена; префикс `ГКСК_`).
Назначение — найти списания безналичных денежных средств, которые ещё не сопоставлены
с заявками на расходование денежных средств, и одним действием связать оплату с заявкой.

## Состав объектов

| Объект | Назначение |
|---|---|
| `DataProcessor.ГКСК_СопоставлениеОплатПоЗаявкам` | Обработка; основная (и единственная) форма — `Форма`. |
| `DataProcessor.ГКСК_СопоставлениеОплатПоЗаявкам.Form.Форма` | Форма типа GENERIC: поле даты отбора, таблица результата, кнопка «Сопоставить оплату с заявкой». |
| `CommonModule.ГКСК_СопоставлениеОплатПоЗаявкамСервер` | Серверная логика: подготовка задания, фоновая процедура приведения договоров к детализации «По заказам» и сопоставления оплат, поиск объектов расчётов. |

Заимствованные (borrowed) объекты основной конфигурации, нужные для типов колонок таблицы
и работы кода:

- `Document.СписаниеБезналичныхДенежныхСредств`;
- `Document.ЗаявкаНаРасходованиеДенежныхСредств`;
- `Enum.СтатусыЗаявокНаРасходованиеДенежныхСредств`.

## Реквизиты формы

| Реквизит | Тип | Назначение |
|---|---|---|
| `ДатаОтбора` | `Дата` | Значение параметра `&Дата` запроса. При открытии заполняется началом текущего месяца. |
| `ТаблицаРезультата` | `ТаблицаЗначений` | Результат запроса: `Статус`, `Автор`, `Расход` (списание БДС), `Ссылка` (заявка), `Колво`. |

Элементы формы: поле `ДатаОтбора` (при изменении перечитывает таблицу), таблица
`ТаблицаРезультата`, кнопка `СопоставитьОплатуСЗаявкой` в командной панели формы.

## Логика

### Заполнение таблицы

При создании формы и при изменении `ДатаОтбора` выполняется запрос (параметр `&Дата` —
`ДатаОтбора`):

```sql
ВЫБРАТЬ
	Заявка.Статус КАК Статус,
	Заявка.Автор КАК Автор,
	МАКСИМУМ(Списание.Ссылка) КАК Расход,
	Заявка.Ссылка КАК Ссылка,
	КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Списание.Ссылка) КАК Колво
ИЗ
	Документ.СписаниеБезналичныхДенежныхСредств.РасшифровкаПлатежа КАК Списание
		ВНУТРЕННЕЕ СОЕДИНЕНИЕ Документ.ЗаявкаНаРасходованиеДенежныхСредств КАК Заявка
		ПО Списание.Ссылка.Партнер = Заявка.Партнер
			И Списание.Ссылка.СуммаДокумента = Заявка.СуммаДокумента
ГДЕ
	Заявка.Проведен
	И НЕ ТИПЗНАЧЕНИЯ(Списание.ОбъектРасчетов.Объект) = ТИП(Документ.ЗаказПоставщику)
	И НЕ Списание.Ссылка.ОплатаПоЗаявкам
	И Списание.Ссылка.Дата > &Дата
СГРУППИРОВАТЬ ПО
	Заявка.Ссылка,
	Заявка.Статус,
	Заявка.Автор
```

Отличия от исходного текста пользователя: в `СГРУППИРОВАТЬ ПО` добавлены `Заявка.Статус`
и `Заявка.Автор` — иначе платформа не даёт выводить их без агрегатной функции.

### Кнопка «Сопоставить оплату с заявкой»

Работает по **выделенным строкам** таблицы (множественное выделение). Идентификаторы выделенных
строк табличного поля **не совпадают** с индексами строк таблицы значений, поэтому данные строк
читаются из самого табличного поля — `Элементы.ТаблицаРезультата.ДанныеСтроки(ИдентификаторСтроки)`,
а на сервер передаётся массив структур `{Оплата, Заявка}`.

Вся работа выполняется **в фоновом задании** (`ДлительныеОперации.ВыполнитьВФоне`, стандартное окно
ожидания с прогрессом), потому что включает распроведение и повторное проведение множества документов.

#### Шаг 1. Подготовка задания (сервер, `ГКСК_СопоставлениеОплатПоЗаявкамСервер.ПодготовитьЗадание`)

- по каждой строке определяется заказ поставщику — `Заявка.ДокументОснование`
  (если это не `Документ.ЗаказПоставщику`, строка отбрасывается с ошибкой);
- собирается список договоров заказов и проверяется `Договор.ПорядокРасчетов`;
- если хотя бы у одного договора детализация расчётов отличается от `Перечисления.ПорядокРасчетов.ПоЗаказам`,
  возвращается признак `ТребуетсяПриведение` и описание предстоящих действий.

#### Шаг 2. Подтверждение и запуск

Если приведение требуется — пользователю задаётся вопрос (`ПоказатьВопрос`, «Да/Нет»);
при ответе «Нет» обработка завершается. Затем задание запускается в фоне, на клиенте —
`ДлительныеОперацииКлиент.ОжидатьЗавершение` с окном ожидания и выводом прогресса
(фон сообщает прогресс через `ДлительныеОперации.СообщитьПрогресс`). Результат читается из
временного хранилища по адресу, созданному при запуске.

#### Шаг 3. Приведение договора (только если `ТребуетсяПриведение`)

Цепочка документов собирается по правилу «заказ поставщику → заявки по нему → оплаты по этим заявкам»:
заявки — запросом по `ДокументОснование В (&Заказы)`, оплаты — запросом по
`РасшифровкаПлатежа.ЗаявкаНаРасходованиеДенежныхСредств В (&Заявки)`
(тип оплат — `Документ.СписаниеБезналичныхДенежныхСредств`). Оплата из выделенных строк
включается в цепочку всегда, даже если ещё не связана с заявкой.

Порядок действий:

1. **распроведение** всех документов цепочки (оплаты, заявки, заказы) — только проведённых;
2. **смена детализации расчётов** договоров: `ПорядокРасчетов = Перечисления.ПорядокРасчетов.ПоЗаказам`;
3. **перезаполнение заказа поставщику**: договор проставляется (если не заполнен — ошибка),
   затем **явно выставляется `ПорядокРасчетов = ПоЗаказам`**, **очищается `ОбъектРасчетов`**
   и заказ проводится (`РежимЗаписиДокумента.Проведение`). Порядок расчётов выставляется явно
   потому, что при записи он заполняется только если пуст (`ВзаиморасчетыСервер.ПередЗаписью` →
   `ПроверитьЗаполнитьРеквизит`), а очистка объекта расчётов повторяет типовое поведение при смене
   договора (`ВзаиморасчетыСервер.ФормаПриИзмененииРеквизитов` → `ОчиститьОбъектРасчетов`); новый
   объект расчётов подбирается и создаётся уже при проведении
   (`ОбъектыРасчетовСервер.ПроверитьОбъектыРасчетовПередЗаписью` → `ЗаполнитьОчиститьОбъектРасчетов`).
   Без этого заказ остаётся «по договорам», механизм снова подставляет в шапку объект расчётов
   по договору, и проведение падает: «Не удалось найти объект расчетов для договора …» либо
   «Объект расчетов … не может быть выбран в документах, т.к. исходный объект больше не является
   объектом расчетов или помечен на удаление»;
4. **перезаполнение заявок**: во всех строках ТЧ `РасшифровкаПлатежа` проставляется объект расчётов,
   найденный по заказу (`ОбъектыРасчетовСервер.ПолучитьОбъектРасчетовПоСсылке(Заказ, Организация,
   Перечисления.ТипыРасчетовСПартнерами.РасчетыСПоставщиком)`); при расхождении договор заявки
   приводится к договору заказа; заявка проводится;
5. **перезаполнение оплат**: в строках расшифровки платежа, где указана заявка из цепочки,
   проставляется объект расчётов по соответствующему заказу; изменившиеся оплаты проводятся.

Если объект расчётов по заказу не найден — цепочка прерывается (откат невозможен, поэтому
пользователю сообщается этап, на котором произошла ошибка).

#### Шаг 4. Сопоставление оплат (всегда)

Для каждой выделенной оплаты (`СопоставитьОднуОплату`):

1. оплата — `Расход` (списание БДС), заявка — `Ссылка`;
2. в оплате: `ОплатаПоЗаявкам = Истина`, `ЗаявкаНаРасходованиеДенежныхСредств = заявка`;
3. в **первой** строке ТЧ `РасшифровкаПлатежа`: `ЗаявкаНаРасходованиеДенежныхСредств = заявка`,
   `ОбъектРасчетов` = элемент справочника `ОбъектыРасчетов`, найденный по документу-основанию
   заявки (`Заявка.ДокументОснование`) штатной функцией
   `ОбъектыРасчетовСервер.ПолучитьОбъектРасчетовПоСсылке(<ДокументОснование>, <Организация>)`;
   затем **статья ДДС** — `СтатьяДвиженияДенежныхСредств` берётся **из договора заявки**
   (`Заявка.Договор` → `Договор.СтатьяДвиженияДенежныхСредств`), а не из заказа поставщику;
   если у договора заявки статья не заполнена, существующая статья не затирается;
4. документ записывается с проведением (`РежимЗаписиДокумента.Проведение`).

Повторные выделения одной и той же оплаты обрабатываются один раз. По завершении таблица результата
перечитывается, пользователю выводится итог (приведён ли договор, сколько оплат сопоставлено)
или текст ошибки с указанием этапа. Текст ошибки дополнительно пишется в журнал регистрации
(событие `ГКСК.СопоставлениеОплатПоЗаявкам`, уровень «Ошибка») — с указанием этапа, на котором
прервалась цепочка.

Запуск выполняется через `ДлительныеОперации.ВыполнитьВФоне`; адрес результата БСП формирует сама
(`ДлительныеОперации.ПараметрыВыполненияВФоне(УникальныйИдентификатор)` — временное хранилище формы),
а результат читается из `Результат.АдресРезультата` в обработчике завершения
`ДлительныеОперацииКлиент.ОжидатьЗавершение`. Собственное временное хранилище для результата
не создаётся; статус `"Ошибка"` выводится через `СтандартныеПодсистемыКлиент.ВывестиИнформациюОбОшибке`.

## Известные особенности / ограничения

- **SU239 в модулях формы и общего модуля.** У заимствованных документов модель EDT не видит реквизиты
  основной конфигурации (`ОплатаПоЗаявкам`, `ЗаявкаНаРасходованиеДенежныхСредств`,
  `ДокументОснование`, `РасшифровкаПлатежа`), поэтому по этим обращениям в модулях формы и общего
  модуля `ГКСК_СопоставлениеОплатПоЗаявкамСервер` остаются предупреждения `SU239` («Свойство (метод) объекта не обнаружено»). На исполнение
  не влияет: в рантайме заимствованный объект — это объект основной конфигурации со всеми
  реквизитами. Это известное поведение EDT для заимствованных объектов (ср. `SU100`).
- Заимствование объектов понадобилось из-за того, что колонки таблицы формы имеют
  ссылочные типы, а EDT не позволяет указать тип объекта основной конфигурации, пока он
  не заимствован в расширение.
