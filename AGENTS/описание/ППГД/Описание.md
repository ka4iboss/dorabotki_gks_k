## 1. Общее назначение

Подсистема реализует функциональный блок **«Права и профили групп доступа»** расширения
`Доработки_ГКС_К` (конфигурация `1С:ERP Управление предприятием 2`, версия `2.5.26.118`,
платформа `8.3.27`, режим совместимости расширения `8.3.27`, назначение `Customization`).

Функциональные области:

1. **Управление профилями групп доступа.** Доработка типового справочника
   `ПрофилиГруппДоступа`: собственные реквизиты авторства/дат, табличные части
   `пд_Объекты` и `Расш_ПГДРодительскиеПрофили`, текстовые буферы отложенных ролей;
   доработанные формы элемента и списка (обновление ролей из родительских профилей,
   подбор ролей по метаданным, копирование, обработка отложенных ролей).
2. **Генерация групп доступа** по выбранному профилю и значениям доступа
   (обработка `ППГД_ГенерацияГруппДоступа`).
3. **Подбор ролей для профиля** по метаданным — построение деревьев реквизитов и ролей
   (обработка `ППГД_ПодборРолейДляПрофиляГруппДоступа`).
4. **Выгрузка/загрузка прав** в XML через XDTO-пакет `ППГД_ПраваДоступа`
   (пространство имён `http://rules`): обработка `ППГД_ВыгрузкаЗагрузкаПрав`
   и серверные общие модули `ППГД_ОбменДаннымиXDTOСервер`,
   `ППГД_МенеджерОбменаПравамиДоступа`.
5. **Просмотр и редактирование прав** — обработка `ППГД_ПросмотрПрав`
   (матрицы «роли × метаданные», «профили × пользователи», редактирование состава
   ролей пользователей ИБ, сброс/установка пароля).
6. **Запуск клиента от имени пользователя** (`ППГД_ЗапускОтИмениПользователя`).
7. **Журнал регистрации** — доработка типовой обработки `ЖурналРегистрации`,
   собственная общая команда `ППГД_ОткрытьЖурналРегистрации` и регистр сведений
   `ППГД_ЖурналЗагрузки` («Журнал загрузки») с командой `ЖурналЗагрузкиПрав`.
8. **Утилиты анализа прав** — `ППГД_ДампПравРолей` (дамп прав ролей в текстовые файлы)
   и `ППГД_АнализЗапросовМодулей` (разбор текстов модулей и заполнение регистра
   `ППГД_ПоляВЗапросахМодулей`), в подсистему не включены.

**Префикс имён объектов подсистемы — `ППГД_`** (единый после переименования 1.7.0).
Исторические префиксы `пд_`, `ТБ_`, `ппд_`, `АКС_`, `Расш_ПГД` встречаются только внутри
имён реквизитов/ТЧ заимствованных объектов (`пд_Объекты`, `Расш_ПГДРодительскиеПрофили`).

## 2. Конфигурация и подсистема

### 2.1 Параметры конфигурации расширения

Полный набор параметров — в корневом `описание/Структура.md` §1. Ключевое для подсистемы:

- **Имя:** `Доработки_ГКС_К`; синоним «Доработки ГКС К».
- **Принадлежность:** `Adopted` (расширение), тип `ConfigurationExtension`.
- **Префикс имён (`namePrefix`):** `ГКСК`; имена объектов подсистемы — `ППГД_`.
- **Назначение (purpose):** `Customization`.
- **Режим совместимости расширения:** `8.3.27`.
- **Версия:** `2.35.1`; язык по умолчанию — `Language.Русский`.
- **Роль подсистемы:** `Role.ППГД_ОсновнаяРоль`.
- **Файл:** `src/Configuration/Configuration.mdo`.

### 2.2 Подсистема

**`ППГД_ПраваПрофилейГруппДоступа`** (синоним «Права», `includeInCommandInterface = true`,
картинка `CommonPicture.ППГД_ИконкаПодсистемы`). Состав (из `.mdo`):
`Catalog.ГруппыДоступа`, `Catalog.ИдентификаторыОбъектовМетаданных`,
`Catalog.ИдентификаторыОбъектовРасширений`, `Catalog.ПрофилиГруппДоступа`,
`Constant.ОграничиватьДоступНаУровнеЗаписей`,
`DataProcessor.ППГД_ГенерацияГруппДоступа`,
`DataProcessor.ППГД_ПодборРолейДляПрофиляГруппДоступа`,
`DataProcessor.ППГД_ВыгрузкаЗагрузкаПрав`, `InformationRegister.ППГД_ЖурналЗагрузки`,
`Catalog.Пользователи`, `DataProcessor.ППГД_ЗапускОтИмениПользователя`,
`DataProcessor.ППГД_ПросмотрПрав`, `CommonCommand.ППГД_ОткрытьЖурналРегистрации`.

Файл: `src/Subsystems/ППГД_ПраваПрофилейГруппДоступа/ППГД_ПраваПрофилейГруппДоступа.mdo`.

> **История.** Подсистема ранее называлась `АКС_ППГД`. Утилиты `ППГД_ДампПравРолей` и
> `ППГД_АнализЗапросовМодулей` в подсистему не включены; в её состав также не входят

## 4. Справочники

### 4.1 Собственных справочников нет

Все справочники подсистемы — заимствованные (`Adopted`).

### 4.2 `ПрофилиГруппДоступа` (заимствованный, расширен)

Файл: `src/Catalogs/ПрофилиГруппДоступа/ПрофилиГруппДоступа.mdo`.
Иерархический, `descriptionLength = 150`, `objectModule = Extended`.
Формы: `ФормаЭлемента`, `ФормаСписка` (обе Extended).

Реквизиты:

| Имя | Тип | Происхождение | Комментарий |
|-----|-----|---------------|-------------|
| `Комментарий` | String | Типовой | — |
| `Расш_ПГДОтложенныеРолиДобавление` | String | Расширение | Отложенные роли: добавление |
| `Расш_ПГДТекстовыеРолиКРодительским` | String | Расширение | Текстовые роли к родительским |
| `Расш_ПГДОтложенныеРолиУдаление` | String | Расширение | Отложенные роли: удаление |
| `Автор` | `CatalogRef.Пользователи` | Расширение | Заполняется при создании элемента |
| `ДатаСоздания` | Date | Расширение | Дата и время создания |
| `ДатаПоследнегоИзменения` | Date | Расширение | Обновляется при каждой записи |

Табличные части:

| Имя | Происхождение | Колонки |
|-----|---------------|---------|
| `Роли` | Типовая | `Роль` (AnyRef) |
| `ЗначенияДоступа` | Типовая | `ЗначениеДоступа` (`DefinedType.ЗначениеДоступа`), `ВключаяНижестоящие` (Boolean) |
| `ВидыДоступа` | Типовая | собственных колонок в расширении нет |
| `пд_Объекты` | Расширение | `ОбъектМетаданных` (`CatalogRef.ИдентификаторыОбъектовРасширений` \| `CatalogRef.ИдентификаторыОбъектовМетаданных`) |

**Модуль объекта** (`src/Catalogs/ПрофилиГруппДоступа/ObjectModule.bsl`) — расширяет типовую
запись через аннотацию:

```1c

```

Для не-группы: при создании заполняет `Автор` и `ДатаСоздания`; при каждой записи
обновляет `ДатаПоследнегоИзменения`. Логика работы форм — см. §6.8.

### 4.4 `Пользователи`, `ГруппыПользователей` (заимствованные)

Файлы: `src/Catalogs/Пользователи/Пользователи.mdo`,
`src/Catalogs/ГруппыПользователей/ГруппыПользователей.mdo`. Только флаг

> **Важно.** Расширение не наследует свойства заимствованных объектов: в модели EDT у

> (`descriptionLength = 0`, `hierarchical = false`), что даёт маркеры SU100/SU118 при
> обращении к путям данных. При необходимости свойства приводятся к базовым.

Заимствованные справочники-идентификаторы (типовой механизм БСП), используются как

### 5.3 `ППГД_ДампПравРолейСервер` (Сервер, внешнее соединение, собственный)

Файл: `src/CommonModules/ППГД_ДампПравРолейСервер/Module.bsl`.

- `Функция ВыгрузитьПраваРолей(Знач КаталогВыгрузки, Знач ИсключаемыеРоли) Экспорт` —
  выполняется в фоне, читает регистр `ПраваРолей` одним запросом с сортировкой по объекту
  и роли, при смене объекта пишет файл (`ЗаписатьФайлОбъекта`) и сообщает прогресс
  (`ДлительныеОперации.СообщитьПрогресс`); после объектов вызывает выгрузку подсистем.
  Возвращает `Структура("Объектов, Подсистем, Файлов")`.
- `Функция ВыгрузитьПраваРолейНаПодсистемы(Знач КаталогВыгрузки, Знач ИсключаемыеРоли) Экспорт`
  — обходит `Метаданные.Подсистемы` вместе с вложенными (`ДобавитьПодсистемы`), по каждой

### 6.2 `ППГД_ПодборРолейДляПрофиляГруппДоступа`

Файл: `src/DataProcessors/ППГД_ПодборРолейДляПрофиляГруппДоступа/`.

Назначение: подбор ролей и объектов метаданных для профиля; строит деревья реквизитов и
ролей, возвращает результат в форму профиля.
Реквизит: `ПрофильГруппыДоступа`. Табличные части: `ОбъектыПрофиля`
(`ОбъектМетаданных`, `ПолноеИмя`, `Синоним`), `РеквизитыОбъектов`
(`ОбъектМетаданных`, `Реквизит`, `СинонимОбъектаМетаданных`, `СинонимТабличнойЧасти`,
`Синоним`, `Ключ`, `ТипСтрокой`, `Использовать`), `ТипыРеквизитов` (`Реквизит`, `Метаданные`),
`РолиМетаданных` (`_Реквизит`, `Метаданные`, `ИмяРоли`, `Роль`, права `ПравоЧтение`,
`ПравоИзменение`, `ПравоДобавление`, `ПравоПросмотр`, `ПравоРедактирование`,
`ПравоИнтерактивноеДобавление`, флаги «без ограничения», `Использовать`),
`ИспользуемыеРоли` (`ИмяРоли`, `Роль`).
Макеты СКД: `МакетФормированияДереваРеквизитов`, `МакетФормированияДереваРолей`.
Форма: `Форма` (`Forms/Форма/Module.bsl`). Ключевые процедуры:
`ЗаполнитьДанныеОбъектовПрофиля`, `ЗаполнитьДеревоРеквизитов`, `ЗаполнитьДеревоРолей`,
`ПолучитьДерево` (СКД → ДеревоЗначений), `акс_ЗаполнитьДеревоРолейПоУровнюДоступа`,
`ПолучитьРезультатПодбораРолей` (возвращает `Структура("Роли,Объекты", …)`).

**Исключаемые роли** — реквизит формы `СписокРолиИсключения` (`СписокЗначений`; значение —
`СправочникСсылка.ИдентификаторыОбъектовМетаданных`), на форме — поле ввода «Роли исключения»:
роли, права которых не попадают в дерево ролей. Табличных частей и отдельных команд у списка
нет, правится он штатным диалогом поля ввода. Заполняется один раз при создании формы
(`ПриСозданииНаСервере` → `ЗаполнитьСписокРолейИсключения`): все `Метаданные.ОсновныеРоли` +
роль `Роль.УдаленныйДоступOData` + роли «только для администраторов системы» и «только для
внешних пользователей» (`Пользователи.НазначениеРолей()`); имена приводятся к ссылкам через
`ОбщегоНазначения.ИдентификаторыОбъектовМетаданных`, имена, которых нет в конфигурации, молча
пропускаются.

Список используется в двух местах: как параметр запроса
(`НЕ ПраваРолей.Роль В (&СписокРолиИсключения)`) и через функцию `ПолучитьИсключенныеРоли()`,
по которой `ДобавитьРолиПодсистемы` отсеивает исключённые роли при подборе по подсистемам.
Список живёт в рамках сеанса: объект обработки в базе не сохраняется, при следующем открытии
формы заполняется значениями по умолчанию.

Важно: запрос ролей выполняется только по метаданным, которых ещё нет в ТЧ (гвардия
`НеЗаполненныеМетаданные` / `Объект.РеквизитыОбъектов`, результат дописывается в
`РолиМетаданных` без очистки), поэтому изменение списка исключений в уже открытой форме влияет
только на ещё не загруженные объекты. Обработчик `СписокРолиИсключенияПриИзменении` вызывает
`ОбновитьДанные()` → `ОбновитьДанныеНаСервере()` (`ЗаполнитьДанныеОбъектовПрофиля`,
`ЗаполнитьДеревоРеквизитов`, перестроение дерева ролей по выбранному режиму группировки).

**Роли подсистем (разделов).** Регистр `ПраваРолей` не содержит прав на подсистемы, поэтому
`ЗаполнитьДанныеОбъектовПрофиля` дополнительно вызывает `ЗаполнитьРолиПодсистем(Синонимы)`:
она собирает подсистемы, в состав которых входят объекты профиля, вместе с родительскими
(`ПолучитьПодсистемыОбъектовПрофиля` → рекурсивная `ПодсистемыСОбъектамиПрофиля`; обход
`Метаданные.Подсистемы` и `Подсистема.Подсистемы`, ключ подсистемы наращивается префиксом) и по
каждой паре «подсистема × роль» проверяет `ПравоДоступа("Просмотр", Подсистема, Роль)`
(`ДобавитьРолиПодсистемы`). Найденные роли дописываются в ту же ТЧ `РолиМетаданных` с ключом
`Подсистема.<Цепочка>` (например `Подсистема.Продажи.Подсистема.ОптовыеПродажи`) и попадают в
дерево ролей узлами «Подсистема …». Автоматически они **не отмечаются**: для видимости раздела
достаточно одной роли из многих, выбор остаётся за пользователем. Служебные:
`ПолучитьКлючиЗаполненныхПодсистем`, `ПолучитьИсключенныеРоли`, `ПолучитьИдентификаторыРолей`;
`ПолучитьАктивныеМетаданныеТиповРеквизитов` не отбрасывает строки подсистем как «неактивные».

**Почему подсистемы обходятся только сверху вниз.** Подниматься по `Родитель()` нельзя: у
подсистемы верхнего уровня `Родитель()` возвращает саму конфигурацию, и добавленная в 1.12.1
проверка `РодительскаяПодсистема <> Метаданные` на практике не срабатывала — конфигурация попадала
в список подсистем, и `ПравоДоступа("Просмотр", …)` падала с ошибкой «Право Просмотр неприменимо к
Конфигурация.УправлениеПредприятием». Обход сверху вниз заодно исправил ключи подсистем верхнего
уровня: раньше в ключ попадало имя конфигурации, из-за чего проверка уже заполненных подсистем не
срабатывала и при повторном заполнении роли дублировались.

**Синонимы и фиксированные коллекции.** Собранные синонимы (`Синонимы`) передаются в дерево как
`ФиксированноеСоответствие` — реквизиты `СинонимыМетаданных`, `МетаданныеПоРеквизитам`,
`КлючиРеквизитовПоМетаданным`. У `ФиксированноеСоответствие` оператор `[]` с несуществующим ключом
вызывает исключение «Поле объекта не обнаружено (…)», тогда как `.Получить(…)` возвращает
`Неопределено`, поэтому во всех обращениях к этим коллекциям используется `.Получить(...)`.
Синонимы ролей попадают в карту только из запроса к регистру `ПраваРолей`; роли, найденные через
`ПравоДоступа` (роли подсистем), дописывают свои синонимы в `Синонимы` в `ДобавитьРолиПодсистемы`.

**Роли регистров движений.** Для документов профиля дополнительно собираются регистры, по
которым документ может выполнять движения: права на них нужны для проведения и записи
документа. Источник — коллекция движений объекта метаданных
(`Метаданные.Документы.<Имя>.Движения`, тип `КоллекцияЗначенийСвойстваОбъектаМетаданных`),
а не данные конкретного документа. Список даёт функция
`РегистрыДвиженийОбъектовПрофиля(ТаблицаОбъектовПрофиля)` (возвращает соответствие
«полное имя регистра → синоним»; строки профиля, не начинающиеся с «Документ.», пропускаются).
Полные имена регистров попадают в тот же список метаданных, по которому запрашиваются роли из
регистра `ПраваРолей`, поэтому в дереве ролей появляются группы «РегистрНакопления …»,
«РегистрСведений …» с ролями на эти регистры; автоматически они не отмечаются.
`ПолучитьАктивныеМетаданныеТиповРеквизитов` считает такие регистры активными (иначе строки
ролей по ним отфильтровывались бы), из-за чего её директива изменена с
`&НаКлиентеНаСервереБезКонтекста` на `&НаСервереБезКонтекста`.

**Группировка дерева ролей.** Режим выбирается радиокнопкой `акс_ГруппироватьРолиПо`: «Метаданным»
(стандартный, через СКД `МакетФормированияДереваРолей`), «Виду доступа»
(`акс_ЗаполнитьДеревоРолейПоВидуДоступа`) и «Право доступа» (`акс_ЗаполнитьДеревоРолейПоУровнюДоступа`,
иерархия право → тип метаданных → объект → роль). В режиме «Виду доступа» строки раскладываются по
группам-корням **по фактическим правам роли на объект**, а не по вхождению слова в имя роли: вид
доступа — самое сильное право строки, от слабого к сильному «Чтение» → «Просмотр» → «Добавление»
(вместе с интерактивным добавлением) → «Изменение» → «Редактирование» (`ВидДоступаСтрокиРоли`).
Роль с правами «чтение + просмотр» попадает в «Просмотр», а с «+ изменение/редактирование» —
в «Изменение»/«Редактирование», поэтому в группе «Просмотр» не остаётся ролей, дающих больше
просмотра. Права «Удаление», «Проведение» и «ОтменаПроведения» в регистре `ПраваРолей` не хранятся,
поэтому для строк, попавших в «Чтение»/«Просмотр», они дополнительно проверяются через `ПравоДоступа`
(`ЕстьПраваСверхПросмотра` → `ПраваСверхПросмотраОбъекта`; набор прав зависит от типа объекта, иначе
`ПравоДоступа` упала бы на неприменимом праве) — такие роли уходят в группу «Прочие права». Строки
объектов, по которым роли вообще не подобраны, попадают в группу «Без прав» и показываются именем
объекта. Внутри группы роль показывается один раз: команды `акс_ПроставитьФлаги` / `акс_СнятьФлаги`
ищут строки табличной части по имени роли, поэтому флажок в дереве помечает роль по всем объектам.

### 6.9 `ППГД_АнализЗапросовМодулей` и подбор ролей по полям запросов (в подсистему не включена)

Файл: `src/DataProcessors/ППГД_АнализЗапросовМодулей/`.

Утилита подготовки данных: разбирает тексты модулей конфигурации и заполняет регистр
сведений `ППГД_ПоляВЗапросахМодулей` — какие поля объектов метаданных используются в
текстах запросов модулей.

- Источник текстов — каталог выгрузки модулей (`Конфигуратор /DumpConfigFiles <каталог> -Module`),
  путь задаётся в поле формы; каталог обходится целиком вручную (стеком каталогов, по одному
  каталогу за вызов `НайтиФайлы`), берутся файлы с именами `*.bsl` и `*.txt` (признак файла —
  по окончанию имени, а не по свойству `Файл.Расширение`).
- Работа выполняется в фоновом задании (`ДлительныеОперации.ВыполнитьФункцию` +
  `ДлительныеОперацииКлиент.ОжидатьЗавершение` с индикацией прогресса). Итоги последнего
  запуска показываются на форме в поле «Итоги анализа» (реквизит `ИтогиАнализа`, только для
  чтения) и дублируются всплывающим оповещением: «файлов найдено / модулей / запросов /
  пропущено запросов / полей». Причина, по которой анализ не выполнен, тоже выводится в это
  поле и дополнительно модальным предупреждением. Есть команда «Проверить каталог»
  (`ПроверитьДоступностьКаталога`, тоже через длительную операцию) — показывает, что именно
  видит процесс на сервере.
- Регистр `ППГД_ПоляВЗапросахМодулей`: измерения `Метаданные` (полное имя объекта,
  например `Справочник.Валюты`, для реквизитов табличных частей — `...ТабличнаяЧасть.<Имя>`)
  и `Поле` (имя поля, например `Наименование`, `Товары.Номенклатура`, `*`); ресурсы
  `КоличествоЗапросов` (Число) и `СписокМодулей` (Строка, до 20 **путей модулей относительно
  корня выгрузки** через `; `, например
  `Documents/ЗаказПокупателя/Forms/ФормаДокумента/Ext/Form/Module.bsl` — по пути модуля
  определяется, какому объекту метаданных он принадлежит).

**Разбор текстов** (общий модуль `ППГД_АнализЗапросовСервер`, §5.4):

1. Текст модуля читается как UTF-8; если кириллицы в прочитанном тексте нет, файл
   перечитывается в ANSI (функции `ПрочитатьФайлВКодировке`, `ЕстьКириллица`).
2. Из текста модуля удаляются однострочные комментарии; содержимое строковых литералов
   защищено от анализа (при разборе запроса литералы заменяются на `''`).
3. Ищутся выражения, в которых может быть текст запроса: аргумент конструктора
   `Новый Запрос(...)` и правая часть присваивания `....Текст = ...`.
4. Выражение разбивается на части по знакам `+` верхнего уровня (вне литералов и скобок,
   функция `ЧастиСложения`), каждая часть разбирается отдельно (`ЗначениеЧастиТекста`): строковый
   литерал, `СтрШаблон("...", ...)` (берётся текст шаблона), имя переменной (ищется присваивание ей
   литерала) или служебный символ (`Символы.ПС`, `Символы.Таб`, `Символы.ВК` — функция
   `ЗначениеСимвола`). Если хотя бы одну часть разобрать нельзя (вызов функции, текст из реквизита,
   `СтрЗаменить`), запрос попадает в счётчик «пропущено».
5. В тексте запроса разбираются источники после `ИЗ` / `СОЕДИНЕНИЕ` вместе с псевдонимами
   (в том числе виртуальные таблицы регистров и табличные части), затем — обращения к полям
   через псевдонимы: `<Псевдоним>.<Поле>`, `<Псевдоним>.<ТЧ>.<Реквизит>`, `<Псевдоним>.<Реквизит>.<Поле>`
   (один переход по ссылке), поле `*`. Поля сверяются с метаданными, поэтому в регистр
   попадают только реально существующие реквизиты, измерения, ресурсы и стандартные реквизиты.
6. Дополнительно ищутся поля, записанные **без псевдонима** (`НайтиСсылкиНаГолыеПоля`): из текста
   удаляются уже разобранные обращения `Псевдоним.Поле`, а оставшиеся имена сопоставляются с полями
   таблиц запроса (`ИменаПолейОбъекта`) и стандартными реквизитами.

Запись результата — `ЗаписатьНаборЗаписей` порциями по 500 записей; ключ накопления нормализуется
(`ВРег(СокрЛП(X)) + "|" + ВРег(СокрЛП(Y))`), так как платформа сравнивает строки без учёта регистра
и конечных пробелов.

**Подбор ролей по полям запросов** в `ППГД_ПодборРолейДляПрофиляГруппДоступа` — кнопка «Роли по
полям запросов» (команда формы `акс_ПоказатьРолиПоПолямЗапросов`), серверная процедура
`акс_ЗаполнитьДеревоРолейПоПолямЗапросов`:

- дерево группируется по объектам метаданных, поля которых используются в запросах модулей
  (учитываются «активные» метаданные профиля — объекты профиля, типы реквизитов, регистры
  движений, подсистемы); имя узла — полное имя объекта и перечень полей (до 5 полей, далее
  «и еще N»);
- в узел попадают только те роли, которые дают доступ к этим полям: проверка выполняется
  функцией `ПараметрыДоступа("Просмотр", ОбъектМетаданных, СписокПолей, Роль)`, поэтому
  учитываются ограничения доступа на уровне записей и полей (RLS);
- поля табличных частей передаются как `<ИмяТЧ>.<Реквизит>`, поле `*` из проверки исключается;
  объекты, недопустимые в `ПараметрыДоступа` (обработки, отчёты, константы и т. п.), пропускаются;
- строки ролей берутся из ТЧ `РолиМетаданных`, поэтому работают команды
  `акс_ПроставитьФлаги` / `акс_СнятьФлаги` и перенос ролей в профиль;
- объекты вне профиля показываются в **дереве реквизитов**, а не отдельной группой дерева ролей:
  процедура `ДополнитьРеквизитыОбъектовВнеПрофиля` отбирает из регистра `ППГД_ПоляВЗапросахМодулей`
  записи по объектам вне активных метаданных профиля (`НЕ Метаданные В (&СписокМетаданных)`) и
  добавляет в ТЧ `РеквизитыОбъектов` **строку на каждое используемое поле** с `Использовать = Ложь`;
  в имени реквизита видно, какому объекту профиля он нужен: `Поле (нужен для: Документ.ЗаказПокупателя)`;
- объект считается нужным профилю, только если к его полям обращаются модули объектов профиля:
  принадлежность модуля объекту профиля определяется по пути модуля из ресурса `СписокМодулей` —
  имя объекта ищется в **любом** элементе пути (`<Тип>/<ИмяОбъекта>/...`) функцией
  `ОбъектыПрофиляВМодулях` (не только во втором элементе: перед типом может стоять каталог
  выгрузки, например `src/Documents/...`). Отбор условиями `ПОДОБНО` по каждому объекту профиля не
  используется: у профиля ERP объектов больше тысячи, а запрос с таким числом параметров платформа
  не разбирает;
- регистр читается один раз: реквизит формы `ОбъектыВнеПрофиляЗаполнены` сбрасывается при смене
  состава объектов профиля и по команде «Заполнить»;
- отметка строки объекта вне профиля делает **сам объект** активным метаданным профиля:
  `ПолучитьАктивныеМетаданныеТиповРеквизитов` для строк без записи в `МетаданныеПоРеквизитам`
  добавляет объект строки. После этого роли по объекту подбираются обычным путём и появляются в
  дереве ролей во всех режимах группировки; снятие отметки убирает объект из активных метаданных.
  Обработчик флажка в дереве реквизитов пересчитывает данные (`ОбновитьДанныеНаСервере`);
- в режиме «По полям запросов» по объектам вне профиля проверяются **только отмеченные поля**
  (`ПоляЗапросовПоМетаданнымПрофиля`);
- реквизиты ТЧ `ДополнительныеРеквизиты` при заполнении дерева реквизитов сразу снимаются с отметки;
- заполнение сопровождается диагностическим сообщением (`ВывестиДиагностикуОбъектовВнеПрофиля`).

Попутно: в список метаданных для запроса ролей из регистра `ПраваРолей` добавлены **сами объекты
профиля** — роли на объект целиком видны во всех режимах группировки; в `ЗаполнитьНаСервере`
добавлены ветки режимов «Право доступа» и «По полям запросов».

## 7. Обмен правами через XDTO (выгрузка/загрузка)

### 7.1 XDTO-пакет `ППГД_ПраваДоступа`

Файл: `src/XDTOPackages/ППГД_ПраваДоступа/ППГД_ПраваДоступа.mdo` (+ `Package.xdto`).
Синоним «Права доступа», пространство имён `http://rules`.

Основные типы: `Профиль`, `ПрофильГруппа`, `ГруппаДоступа`, `ГруппаДоступаГруппа`,
`Пользователь`, `ГруппаПользователей`, `РолиСтрока`, `ВидыДоступаСтрока`,
`ЗначенияДоступаСтрока`, `НазначениеСтрока`, `СоставГруппыПользователейСтрока` и
коллекции `Роли`, `ВидыДоступа`, `ЗначенияДоступа`, `Назначение`, `Состав`.

> Имена XDTO-типов и пространство имён `http://rules` при переименовании не менялись —
> формат обмена совместим с прежним.

### 7.2 Сценарий выгрузки

1. Обработка (`ППГД_ВыгрузкаЗагрузкаПрав`) формирует `КомпонентыОбмена`
   через `ППГД_ОбменДаннымиXDTOСервер.ИнициализироватьКомпонентыОбмена`.
2. `ОткрытьФайлВыгрузки` → `Выгрузка*` (создают XDTO-объекты) →
   `ФабрикаXDTO.ЗаписатьXML`.
3. Структуры-приёмники заполняет `ППГД_МенеджерОбменаПравамиДоступа.Выгрузить*`.

### 7.3 Сценарий загрузки

1. `ППГД_ОбменДаннымиXDTOСервер.ЗагрузкаСообщения` → `ПрочитатьСообщениеОбмена`.
2. `ОбъектXDTOВСтруктуру` → `СтруктураОбъектаXDTOВДанныеИБ` →
   `КонвертацияСвойствСтруктурыОбъектаXDTO` → запись объектов ИБ.
3. Ведётся `ТаблицаПротокола` и счётчики «Создано/Обновлено» по типам объектов.

### 7.4 Хранение прав

Права хранятся в типовых объектах: `Справочник.ГруппыДоступа` (реквизит `Профиль`, ТЧ
`ЗначенияДоступа`, `ВидыДоступа`, `Пользователи`) и `Справочник.ПрофилиГруппДоступа`
(ТЧ `Роли`, `ЗначенияДоступа`, `ВидыДоступа`, `Назначение`). Собственные дополнения —
ТЧ `пд_Объекты`, `Расш_ПГДРодительскиеПрофили` и реквизиты авторства/дат.
