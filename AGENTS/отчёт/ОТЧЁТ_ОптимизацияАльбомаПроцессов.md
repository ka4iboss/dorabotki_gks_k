# ОТЧЁТ — Оптимизация альбома процессов (память и отзывчивость)

## Проблема

Альбом процессов с большим количеством картинок создавал высокую
нагрузку на оперативную память и подвисал сеанс после закрытия формы.
Выявлено четыре источника:

1. **Слайдер ширины картинок** перестраивал весь альбом при каждом
   изменении. Каждый «чих» слайдера = серверный вызов + перекодирование
   всех картинок в base64 + пересылка HTML на клиент.
2. **`ЗаменитьКодыИзображенийНаDataURI`** выполнял серию
   `СтрЗаменить` по всей строке HTML для каждой картинки. Для альбома
   на 50 картинок и HTML в 20 МБ это 50 копий растущей строки внутри
   платформы.
3. **`СоответствиеКодДанныеИзображений`** не имело кеша — картинки
   перечитывались из БД при каждом построении альбома.
4. **HTMLDocumentField не освобождает память** при закрытии формы —
   data:URI в base64 остаются в DOM браузера, пока GC не пройдёт.

## Решение

### A. Слайдер без перестроения альбома

Файл:
`src/Catalogs/ДемонстрационныеСценарии/Forms/АльбомПроцессов/Module.bsl`.

В построителе `ГКСИ_АльбомПроцессов.ГКСИ_СобратьДокумент` стиль
ограничения ширины картинок вынесен в отдельный блок
`<style id="album-imgs-style">…</style>`. Слайдер на клиенте вызывает
новый обработчик `ГКСИ_ОбновитьСтильКартинок`:

```bsl
Документ = Элементы.ТекстHTML.Документ;
УзелСтиля = Документ.getElementById("album-imgs-style");
УзелСтиля.textContent = НовыйCSS;
```

Никакого обращения к серверу, никакой перекодировки картинок. Стиль
применяется мгновенно, картинки не перезагружаются.

Старые серверные методы `ГКСИ_ПерестроитьАльбом` / `ГКСИ_СобратьАльбомНаСервере`
сохранены для совместимости, но больше не вызываются из обработчиков
слайдера.

### B. Потоковая подстановка картинок

Файл: `src/CommonModules/ГКСИ_MarkdownПереопределяемый/Module.bsl`.

`ЗаменитьКодыИзображенийНаDataURI` переписан с серии `СтрЗаменить` на
один линейный проход:

1. `ГКСИ_СобратьВхожденияКодов` — два `СтрНайтиВсеПоРегулярномуВыражению`
   (для `<img src="КОД">` и `![alt](КОД)`), сортировка результатов
   по позиции начала, формирование массива структур `{Позиция, Длина, Замена}`.
2. `ГКСИ_ПрименитьЗаменыКФрагментам` — нарезка исходного текста
   через `Сред(ИсходныйТекст, Курсор, Длина)` с подстановкой готовых
   замен и финальным `СтрСоединить`. Без промежуточных полных копий
   строки.

Дополнительно:

- `ДанныеФайла.Base64 = ""` сразу после формирования `DataURI` —
  уменьшает пиковое потребление памяти.
- `СоответствиеКодДанные = Неопределено` после формирования массива
  вхождений.
- `Вхождения = Неопределено` после применения замен.

### C. Кеш «Код → data:URI» через общий модуль

Создан новый общий модуль:
`src/CommonModules/ГКСИ_ДанныеИзображенийMarkdownПовтИсп/`.

Свойства модуля:
- `Server = true`, `ExternalConnection = true`,
  `ReturnValuesReuse = DuringSession`.
- Экспорт `СоответствиеКодДанные(МассивКодов)` возвращает
  соответствие `Код → {Base64, Mime}`.

Платформа сама кеширует результат экспортной функции в разрезе
параметров на время сеанса. Это значит:

- повторный вызов с тем же массивом кодов не выполняет запрос к БД;
- повторное построение альбома (после открытия, после смены языка,
  после перестроения по внешнему событию) не перекодирует картинки;
- кеш автоматически инвалидируется платформой при изменении данных
  файла инструкции.

`ГКСИ_MarkdownПереопределяемый.СоответствиеКодДанныеИзображений`
теперь однострочный делегат:

```bsl
Функция СоответствиеКодДанныеИзображений(МассивКодов)
    Возврат ГКСИ_ДанныеИзображенийMarkdownПовтИсп.СоответствиеКодДанные(МассивКодов);
КонецФункции
```

### D. Не реализовано

Перенос `ТекстHTML` во временное хранилище отклонён. Причина:
после пункта A HTML по сети при движении слайдера больше не идёт,
а `УстановитьТекст()` у HTMLDocumentField доступен только в толстом
клиенте. Альбом открывается в тонком — поэтому единственный
рабочий канал доставки HTML остаётся через реквизит формы, что и
было.

### E. Очистка HTML-поля перед закрытием формы

Файл:
`src/Catalogs/ДемонстрационныеСценарии/Forms/АльбомПроцессов/Module.bsl`.

Добавлен клиентский обработчик `ГКСИ_ПередЗакрытием`, привязанный
через `УстановитьДействие("ПередЗакрытием", …)` в
`ГКСИ_ПриСозданииНаСервере`. Метод `ГКСИ_ОчиститьHTMLПередЗакрытием`
делает четыре вещи в порядке убывания веса:

1. **Обнуляет `src` у всех `<img>`** через `Документ.images`. Снимает
   ссылки на декодированные bitmap-объекты в WebKit — до этой правки
   они удерживались в bitmap-кеше до принудительного GC.
2. **Очищает `<head>`** (`head.innerHTML = ""`). Снимает
   `<style id="album-imgs-style">`, `<script>`, `<link>`, `<meta>`.
3. **Очищает `<body>`** (`body.innerHTML = ""`). Снимает все DOM-узлы
   с их data:URI в атрибутах.
4. **Очищает реквизит `ТекстHTML`** (`ТекстHTML = ""`). Снимает
   гигантскую строку HTML из контекста управляемой формы.

Все шаги в `Попытка/Исключение` — документ может быть ещё не
сформирован или уже разрушен. Полная выгрузка bitmap-кеша WebKit
происходит после закрытия формы, когда платформа разрушает
`HTMLDocumentField`.

### F. Сжатие картинок в кеше сеанса

Файл:
`src/CommonModules/ГКСИ_ДанныеИзображенийMarkdownПовтИсп/Module.bsl`.

Кеш `СоответствиеКодДанные` принимает второй параметр
`МаксимальнаяШиринаПикселей`. Если он > 0 — каждая картинка при
первом чтении из БД проходит через `ОбрабатываемаяКартинка`:

- `УстановитьРазмер(Ширина, 0)` — пропорциональный ресайз;
- `УстановитьФормат` — JPEG для фото/BMP, PNG для PNG/GIF
  (сохраняем альфа-канал);
- результат кладётся в кеш как готовый base64.

**Алгоритм по форматам:**

| Исходник | Целевой формат | Почему |
|----------|----------------|--------|
| JPEG/JPG | JPEG | Меньше base64 без потерь смысла |
| BMP | JPEG | Огромный выигрыш (~10x) |
| PNG | PNG | Сохраняем прозрачность |
| GIF | PNG | Теряется анимация (некритично для инструкций) |
| SVG | (пропускаем) | Вектор, сжимать нечего |

**Источник ширины:** форма «АльбомПроцессов» через новый
`ГКСИ_ШиринаКартинокВПикселях(Число, Единица)`:

- `px` — берём как есть;
- `%` или пусто — 1280 px (A4 @ 96dpi × 1.5 retina).

**Кеш с разной шириной** хранится отдельно (платформа кеширует
в разрезе параметров), так что смена ширины пользователем не
ломает уже закешированные варианты.

**Цепочка вызовов:**

```
Форма АльбомПроцессов
  └─> ГКСИ_СобратьАльбомНаСервере
        └─> ГКСИ_ШиринаКартинокВПикселях  → целевая ширина
        └─> ГКСИ_АльбомПроцессов.СобратьДокументАльбома
              └─> ГКСИ_ЗаполнитьОписанияПоЯзыкам(..., МаксимальнаяШиринаПикселей)
                    └─> ГКСИ_MarkdownПереопределяемый.ЗаменитьКодыИзображенийНаDataURI(..., МаксимальнаяШиринаПикселей)
                          └─> ГКСИ_ДанныеИзображенийMarkdownПовтИсп.СоответствиеКодДанные(..., МаксимальнаяШиринаПикселей)
                                └─> ПодготовитьДанныеКартинки (ресайз + перекодирование)
```

**Ожидаемый выигрыш:** альбом с 50 картинками 1920×1080 в PNG →
после сжатия до 1280 px и перевода в JPEG base64 падает с
100–200 МБ до 10–20 МБ. Это **×10** по памяти сервера, скорости
передачи клиенту и пику RAM браузера.

**Минусы:**
- небольшая CPU-цена при первом показе картинки в сеансе (десятки мс на 1 картинку);
- качество JPEG ниже оригинала (но для альбома приемлемо);
- GIF теряет анимацию (на инструкциях её и нет).

**Обратная совместимость:** параметр `МаксимальнаяШиринаПикселей`
имеет дефолт `0` — для других потребителей (`ЗаменитьКодыИзображенийНаDataURI`,
`СоответствиеКодДанныеИзображений`) поведение не изменилось.
