## 1. Реализация Markdown для типовых «Описаний процессов» ERP

Типовой механизм 1С:ERP «Описания процессов» (справочник `ДемонстрационныеСценарии`)
хранит текст описания как HTML в присоединённом файле и редактируется голым HTML.
Расширение дополняет его возможностью редактирования и хранения в Markdown, сохранив
типовой HTML-вывод.

### 1.1 Взаимствованный справочник `ДемонстрационныеСценарии`

Файл: `src/Catalogs/ДемонстрационныеСценарии/ДемонстрационныеСценарии.mdo`

- Справочник принят в расширение (`objectBelonging = Adopted`, `extendedConfigurationObject`).
- Полное определение справочника взято из основной конфигурации (производимые типы,
  стандартные реквизиты, реквизиты, табличные части) — это необходимо, чтобы подменяемая
  форма «видела» реквизиты объекта (`Description`, `Code`, `Parent`, `ПолныйКод`,
  `ОбъектыКонфигурации`, `ПрофилиГруппДоступа`, `Комментарий` и др.).
- Добавлены реквизиты-расширения:
  - `ТекстMarkdown` — `Строка` (неограниченная); хранит Markdown всех языков в одном
    реквизите с разделителями `<!--md:lang:<КодЯзыка>--> ... <!--/md:lang:<КодЯзыка>-->`;
  - `MarkdownСформирован` — `Булево`, признак того, что Markdown уже инициализирован
    (защита от повторной миграции HTML → Markdown).
- Зарегистрирована подменяемая форма `ФормаЭлемента` (остальные формы справочника
  наследуются из основной конфигурации).

### 1.2 Подменяемая форма `ФормаЭлемента`

Файлы:
- `src/Catalogs/ДемонстрационныеСценарии/Forms/ФормаЭлемента/Form.form`
- `src/Catalogs/ДемонстрационныеСценарии/Forms/ФормаЭлемента/Module.bsl`

Форма полностью повторяет типовую (статусы, режимы «Просмотр/Редактирование/Перевод»,
языки, отчёт `ДемонстрационныеСценарииОбъекта`, профили и объекты конфигурации,
поиск/замена), но вместо голого HTML-редактора используется подсистема `ГКСИ_РМ_РедакторMarkdown`.

Изменения в форме (`Form.form`):
- добавлены реквизиты: `ТекстMarkdownСтрока`, `ФайлыBase64`, `ТекстПросмотр`;
- добавлена группа `ГруппаMarkdownРедактор` (контейнер панели редактора);
- добавлены обработчики: `ПриОткрытии` (OnOpen) и клиентский `ПередЗаписью` (BeforeWrite).

Логика в модуле (`Module.bsl`):
- `ПриСозданииЧтенииНаСервере()`: настройка языков, заполнение `ФайлыBase64`,
  вставка панели `ГКСИ_MarkdownСерверВызовСервера.ВставитьПолеРедактированияТекстаНаФорму`.
- `ПолучитьСегментMarkdown` / `ЗаменитьСегментMarkdown` — работа с языковыми сегментами.
- Переключение языков подставляет нужный сегмент в `ТекстMarkdownСтрока`.
- `ПриОткрытии()`: миграция существующего HTML-описания в Markdown при первом открытии
  (`htmlToMd`); при неудаче миграция повторяется на записи, с защитой от потери данных
  (пустой Markdown не перезаписывает существующий HTML).
- `ПередЗаписью()` (клиент): Markdown → HTML с base64-встраиванием картинок; результат
  заносится в строку `ОписанияСценария` (реквизит `ТекстHTML`).
- `ПередЗаписьюНаСервере()`: сохранение новых присоединённых файлов
  (`ГКСИ_MarkdownСерверВызовСервера.ЗаписатьНовыеПрисоединенныеФайлы`), сборка общего реквизита
  `ТекстMarkdown` из сегментов, запись HTML-файлов типовым механизмом
  (`ДемонстрационныеСценарии.ЗаписатьНовыеОписанияСценариевИзФормыОбъекта`).
- Подключаемые обработчики подсистемы Markdown (`РМ_Подключаемый_*`).

Вывод остаётся типовым: Альбом процессов, отчёт и «Поиск и замена» работают как раньше,
поскольку HTML пишется стандартным механизмом в типовой файл `ОписанияСценария`.

## 2. Исправление ошибок из Problems.tsv

### 2.1 Удалены принятые модули `ДемонстрационныеСценарии*` (исправлены все «Блокирующая» ошибки)

В расширении присутствовали принятые общие модули `ДемонстрационныеСценарии`,
`ДемонстрационныеСценарииВызовСервера`, `ДемонстрационныеСценарииКлиент`,
`ДемонстрационныеСценарииКлиентСервер` с содержимым, скопированным из основной конфигурации.
Это порождало блокирующие ошибки:

- `bsl-legacy-check-module-extension` — «Повторяющееся имя метода … уже есть в
  заимствованном модуле» (принятый модуль наследует базовый, копия создаёт дубликаты);
- `extension-method-prefix` — методы базового модуля не имеют префикса расширения `ГКСИ_`.

Решение: каталоги модулей удалены, ссылки на них убраны из `Configuration.mdo`.
Типовые функции (`ЗаполнитьОписанияСценариев`, `ЗаписатьНовыеОписанияСценариевИзФормыОбъекта`,
`ЯзыкиКонфигурации` и др.) наследуются из основной конфигурации и используются как есть.

### 2.2 Документ `ГКСИ_Инструкция` — недопустимые директивы компиляции

Файл: `src/Documents/ГКСИ_Инструкция/ObjectModule.bsl`

Из модуля объекта удалены директивы `&НаСервере` (модуль объекта всегда выполняется на
сервере и не поддерживает директивы компиляции формы). Исправлены ошибки
`form-module-pragma` и `bsl-legacy-check-pragma`.

### 2.3 Обработка `ГКСИ_ФормированиеИнструкции` — веб-клиент

Файл: `src/DataProcessors/ГКСИ_ФормированиеИнструкции/Forms/Форма/Module.bsl`

Процедура `Печать()` использовала на клиенте серверные конструкции
`ПолучитьИмяВременногоФайла` и `ЗаписьТекста`, недоступные в веб-клиенте. Формирование
HTML-файла вынесено в серверную функцию `СформироватьHTMLФайлНаСервере` (запись файла →
временное хранилище), а на клиенте файл скачивается через `НачатьПолучениеФайла`.

### 2.4 Косметические правки

- В модуле формы `ДемонстрационныеСценарии` устаревший псевдоним `ЭтаФорма` заменён
  на `ЭтотОбъект`.

## 3. Восстановление кодировки файла

При правках с помощью PowerShell-скриптов через `[System.IO.File]::ReadAllText/WriteAllText`
без явной кодировки файл `Module.bsl` формы `ДемонстрационныеСценарии` был прочитан как
Windows-1251 и записан как UTF-8 — содержимое оказалось дважды закодировано (мохибейк),
а переводы строк — в LF вместо CRLF.

Исправлено:
- снято двойное кодирование (UTF-8 → CP1251 → исходный UTF-8);
- переводы строк нормализованы в CRLF (как в остальном проекте: CR=LF, без «голых» LF).

Остальные отредактированные файлы (справочник, форма, конфигурация, модули документа и
обработки, README) проверены — кодировка UTF-8 без BOM корректна, мохибейк отсутствует.

## Ограничения

- Статический XML/BSL-дамп не компилируется — проверка возможна только после загрузки
  расширения в Конфигуратор/EDT.
- `htmlToMd` приблизителен — сложная вёрстка может конвертироваться неточно; после
  миграции рекомендуется выборочно проверить описания.
- В `Problems.tsv` остаются «Незначительная» замечания стиля во встроенной сторонней
  библиотеке `ГКСИ_*` (структура модулей, документирующие комментарии, префиксы имён без
  `ГКСИ_` и т.п.), а также рекомендации по правам ролей (`right-delete`, `right-start-*`)
  и 2 замечания производительности `query-in-loop` в обработке `ГКСИ_ФормированиеИнструкции`.

## 4. Кнопки «Добавить»/«Удалить» в панели групп на ФормаЭлемента и ФормаГруппы

В `cfe to xml` (новый EDT-проект, импортированный из CFE) есть рабочая
логика добавления/удаления связи с группой через кнопки командной панели.
В EDT-проекте `Доработки_ГКС_К` программный построитель
панели `ГКСИ_ДобавитьПанельГруппСценария()` уже был реализован в обоих
формах, но **клиентские обработчики-делегаты команд были потеряны** —
кнопки создавались, но нажатие не обрабатывалось, что давало маркеры
SU90 «Неиспользуемый метод» (см. `ПЛАН_ИсправленияОшибокEDT.md`, §17).

Что сделано:

### 4.1 `ФормаЭлемента/Module.bsl`

Добавлены 3 клиентские процедуры (по образцу `cfe to xml`):

- `ГКСИ_ДобавитьГруппу(Команда)` — открывает форму выбора группы
  (`Catalog.ДемонстрационныеСценарии.ФормаВыбора`) с параметром
  `ВыборГруппИЭлементов = Группы` и отбором `ЭтоГруппа = Истина`;
  результат возвращается через `ОписаниеОповещения`.
- `ГКСИ_ЗавершениеВыбораГруппы(РезультатВыбора, ДополнительныеПараметры) Экспорт` —
  обработчик оповещения: проверяет, что значение заполнено и не дублирует
  уже существующую строку, добавляет новую строку в таблицу формы
  `ГКСИ_ГруппыСценария` (поле `ПолныйКодКонтекстный` обнуляется —
  пересчитается в `ГКСИ_ПриЗаписи` модуля объекта).
- `ГКСИ_УдалитьГруппу(Команда)` — удаляет текущую строку таблицы формы.

Все три процедуры помечены `@skip-warning` (подавление SU90 — линтер не
видит вызовов из `Команда.Действие = "..."` и `ОписаниеОповещения(...)`).

### 4.2 `ФормаГруппы/Module.bsl`

- `ГКСИ_ДобавитьПанельГруппСценария()` переделан из заглушки в реальный
  построитель: добавляет команды `ГКСИ_ДобавитьГруппу`/`ГКСИ_УдалитьГруппу`
  и кнопки **в группу-родитель таблицы `ГКСИ_ГруппыСценария`**, которая
  уже декларирована в `Form.form` (внутри группы `ГруппаКомментарийРодитель`)
  вместе со всеми колонками, поиском и состоянием просмотра.
- Добавлены те же 3 клиентские процедуры, что и в `ФормаЭлемента`,
  с дополнительной проверкой `РезультатВыбора = Объект.Ссылка` —
  запрет добавлять группу в саму себя.

> **Важно:** первая реализация добавляла кнопки прямо в `ТаблицаФормы`,
> что падало с ошибкой `Недопустимое значение параметров` — `Table` не
> может быть родителем объекта `Button` в иерархии элементов формы
> (кнопки могут лежать только в `FormGroup`). Родителем кнопки делается
> `ТаблицаФормы.Родитель`. Подробности и корректный шаблон — в
> `рецепты/Рецепты.md`, раздел «Добавить кнопки в командную панель уже
> декларированной в Form.form таблице».

### 4.3 Оставшиеся маркеры EDT

После правки остаются только warnings:

- `SU232` × 5 — ссылки на функции удалённого общего модуля
  `ДемонстрационныеСценарии*` (`ДобавитьТегиТелаЕслиНеобходимо`,
  `РезультатОбновленияПрисоединенногоФайла`, `ПараметрыДобавленияФайла`,
  `ИмяФайлаОписанияСценария`, `ДобавитьФайл`) — существовали до правки
  и не имеют отношения к этой задаче (см. §2.1).
- `SU30` × 4 — «Пропущено определение параметра для: РезультатВыбора /
  ДополнительныеПараметры» на обработчиках оповещения
  `ГКСИ_ЗавершениеВыбораГруппы`. Это **известная ложь линтера EDT**
  на стандартном паттерне `ОписаниеОповещения(ИмяПроцедуры, ЭтотОбъект)`
  — аналогичные обработчики в `cfe to xml` не показывают SU30 только
  потому, что BSL-кеш того проекта ещё не пересчитан. Код рабочий,
  рекомендуется полный пересчёт проекта в EDT после импорта.
- `SU90` × 4 — подавлены `@skip-warning` (см. выше).
- `problem` (компиляция) — 0.
