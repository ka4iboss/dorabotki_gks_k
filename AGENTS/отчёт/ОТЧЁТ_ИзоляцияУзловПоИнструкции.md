# ОТЧЁТ: Изоляция узлов по инструкции-источнику (версия 1.78)

## Контекст

При последовательной загрузке инструкций разных ролей (ГИП → ДМТО) в
Альбоме процессов появлялись чужие шаги: например, в ДМТО-альбом под
общей группой «Согласование ТКП» попадали ГИП-уникальные элементы
(«Задачи и процессы согласований», «Выбор согласовантов», «Завершение
согласования ТКП»). Причина: операция «обновить всё» переиспользовала
существующие узлы и **перезаписывала** реквизит `ГКСИ_ИнструкцияИсточник`
на текущую инструкцию, ломая логику фильтрации.

## Корневая проблема (понимание, к которому пришли в диалоге)

- **Группа** может принадлежать нескольким инструкциям одновременно:
  одна запись в справочнике, несколько записей в РС `ГКСИ_ГруппыСценариев`.
  Это **общий** узел — должен быть виден во всех своих инструкциях.
- **Элемент** (шаг) — всегда принадлежит **одной** инструкции:
  уникальный шаг роли. Должен быть виден только в своей ветке.
- `ГКСИ_ИнструкцияИсточник`:
  - **пустой** → узел общий (показывать везде);
  - **заполнен** → узел уникальный (показывать только в этой инструкции).

## Реализовано

### Шаг 1 — переиспользование без перезаписи источника

`src/CommonModules/ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl`,
`ОбработатьУзелРекурсивно`:

- реквизит `ГКСИ_ИнструкцияИсточник` заполняется только для **новых**
  узлов (`ЭтоНовыйЭлемент = Истина`);
- для существующих, найденных через авто-резолв или явное действие
  «Обновить», реквизит сохраняется прежним;
- заполняется и для групп, и для элементов (раньше — только для
  элементов).

### Шаг 2 — защита авто-резолва от переиспользования чужих узлов

`src/CommonModules/ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl`,
`ОбработатьУзелРекурсивно` (после вызова `ГКСИ_АвтоРезолвУзлаПоКешу`),
`НайтиСуществующихПоИмени`, `ГКСИ_ПолучитьИнструкциюИсточникИзКеша`:

- в `НайтиСуществующихПоИмени` и `ГКСИ_ПолучитьИнструкциюИсточникИзКеша`
  кеш существующих узлов обогащён полем `ГКСИ_ИнструкцияИсточник`;
- в `ГКСИ_АвтоРезолвУзлаПоКешу` сама фильтрация по источнику **не**
  делается (функция фильтрует только по типу — `ЭтоГруппа`/элемент);
- в `ОбработатьУзелРекурсивно` сразу после авто-резолва (строки 899-919)
  добавлена проверка источника:
  - если у найденного узла `ГКСИ_ИнструкцияИсточник` заполнен и не
    совпадает с текущей инструкцией — `РешениеПоУзлу` сбрасывается в
    `Неопределено` (узел будет создан как новый);
  - если у узла источник пустой (общая группа) или не заполнен
    (дозаполнение) — узел переиспользуется как обычно.
- при авто-резолве больше не подменяются уникальные узлы другой роли —
  «обновить всё» в авто-резолве работает только для своих и общих.

**Важно про форму конфликтов**: «обновить всё» на форме конфликтов
(`РешенияПоКонфликтам`) по-прежнему применяет «Обновить» ко всем
выбранным существующим узлам без проверки источника — это осознанное
решение пользователя, которое должно быть применено как есть. Шаг 2
защищает только **автоматический** путь (когда форма конфликтов не
открывалась). Если форма открыта и пользователь явно выбирает
«Обновить всё» — это его решение, и оно будет выполнено. Если в
результате такого осознанного выбора `ГКСИ_ИнструкцияИсточник` чужих
элементов/групп окажется перезаписан — это исправляется отдельной
процедурой (Шаг 3).

### Шаг 3 — процедура исправления существующих данных

`src/CommonModules/ГКСИ_ГруппыСценариевСервер/Module.bsl`,
новая экспортная процедура `ГКСИ_ИсправитьИнструкцииИсточников()` +
вспомогательная `ГКСИ_СобратьКорневыеИнструкцииУзла` (с защитой от
циклов через `Посещённые`):

- обходит все узлы справочника через `ГКСИ_ГрафГрупп()`;
- для каждого узла определяет множество корневых инструкций (подъём по
  РС `ГКСИ_ГруппыСценариев` до самого верхнего предка);
- если множество содержит **ровно одну** корневую инструкцию →
  `ГКСИ_ИнструкцияИсточник = эта инструкция`;
- если множество содержит **более одной** (общий узел) →
  `ГКСИ_ИнструкцияИсточник` очищается;
- по итогам пишет в журнал регистрации (`ГКСИ.ГруппыСценариевСервер`,
  «обработано N узлов, изменено M»).

Вызывается **вручную** после исправления архитектуры, чтобы привести
уже испорченные «обновить всё» данные в соответствие с реальной
структурой РС.

### Шаг 4 — фильтр в Альбоме процессов

`src/CommonModules/ГКСИ_АльбомПроцессов/Module.bsl`,
`ГКСИ_ОтфильтроватьУзлыПоИнструкции`:

- в пакет запроса `ГКСИ_ЗагрузитьДанныеУзлов` добавлено поле
  `ГКСИ_ИнструкцияИсточник`, заполняется в `ИнструкцииИсточникиПоУзлам`;
- в `СобратьДокументАльбомаПоГруппам` после загрузки данных вызывается
  функция `ГКСИ_ОтфильтроватьУзлыПоИнструкции(Узлы, МассивКорневыхГрупп, ДанныеУзлов)`:

  **Логика (после правки 1.83).** У каждого узла определяется множество
  корневых инструкций:
  - если реквизит `ГКСИ_ИнструкцияИсточник` заполнен (только для элементов,
    потому что для групп реквизит недоступен) → одноэлементное множество
    `{Источник}`;
  - если пустой → определяется через подъём по графу до самых верхних
    предков через РС `ГКСИ_ГруппыСценариев` (массовый подъём через
    `ГКСИ_ГрафГрупп()` + `ГКСИ_СобратьКорневыеИнструкцииУзла`).

  Узел включается в альбом тогда и только тогда, когда хотя бы один из
  его корней входит в множество корневых групп альбома
  (`МассивКорневыхГрупп`).

  **Важно**: общая группа, принадлежащая нескольким инструкциям (через
  РС), показывается **только в тех альбомах**, в множество корней которых
  входит хотя бы один её корень. Например, группа из инструкций 001 и 012
  **не попадёт** в альбом инструкции 025 — потому что пересечение её
  корней с корнями альбома 025 пустое.

  В ранних версиях (1.78, 1.80–1.82) была ошибочная логика «общий узел —
  показываем в любой ветке»: это приводило к тому, что общая группа
  попадала во все альбомы подряд.

## Что нужно сделать пользователю после применения версии 1.78

1. **F7 в EDT** для обновления конфигурации БД.
2. **Запустить** `ГКСИ_ГруппыСценариевСервер.ГКСИ_ИсправитьИнструкцииИсточников()`
   (через внешнюю обработку, форму отладки или «Выполнить код»).
3. После прогона — переформировать Альбом процессов для каждой
   инструкции. ГИП-уникальные шаги больше не появятся в ДМТО-альбоме,
   общие группы останутся видны везде.
4. Дальнейшие загрузки (с правильным выбором «Обновить» или «Создать
   новый») будут работать корректно сами.

## Известные ограничения

- Шаг 3 (исправление данных) запускается **вручную**. Для повседневной
  работы это не нужно, но после больших миграций данных или смены
  формата инструкций имеет смысл прогонять разово.
- «Обновить всё» по-прежнему применяет «Обновить» ко **всем**
  существующим узлам из кеша. Шаг 2 защищает только **авто-резолв**
  (когда пользователь не открывал форму конфликтов); если пользователь
  вручную выбрал «Обновить всё» на форме — это его осознанное решение,
  и оно будет применено.
- Альбом процессов по выделенным нескольким корневым группам
  (`МассивГрупп`) применяет фильтр по **множеству** корней — узел
  показывается, если входит хотя бы в одну из корневых инструкций.
