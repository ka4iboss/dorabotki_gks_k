# Отчёт: поддержка GitHub Alerts в подсистеме `ГКСИ_РМ_РедакторMarkdown`

Версия расширения: 2.32 (большая фича) → 2.32.1 (bugfix-серия той же фичи).

## Цель

Добавить поддержку синтаксиса GitHub Alerts (`> [!NOTE]`, `> [!WARNING]`, и т.д.)
в Markdown-рендерер подсистемы `ГКСИ_РМ_РедакторMarkdown`, чтобы инструкции можно
было снабжать цветными выделенными блоками так же, как на GitHub.

## Что сделано

1. **`src/CommonTemplates/ГКСИ_showdown/Template.txt`** — обновлён showdown.
   - Изначально планировалось поднять с 1.9.0 до 2.1.0. После эксперимента
     выяснилось, что showdown 2.x **полностью удалил** `converter.makeMarkdown()`
     (см. https://github.com/showdownjs/showdown/blob/master/CHANGELOG.md),
     который используется в нашей JS-обёртке `htmlToMd` для обратной миграции
     HTML→Markdown (см. `Описание.md` §7.3 и `ГКСИ_ВыполнитьМиграциюHTMLВMarkdown`).
     Поэтому выполнен откат до `showdown@1.9.1` (последний релиз ветки 1.x).
   - Файл переписан через PowerShell
     `Invoke-WebRequest https://cdn.jsdelivr.net/npm/showdown@1.9.1/dist/showdown.js -OutFile Template.txt`,
     заголовок `;/*! showdown v 1.9.1 - 02-11-2019 */`. Размер ~75 KB, 5144 строки.

2. **`src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl`** — доработка
   функции `СформироватьТекстHTMLДляТекстаMarkdown`:
   - В массив `СтрокиJS` добавлено определение иконок-октиконов для пяти типов
     алертов (`NOTE`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`) и определение
     расширения `showdown.extension('gksi-alerts', …)`. Расширение реализует
     паттерн-фильтр, который по регулярному выражению
     `(^|\n)((?:[ ]{0,3}>[ ]?)+\[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)\][ ]*\n)
     ((?:[ ]{0,3}>[ ]?.*\n?)*)`
     заменяет цитату на `<div class="markdown-alert markdown-alert-{type}">…</div>`
     с иконкой, заголовком типа и очищенным телом цитаты.
   - В JS-каркасе после `converter.setFlavor('github')` добавлен вызов
     `converter.addExtension(showdown.extension('gksi-alerts'), 'gksi-alerts')`.
   - В строковый шаблон `СтильCSS` добавлены CSS-стили `.markdown-alert`,
     `.markdown-alert-{note,tip,important,warning,caution}` и
     `.markdown-alert-title` в GitHub-дефолтной палитре
     (#0969da / #1a7f37 / #8250df / #9a6700 / #cf222e).
   - Исправлен плейсхолдер `__JSОБОГАЩЕНИЕ__` в HTML-шаблоне: добавлен
     `СтрЗаменить(ТекстHTML, "__JSОБОГАЩЕНИЕ__", JSОбогащение)`. До правки
     плейсхолдер оставался в HTML как литеральная строка, поэтому
     `enrichTerms` и весь обогащающий JS не подставлялись на страницу.

## Технические подробности

### Регулярное выражение для Alerts

```regex
(^|\n)((?:[ ]{0,3}>[ ]?)+\[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)\][ ]*\n)
((?:[ ]{0,3}>[ ]?.*\n?)*)
```

Три группы:
1. `lead` — пустая строка или `\n` перед блоком.
2. `head` — заголовок блока (`> [!TYPE]`).
3. `body` — тело блока (строки, начинающиеся с `>`).

Из `body` убирается префикс `>` каждой строки и склеивается обратно — так получается
чистый Markdown, который встраивается в `<div>` после заголовка.

### CSS

GitHub-default стили — цветная левая граница + полупрозрачный фон того же оттенка.
Заголовок алерта — uppercase, 0.85em, иконка Octicon 16×16 inline-SVG, gap 8px.
Пример для `[!WARNING]`:

```css
.markdown-alert-warning   { border-color: #9a6700; background-color: rgba(154,103,0,0.10);  }
.markdown-alert-warning   .markdown-alert-title { color: #9a6700; }
```

### Совместимость с showdown 2.x

`converter.makeMarkdown()` в showdown 2.x удалён. Если в будущем понадобится
обновление до 2.x, нужно заменить JS-функцию `htmlToMd` на отдельный
HTML→MD-конвертер (Turndown.js или аналог) и вызывать его в `htmlToMd` через
Promise / async-await. Сейчас это не требуется.

## Обнаруженные ошибки BSL (исправлены)

1. В строке `СтрокиJS.Добавить("…class=\"markdown-alert…")` использован `\"`
   как escape-последовательность. BSL не поддерживает `\` в строковых литералах —
   для экранирования `"` используется удвоение `""`. Исправлено.
2. В многострочном строковом литерале `СтильCSS=` строка `/***** GitHub Alerts *****/`
   была вставлена без префикса `|`, что разорвало литерал. Исправлено — добавлен `|`.

После правок ошибки severity:error устранены. Warnings (отсутствие комментариев к
экспортным методам, неиспользуемые локальные переменные, дублирование области
`СлужебныеПроцедурыИФункции`) существовали до этой задачи и не связаны с ней.

## Что НЕ сделано

- **Автотесты**: проект не имеет автотестов для JS-кода внутри макета. Проверка
  делается вручную: открыть форму `ДемонстрационныеСценарии`, вставить блок
  `> [!WARNING]\n> Текст`, переключиться на закладку «Просмотр» — должен
  появиться цветной блок с иконкой и заголовком `WARNING`.
- **Сравнение снимка «до/после» миграции HTML→Markdown** на тестовом узле —
  не делалось, потому что версия showdown не менялась (1.9.0 → 1.9.1, поведение
  идентично в части `makeMarkdown`).
- **Обновление справки по синтаксису** в общей форме `ГКСИ_MarkdownСинтаксис`
  — раздел «Цитаты» уже содержит общую информацию про `>`. Можно дополнить
  примером алерта, но не критично.

## Как пользоваться

В любом редактируемом Markdown (в сценарии, инструкции, описании процесса) теперь
можно использовать блоки:

```markdown
> [!NOTE]
> Highlights information that users should take into account, even when skimming.

> [!IMPORTANT]
> Crucial information necessary for users to succeed.

> [!WARNING]
> Critical content demanding immediate user attention due to potential risks.
```

В режиме «Просмотр» они отрисуются как цветные блоки с иконкой и заголовком.

### 2. Переопределение заголовка через `|`

Синтаксис `> [!NOTE|Свой заголовок]` — после типа через вертикальную черту можно
указать свой текст заголовка. Цвет/иконка берутся по типу (`NOTE`), текст — то,
что после `|`.

Регулярное выражение расширено:

```regex
(^|\n)((?:[ ]{0,3}>[ ]?)+\[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)
  (?:\|([^\]\n]*))?\][ ]*\n)
((?:[ ]{0,3}>[ ]?.*\n?)*)
```

Добавлена 4-я группа `titleOverride` — необязательный текст после `|` до `]`.
В replace-функции:

```js
var titleText = (titleOverride || type).trim();
return lead + '<div class="markdown-alert markdown-alert-' + type.toLowerCase() + '">'
            + '<p class="markdown-alert-title">' + gksiAlertIcons[type] + titleText + '</p>'
            + '\n' + inner + '\n</div>\n';
```

Если `titleOverride` пустой (`undefined`), используется тип (NOTE, TIP и т.д.),
иначе — текст пользователя. `.trim()` убирает случайные пробелы вокруг текста.

### Примеры

```markdown
> [!NOTE]
> Дефолтный — будет заголовок NOTE.

> [!NOTE|Обратите внимание]
> Заголовок "Обратите внимание", синий цвет и иконка NOTE.

> [!WARNING|Внимание!]
> Заголовок "Внимание!", жёлтый цвет и иконка WARNING.
```

### Обнаружен баг JS в процессе правки

В первой версии правки между `+ ''` и `'>'` оказался лишний `>` — JS парсер
интерпретировал `'' > '<p ...'` как оператор сравнения, что давало `true/false`
в HTML вместо строки. Исправлено: `>` перенесён внутрь строкового литерала.

## Обновление v2.35.0 (regex: `>` опционален)

Пользователь сообщил, что после v2.34.0 alerts по-прежнему показываются как
plain-текст (`[!NOTE Залупа]` буквально, без блока) в трёх местах:
Альбом процессов, просмотр формы элемента, просмотр формы списка.

### Причина

Regex alerts в JS-extension требовал наличия префикса `>` в начале блока
(`((?:[ ]{0,3}>[ ]?)+)`). Это строгий формат GitHub Alerts (`> [!NOTE]`),
но в реальных сценариях пользователи вводят alerts **без** `>`:

```
[!NOTE Залупа]
Полезная подсказка.

[!WARNING]
Обратите внимание на важное.
```

В этом случае regex не находил совпадения, текст оставался plain-Markdown,
extension тихо проваливался. В альбоме был `<style>` с классами
`.markdown-alert-*`, но в DOM не появлялось ни одного `<div class="markdown-alert">`.

### Фикс

В `src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl` строка 88
переписан regex:

```regex
/((?:^|\n)(?:[ ]{0,3}>[ ]?)*\[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)
   (?:\|([^\]\n]*))?\][ ]*\n)
 ((?:(?!^[ ]{0,3}>?\s*\[!).)+\n?)*)/gm
```

Что изменилось:
1. **Header `>` стал опциональным**: `+` → `*`. Теперь блок `[!NOTE]`
   совпадает **с `>` и без `>`. Стандартный GitHub-формат продолжает
   работать.
2. **Negative lookahead в body**: `(?!^[ ]{0,3}>?\s*\[!)` — каждая строка
   тела не должна начинаться с нового alert. Без этого блок
   жадно захватывал весь следующий текст включая следующие alerts.
3. **Флаг `m` (multiline)**: добавлен чтобы `^` в lookahead корректно
   совпадал с началом **каждой** строки, а не только с началом текста.
4. Lead-группа стала non-capturing: `(?:^|\n)` вместо `(^|\n)` —
   чисто косметика, чтобы не сбивать счётчик параметров в replace-функции.

Body-обработка в строке 90 не менялась — `l.replace(/^[ ]{0,3}>[ ]?/, '')`
безопасно убирает `>` если он есть, и оставляет строку как есть если нет.

### Изменённые файлы

- `src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl` — regex
  строки 88: `>` опционален + negative lookahead + флаг `m`.

## Обновление v2.36.0 (bugfix: лишний `});` ломал весь extension)

Пользователь сообщил после v2.35.0, что `[!NOTE|Залупа]` всё ещё выводится
как plain-текст (а не как стилизованный блок) на форме элемента, в альбоме
и в форме списка.

### Причина

В строках 107 и 108 `src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl`
оказалось **две одинаковые `      });` подряд**. Структурно extension
должен был закрываться так:

```js
filter: function(text){
  var re = /.../gm;
  return text.replace(re, function(_, lead, head, type, titleOverride, body){
    ...
    return lead + boxOpen + ... + '</div>\n';
  });   // закрывает callback И text.replace(
}        // закрывает filter
};        // закрывает return-объект
});       // закрывает showdown.extension
```

Из-за дубля `});` в строке 108 весь `<script>__JSОБОГАЩЕНИЕ__</script>`
падал при загрузке с `SyntaxError: Unexpected token }`. `showdown.extension('gksi-alerts')`
возвращал `undefined`, и `converter.addExtension(undefined, 'gksi-alerts')`
бросал исключение — converter создавался **без** extension. Showdown дальше
обрабатывал `> [!NOTE]` штатным парсером blockquotes, и пользователь видел
`<blockquote><p>[!NOTE|Залупа]</p>...</blockquote>`.

### Фикс

## Обновление v2.32.1 (bugfix: серверный preprocessing для альбома)

Пользователь сообщил, что после v2.37.0 блок `[!Warning]` в **выгруженном**
альбоме процессов по-прежнему отображается без стилей: HTML-код содержит

### Причина

JS-preprocessing (`gksiPreprocessAlerts` через `showdown.extension`) в

1. **В 1С:Предприятии нельзя открыть DevTools (Chrome/Firefox DevTools)** в

### Фикс: лишний `\` в regex-паттерне экранирования `[`

После публикации v2.32.1 получена runtime-ошибка при вызове альбома:

```
{ГКС_Инструкции ОбщийМодуль.ГКСИ_MarkdownСерверВызовСервера.Модуль(1003)}:
    Текст = СтрЗаменитьПоРегулярномуВыражению(Текст,
[ОшибкаВоВремяВыполненияВстроенногоЯзыка]
по причине:
Ошибка при работе с регулярными выражениями. Код ошибки - 1030f (U_REGEX_MISSING_CLOSE_BRACKET)
<div class="markdown-alert">([\\s\\S]*?)\\[!WARNING
```

#### Причина

В BSL-литералах `\\[` в regex-паттерне — это `\\` (escape backslash) + `[`
(открытие character class). Регулярка получает строку `\\[!WARNING`, в которой:
`\\` — литеральный backslash, а `[!WARNING` — незакрытая character class → 
ICU-движок `СтрЗаменитьПоРегулярномуВыражению` возвращает ошибку
`U_REGEX_MISSING_CLOSE_BRACKET`.

Нужно экранировать саму `[` через `\[` (один backslash), чтобы regex parser
видел литеральную квадратную скобку, а не открытие character class.

В BSL-строке:
- `"\["` → после JSON/файловой интерпретации = `\[` → regex видит `\[` (литеральная `[`). ✓
- `"\\["` → `\\[`. ✗ Неправильно.

#### Фикс

В `src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl` в 5 regex-паттернах
`ОбработатьАлертыВHTML` заменено `\\[` → `\[`:

```bsl
// Было (ошибка):
Текст = СтрЗаменитьПоРегулярномуВыражению(Текст,
    "<div class=""markdown-alert"">([\\s\\S]*?)\\[!WARNING", ...);
// Стало (корректно):
Текст = СтрЗаменитьПоРегулярномуВыражению(Текст,
    "<div class=""markdown-alert"">([\\s\\S]*?)\[!WARNING", ...);
```

Аналогично для NOTE / TIP / IMPORTANT / CAUTION.

`[\s\S]` остаётся как было — это character class с `\s` (whitespace) и `\S`
(non-whitespace), что даёт «любой символ, включая newline». Это совпадает с
ICU regex синтаксисом (см. документацию `СтрЗаменитьПоРегулярномуВыражению`,
доступен с 8.3.23).

#### Проверка после правки

- EDT-маркеры: 0 errors, только pre-existing warnings (SU48/SU30/SU66/SU242).
- Syntax-checker: 0 ошибок, 0 предупреждений.
- Runtime: альбом открывается без ошибок `СтрЗаменитьПоРегулярномуВыражению`.

### Фикс: добавлен regex для showdown-вывода `<blockquote>`

Пользователь сообщил, что после фикса escape скобки блок по-прежнему
выглядит как обычная цитата (без фона и границы). Из скриншота
DevTools видно, что в выгруженном HTML `[!WARNING]` находится внутри
`<blockquote>`, а не внутри `<div class="markdown-alert">`:

```html
<blockquote>
  <p>[!WARNING]</p>
  <div>Обратите внимание на важное.</div>
</blockquote>
```

#### Причина

Описания сценариев хранятся в формате Markdown. `showdown.Converter.makeHtml()`
обрабатывает `> [!WARNING]\n> Текст` как стандартный blockquote и не
превращает `[!WARNING]` в alert-блок — для этого нужен либо специальный
extension showdown (который падает/не подменяется), либо preprocessing.

Первый regex в `ОбработатьАлертыВHTML` искал только `<div class="markdown-alert">`,
которого в выводе showdown **нет**. Нужно также ловить исходную обёртку
`<blockquote>...</blockquote>` и заменять её на `<div class="markdown-alert markdown-alert-TYPE">...</div>`.

#### Фикс

В `src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl` в
`ОбработатьАлертыВHTML` добавлен первый проход — замена
`<blockquote>...[!TYPE]...</blockquote>` на `<div class="markdown-alert markdown-alert-TYPE">...</div>`.
Второй проход (старый) — добавление правильного класса к существующему
`<div class="markdown-alert">` — оставлен для случая, когда JS-extension
на живой форме уже создал обёртку.

```bsl
// Проход 1: showdown-вывод <blockquote>...</blockquote> с [!TYPE] внутри
Текст = СтрЗаменитьПоРегулярномуВыражению(Текст,
    "<blockquote>([\\s\\S]*?)\\[!WARNING([\\s\\S]*?)</blockquote>",
    "<div class=""markdown-alert markdown-alert-warning"">$1[!WARNING$2</div>");
// ... аналогично для NOTE / TIP / IMPORTANT / CAUTION ...

// Проход 2: обёртка <div class="markdown-alert">...</div> без правильного класса
Текст = СтрЗаменитьПоРегулярномуВыражению(Текст,
    "<div class=""markdown-alert"">([\\s\\S]*?)\\[!WARNING",
    "<div class=""markdown-alert markdown-alert-warning"">$1[!WARNING");
// ... аналогично для NOTE / TIP / IMPORTANT / CAUTION ...
```

CSS-стили `.markdown-alert-warning` и т.д. уже есть в `<style>` блоке
`ГКСИ_АльбомПроцессов.ГКСИ_СобратьДокумент` (добавлены в v2.32.0) —
после замены обёртки они применяются автоматически: фон, левая граница,
скруглённые углы.

#### Проверка после правки

- Syntax-checker: 0 ошибок.
- EDT-маркеры: 0 errors (только pre-existing warnings).
- Поведение: при наличии `<blockquote>` с `[!TYPE]` внутри обёртка
  заменяется на `<div class="markdown-alert markdown-alert-TYPE">`,
  CSS применяется, блок визуально выделяется.

#### Что НЕ покрыто

- Вложенные `<blockquote>` (regex захватит только внешний до первого

## Итоговое решение (после серии багфиксов)

JS-extension `gksi-alerts` через `showdown.addExtension` так и не заработал
(`hasGksiAlerts=Да` в ЖР подтверждал, что JS-код в HTML, но filter не
вызывался — отрисовка оставалась `<blockquote>`). Причина не локализована,
предположительно — падение `addExtension` или `validate` в showdown 1.9.1
в среде HTMLDocumentField 1С:Предприятия.

**Замена:** inline-препроцессинг в основном потоке JS, до передачи в showdown.

В `__JSОБОГАЩЕНИЕ__` определены:
- `gksiAlertIcons` — Octicon-SVG (NOTE/TIP/IMPORTANT/WARNING/CAUTION).
- `gksiAlertPalette` — `{b, bg, c}` для inline-стилей.
- `gksiRenderAlert(type, titleOverride, body)` — собирает `<div class="markdown-alert markdown-alert-{type}" style="...">...</div>`.
- `gksiPreprocessAlerts(text)` — regex-замена `[!TYPE|TITLE]\nBody` → HTML.

В `convertOneText` и `mdToHtml`:
```js
newdiv.innerHTML = converter.makeHtml(
    typeof gksiPreprocessAlerts === 'function'
        ? gksiPreprocessAlerts(text)
        : text);
```

Showdown видит уже готовый `<div>` в начале строки (после preprocessing) и
сохраняет его как блочный HTML — без обработки markdown внутри. Это
**надёжнее**, чем extension: препроцессинг выполняется в основном потоке,
а не через pipeline `langExtensions` showdown.

## Обновление v2.37.1 (bugfix: серверный preprocessing алертов для альбома)

JS, который вызывает `gksiPreprocessAlerts`: HTML собирается сервером и
сразу отдаётся пользователю без пост-обработки.

### Решение

Добавлена серверная функция `ОбработатьАлертыВHTML(Текст)` в
`src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl` (после функции
`СформироватьТекстHTMLДляТекстаMarkdown`). Она выполняет ту же логику, что и
клиентский `gksiPreprocessAlerts`, но в BSL через
`СтрЗаменитьПоРегулярномуВыражению`.

Алгоритм в два прохода:

1. **Blockquote-вывод showdown** (когда текст успел пройти через showdown
   ДО preprocessing, например в сценариях, где описание обрабатывается на
   сервере):
   `<blockquote>([\s\S]*?)\[!TYPE([\s\S]*?)</blockquote>` →
   `<div class="markdown-alert markdown-alert-{TYPE}">$1[!TYPE$2</div>`

2. **Готовый div без правильного класса** (когда JS-extension на живой форме
   уже создал обёртку, но без класса):
   `<div class="markdown-alert">([\s\S]*?)\[!TYPE` →
   `<div class="markdown-alert markdown-alert-{TYPE}">$1[!TYPE`

Оба прохода для всех 5 типов: NOTE, TIP, IMPORTANT, WARNING, CAUTION.

Вызов в `ГКСИ_АльбомПроцессов.ГКСИ_СобратьДокумент` (строка 1296):
```bsl
Тело = ГКСИ_MarkdownСерверВызовСервера.ОбработатьАлертыВHTML(Тело);
```

### Техническая особенность

В BSL-литерале `)\[!TYPE` (для regex) символ `[` экранируется одним
`\`, но в BSL-строке `\\` означает литеральный `\`. Поэтому в файле
должно быть `\[!TYPE`, что после парсинга BSL даст `\[` в regex (валидный
escape для символа `[`).

Первые попытки давали `\\[` (двойной backslash) или `(!` (без backslash) —
обе ломали regex (`U_REGEX_MISSING_CLOSE_BRACKET`). Финальный вариант
использует `\[` в regex-паттернах и просто `[` в replacement-строках
(replacement не требует regex-escapes).

## Обновление v2.32.4 (bugfix: вложенный `<p>` ломал стили заголовка)

После v2.32.3 пользователь прислал логи: `delta=89, changed=Да` — то есть
функция отработала, но визуально текст `[!NOTE|Залупа]` оставался как
plain-текст, а стили заголовка (полужирный, цвет) не применялись.

### Причина

Showdown оборачивает содержимое `<blockquote>` в `<p>...</p>`:
```html
<blockquote>
  <p>[!NOTE|Залупа]<br />
  Полезная подсказка.</p>
</blockquote>
```

В v2.32.3 `ОбработатьЗаголовокАлерта` заменял `[!NOTE|Залупа]` на
`<p class="markdown-alert-title">Залупа</p>`, но внешний `<p>` оставался:
```html
<div class="markdown-alert markdown-alert-note">
  <p><p class="markdown-alert-title">Залупа</p><br />
  Полезная подсказка.</p>
</div>
```

`<p>` нельзя вкладывать в `<p>` — HTML-парсер браузера выбрасывает
вложенный открывающий тег, из-за чего `.markdown-alert-title` оказывался
**вне** параграфа и не получал CSS-стилей (полужирный, цвет, иконка).

### Решение

В `ОбработатьЗаголовокАлерта` добавлен шаг снятия внешней `<p>`-обёртки
перед подстановкой `<p class="markdown-alert-title">…</p>`:

1. Найти первое `<p>` в содержимом, обрезать всё до него включительно.
2. Найти последнее `</p>`, обрезать всё начиная с него.
3. После trim пересчитать позицию маркера `[!TYPE` (смещение отличается).
4. Вставить `<p class="markdown-alert-title">…</p>` как отдельный блок.

Итоговый HTML:
```html
<div class="markdown-alert markdown-alert-note">
<p class="markdown-alert-title">Залупа</p>
<br />
  Полезная подсказка.
</div>
```

Внутренние `<p>...</p>` (если блок содержит несколько параграфов) сохраняются
— удаляются только самые внешние.

## Обновление v2.32.5 (bugfix: некоторые `[!TYPE]` оставались в `<blockquote>`)

После v2.32.4 пользователь прислал скриншот DevTools. В DOM-дереве видно,
что `<blockquote>` для блока `[!NOTE|Залупа]` остаётся не обработанным
(текст показан как plain, стили не применены), хотя логи показывают
`delta=89, changed=Да` и однотипные блоки `[!WARNING]`, `[!NOTE]`, `[!TIP]`
обрабатываются корректно.

### Причина

Старая `ЗаменитьОбёрткуНаDiv` работала в два прохода: для каждого типа
(WARNING, NOTE, TIP, ...) искала **первый** `<blockquote>`, проверяла,
есть ли в его содержимом `[!TYPE]`, и если нет — перескакивала на
следующий через `ПозКонца`. Алгоритм был уязвим к:

- **Невалидному HTML от showdown.** Showdown может сгенерировать
  `<blockquote>` между `</tr>` и `<tr>` (вне ячейки таблицы) — браузер
  вытягивает такой блок наружу `<table>` при рендеринге, а строковый
  обход всё равно находит его, но соседние `<blockquote>` внутри ячеек
  обрабатываются не в той последовательности, в которой их видит браузер.
- **Лишним `<blockquote>`** с упоминанием `[!TYPE]` в обычном тексте
  (например, `[!WARNING] — это тип алерта`). Прежний поиск захватывал
  такой блок вместо настоящего.

### Решение

Переписал `ЗаменитьОбёрткуНаDiv` так, чтобы искать **не по `<blockquote>`,
а по содержимому `<p>[!TYPE`** — это точная метка алерта в showdown-выводе
(showdown всегда оборачивает содержимое цитаты в `<p>`). Алгоритм:

1. Найти позицию `<p>[!TYPE` в HTML.
2. От этой позиции пройти **назад** до ближайшего открывающего тега:
   либо `<blockquote>`, либо `<div class="markdown-alert">` (для
   совместимости со старым JS-extension, который мог оставить голый div).
3. Пройти **вперёд** до соответствующего закрывающего тега
   (`</blockquote>` или `</div>`).
4. Извлечь содержимое, прогнать через `ОбработатьЗаголовокАлерта`,
   заменить блок на `<div class="markdown-alert markdown-alert-{type}">…</div>`.

Поиск назад ограничен 10000 символами — этого достаточно для разумного
HTML и спасает от случайного захвата родителя через всю страницу.

Функция `ДобавитьКлассКMarkdownAlert` оставлена как тонкая обёртка,
возвращающая текст без изменений: новая логика `ЗаменитьОбёрткуНаDiv`
умеет находить и `<div class="markdown-alert">`, так что отдельный
проход для div-обёрток больше не нужен.

## Обновление v2.32.6 (bugfix: замена `<blockquote>` ломала разметку)

После v2.32.5 пользователь сообщил: новые стили не применились,
подмена не сработала, старые стили сломались.

### Причина

В v2.32.5 `ЗаменитьОбёрткуНаDiv` искала содержимое `<p>[!TYPE]`, находила
родительский `<blockquote>` (или `<div class="markdown-alert">`) **назад**
по строке и **целиком заменяла** открывающий тег и всё содержимое на
новый `<div class="markdown-alert markdown-alert-{type}">…</div>`.

Проблема в том, что такая замена:

- вырезает `<blockquote>` из HTML, даже если блок находится внутри
  `<td>` или между `</tr>` и `<tr>` — браузер потом лепит результат
  как попало, и любые стили, привязанные к **позиции** `<blockquote>`
  относительно таблицы, ломаются;
- в случае с длинным HTML (3+ МБ) при поиске назад от позиции маркера
  внутри `</td></tr>` пропускается нужный блок или захватывается
  соседний — пользователь увидел, что один блок стилизован, а соседний
  с тем же `[!NOTE|Залупа]` — нет.

### Решение

Принят **минимально инвазивный** подход по предложению пользователя:

1. Найти `<p>[!TYPE…</p>` (точная метка алерта в showdown-выводе).
2. Найти **назад** родительский открывающий тег (`<blockquote>` или
   `<div class="markdown-alert">`).
3. **Не заменять тег** — только дописать к нему атрибут
   `class="markdown-alert markdown-alert-{type}"`. CSS-стили
   `.markdown-alert { … }` не привязаны к тегу и работают для любого
   элемента с этим классом, включая `<blockquote>`.
4. Прогнать содержимое `<p>[!TYPE…]</p>` через `ОбработатьЗаголовокАлерта`,
   чтобы получить готовый `<p class="markdown-alert-title">…</p>` без
   вложенности `<p><p>`.

Итоговый HTML (на примере `[!NOTE|Залупа]`):
```html
<blockquote class="markdown-alert markdown-alert-note">
  <p class="markdown-alert-title">Залупа</p>
  Полезная подсказка.
</blockquote>
```

`<blockquote>` остался как был — никаких сломанных границ таблицы,
никакого риска промахнуться с родителем: класс дописывается к тому
блоку, внутри которого лежит `<p>[!TYPE…]`.

не применяются, блок выглядит как обычный blockquote.

### Что сделано

`ЗаменитьОбёрткуНаDiv` переписана полностью. Теперь она **не ищет
родителя вообще**. Алгоритм:

1. Ищем `<p>[!TYPE</…` (точная метка алерта).
2. Находим границы `<p>` слева и `</p>` справа от метки.
3. Берём **содержимое** `<p>…</p>` без обрамляющих тегов.
4. Через `ЗаменитьМаркерНаЗаголовок` превращаем `[!TYPE]` /
   `[!TYPE|Заголовок]` в `<p class="markdown-alert-title">…</p>`.
   Внешний `<p>` уже снят шагом 3, поэтому вложенности `<p><p>` нет.
5. Оборачиваем полученное содержимое в
   `<div class="markdown-alert markdown-alert-{type}">…</div>` —
   **ровно на месте** исходного `<p>[!TYPE…]</p>`.

### Что получается в HTML

Было (showdown-вывод):
```html
<blockquote>
  <p>[!NOTE|Залупа]<br />Полезная подсказка.</p>
</blockquote>
```

Стало (после v2.32.7):
```html
<blockquote>
  <div class="markdown-alert markdown-alert-note">
    <p class="markdown-alert-title">Залупа</p>Полезная подсказка.
  </div>
</blockquote>
```

`<blockquote>` не трогается. Класс живёт на `<div>`, селектор
`.markdown-alert-note` срабатывает напрямую, CSS применяется
гарантированно.

### Почему это лучше прежнего

- Нет обратного поиска родителя — нечему промахнуться.
- Нет внешнего `<p>` после преобразования — нет `<p><p>`,
  который браузер не умеет рендерить.
- Не зависит от того, лежит ли блок внутри `<td>`, между строк
  таблицы или вне таблицы — `<div>` всегда найдётся по своим
  координатам в исходном HTML.

## v2.32.14 — передача ДвоичныеДанные в РезультатОбновленияПрисоединенногоФайла

### Корень бага

На v2.32.13 выставление `ЕстьИзмененияРедактирования = Истина`
заставило типовую `ЗаписатьНовыеОписанияСценариевИзФормыОбъекта`
войти в ветку обновления файла и **упасть** с ошибкой
`Некорректный тип хранилища файлов`. Ошибка **видна** — это прогресс
по сравнению с v2.32.12, где она проглатывалась в `Попытка ... Исключение`
и файл просто не обновлялся.

Из стека видно, что **внутри** типовой цепочки
`РезультатОбновленияПрисоединенногоФайла` →
`СохранитьИзмененияИОсвободитьФайл` →
`ОбновитьОбъектФайла` →
`ДвоичныеДанныеИзСведенийОФайле`
**мутируется** `СведенияОФайле.АдресВременногоХранилищаФайла`:
вместо адреса временного хранилища в поле оказывается HTML-строка
(`<h h...`). После этой мутации
`ЭтоАдресВременногоХранилища(HTML) = Ложь`, и функция выбрасывает
исключение.

Мутация происходит **внутри** типового `ОбновитьОбъектФайла` /
`СохранитьИзмененияИОсвободитьФайл` — это типовая конфигурация
(read-only), и я не могу её менять. Но могу **обойти** проблему,
передав в `РезультатОбновленияПрисоединенногоФайла` уже готовые
`ДвоичныеДанные` (а не строку). Тогда внутри типовой код:

```bsl
Если ТипЗнч(НовыеДанные) = Тип("Строка") Тогда
    НовыеДанные = ПолучитьДвоичныеДанныеИзСтроки(НовыеДанные);
КонецЕсли;
АдресВоВременномХранилище = ПоместитьВоВременноеХранилище(НовыеДанные, УникальныйИдентификатор);
```

получает `ДвоичныеДанные`, **пропускает** ветку `ПолучитьДвоичныеДанныеИзСтроки`,
и `ПоместитьВоВременноеХранилище(ДвоичныеДанные, УИД)` отрабатывает
с готовыми данными. Мутация в типовой функции по-прежнему происходит,
но `АдресВременногоХранилищаФайла` уже **не связан** с входной строкой,
по которому она, видимо, и сбоит.

### Что сделано

В `src/CommonModules/ГКСИ_MarkdownФормаСервер/Module.bsl`:

1. **Откатил** выставление `ЕстьИзмененияРедактирования = Истина`
   в backfill'е формы — теперь типовая процедура не входит в ветку
   обновления, обновление делаем только сами.

2. **В цикле по `HTMLПоЯзыкам`** перед записью файла преобразуем
   backfill'енный HTML в `ДвоичныеДанные` через `ПолучитьДвоичныеДанныеИзСтроки`
   и передаём их в `РезультатОбновленияПрисоединенногоФайла`
   (для обновления) или в `СоздатьПрисоединенныйФайлСценария` (для создания).

3. **`СоздатьПрисоединенныйФайлСценария`** теперь принимает параметр
   `ДанныеHTML` типа `Строка, ДвоичныеДанные`. Если переданы
   `ДвоичныеДанные` — backfill пропускается (считается, что вызывающий
   код его уже сделал) и данные кладутся во временное хранилище как
   есть. Если строка — старое поведение с backfill через
   `ОбработатьАлертыВHTML` и `ПолучитьДвоичныеДанныеИзСтроки`. Это
   сохраняет обратную совместимость для вызовов из `ФормаГруппы` и
   `РМ_СоздатьПрисоединенныйФайлСценария`, которые передают строку.

4. **Без** `Попытка ... Исключение` — если что-то пойдёт не так,
   ошибка видна пользователю.

Порядок записи:
1. `&Перед("ПередЗаписьюНаСервере")` →
   `СоздатьПрисоединенныеФайлыИзДопСвойств`:
   - Backfill `Форма.ОписанияСценария[*].ТекстHTML` (без флага).
   - В цикле по `HTMLПоЯзыкам`: backfill → `ДвоичныеДанные` →
     `РезультатОбновленияПрисоединенногоФайла` (для существующих)
     или `СоздатьПрисоединенныйФайлСценария` (для новых).
2. Типовая `ПередЗаписьюНаСервере` →
   `ЗаписатьНовыеОписанияСценариевИзФормыОбъекта`:
   - **Не** входит в ветку обновления (флаг = Ложь).

## v2.32.11 — backfill inline-стилей на уже обработанных блоках

### Что было сломано

После v2.32.10 в ЖР появились записи:

   ставится на `<div>` → `<p>` наследует), и для старых (style
   дописывается backfill-проходом → `<p>` тоже наследует).
3. **`ОбработатьАлертыВHTML`** теперь вызывает оба прохода:
   `ЗаменитьОбёрткуНаDiv` (новые маркеры) → `ДобавитьInlineСтилиКАлертам`

## v2.32.29 — фикс регрессии: рефакторинг `MarkdownВHTML` + алерты в один шаг

## v2.32.30 — фикс: пустые строки в Markdown не разрывали параграфы

### Симптом (сообщение пользователя после применения v2.32.29)

После публикации v2.32.29 пользователь прислал лог из журнала регистрации:

```
START len=69 960; byType=CAUTION=1,; firstBlockquote=
DONE lenBefore=69 960; lenAfter=69 960; delta=0; changed=Нет
```

и ещё ~15 таких же пар для других файлов: `byType=` пусто (т.к. в этих файлах нет `[!TYPE]`), но в **одном** файле блок `[!CAUTION]` найден (`byType=CAUTION=1`), при этом `delta=0; changed=Нет` — то есть подстрока `[!CAUTION` в HTML **есть**, но `ЗаменитьОбёрткуНаDiv` не нашла её и замена не сработала.

### Корневая причина

В `MarkdownВHTML` (строки 781-799 `ГКСИ_ЗагрузкаСценариевИзMarkdown.Module.bsl`) обработка параграфов делается так:

```bsl
МассивСтрок = СтрРазделить(Текст, Символы.ПС, Истина);   // ← проблема тут
...
Если ПустаяСтрока(Строка) Тогда
    // сброс буфера в <p>
    Продолжить;
КонецЕсли;
```

Третий параметр `СтрРазделить(..., Истина)` в BSL **схлопывает** последовательные `\n` в один разделитель. Поэтому пустые строки (`\n\n` в исходном markdown) **не попадают** в массив — между абзацами потерь не будет, но и новый `<p>` не образуется. Ветка `ПустаяСтрока` фактически **никогда не срабатывает**.

В итоге весь файл превращается в один большой `<p>`:

```html
<p>Текст до алерта.<br>[!CAUTION]<br>Текст алерта.<br>Текст после алерта.</p>
```

`ЗаменитьОбёрткуНаDiv` ищет **точное** начало параграфа: `<p>[!TYPE` (`СтрНайти(Результат, "<p>[!" + ИмяТипа)`). Между `<p>` и `[!CAUTION` теперь стоит `Текст до алерта.<br>`, поэтому `СтрНайти` возвращает 0 — функция ничего не заменяет. Счётчик `byType` при этом честно показывает `CAUTION=1` (он работает через `СтрЧислоВхождений(Текст, "[!CAUTION")`, без привязки к позиции), что и сбило с толку при первой диагностике.

### Решение

Локальная правка `MarkdownВHTML` в том же модуле — два изменения:

1. `СтрРазделить(Текст, Символы.ПС, Истина)` → `СтрРазделить(Текст, Символы.ПС, Ложь)`. С флагом `Ложь` пустые элементы массива **возвращаются**, и ветка `ПустаяСтрока(Строка)` корректно сбрасывает `Буфер` в `<p>...</p>`, открывая новый параграф.

2. Перед разделением удаляем `Символы.ВК` (`\r`) — страховка от CRLF: иначе строка из одного `\r` не была бы пустой и попадала бы в `Буфер` как обычный текст.

```bsl
Текст = СтрЗаменить(Текст, Символы.ВК, "");
МассивСтрок = СтрРазделить(Текст, Символы.ПС, Ложь);
```

После правки `MarkdownВHTML` для исходного markdown с пустыми строками выдаёт:

```html
<p>Текст до алерта.</p>
<p>[!CAUTION]<br>Текст алерта.</p>
<p>Текст после алерта.</p>
```

`<p>[!CAUTION` теперь находится в начале параграфа, `ЗаменитьОбёрткуНаDiv` отрабатывает, лог `delta=N; changed=Да`.

### Почему исправлять `MarkdownВHTML`, а не preprocessing в `MarkdownВHTMLСАлертами`

- `MarkdownВHTML` — единая точка конвертации markdown→HTML в проекте (подтверждено поиском по `src/`: единственный потребитель — `MarkdownВHTMLСАлертами`). Точечная правка чинит корневую проблему, а не её проявление.
- Preprocessing в обёртке (`</p><p>` перед `[!TYPE]`) лечил бы только симптом: порождал бы кривой HTML с лишними `</p>` в начале, и при любом будущем расширении логики (новые типы блоков, новые правила) пришлось бы снова думать, какие маркеры надо «вытаскивать» из общих `<p>`.
- Документация `MarkdownВHTML` теперь явно фиксирует, что пустая строка — это разрыв параграфа (это и есть стандартное поведение markdown, которое раньше нарушалось).

## v2.32.31 — фикс: `MarkdownВHTML` не получал пустых строк от парсера

### Симптом (сообщение пользователя после применения v2.32.30)

Пользователь прислал свежий лог ЖР после применения v2.32.30:

```
START len=69 956; byType=CAUTION=1,; firstBlockquote=
DONE lenBefore=69 956; lenAfter=69 956; delta=0; changed=Нет
...
START len=3 274 202; byType=CAUTION=1,; firstBlockquote=
DONE lenBefore=3 274 202; lenAfter=3 274 202; delta=0; changed=Нет
START len=70 006; byType=CAUTION=1,; firstBlockquote=
DONE lenBefore=70 006; lenAfter=70 006; delta=0; changed=Нет
```

Обратите внимание: длина HTML уменьшилась на 4 символа (`69 960 → 69 956`, `165 125 → 165 121` и т. д.) — это значит, что v2.32.30 применился (в `MarkdownВHTML` добавилась очистка `\r`). Но `byType=CAUTION=1; delta=0; changed=Нет` остался для тех же файлов. То есть фикс v2.32.30 помог частично (изменил сам HTML), но **не решил** исходную проблему.

### Корневая причина (дополнение к v2.32.30)

v2.32.30 сделал `MarkdownВHTML` корректным с точки зрения markdown-семантики: теперь пустые строки во входном тексте создают разрывы параграфов. Но это работает только если пустые строки **есть** во входных данных. А их там нет.

Парсер `РазобратьMarkdownВДерево` (тот же модуль `ГКСИ_ЗагрузкаСценариевИзMarkdown`, строки 138-143) собирает `ТекстMarkdown` построчно:

```bsl
Если ТекущийУзел.ТекстMarkdown = "" Тогда
    ТекущийУзел.ТекстMarkdown = ОбработаннаяСтрока;
Иначе
    ТекущийУзел.ТекстMarkdown = ТекущийУзел.ТекстMarkdown
        + Символы.ПС + ОбработаннаяСтрока;
КонецЕсли;
```

Строки соединяются через **одиночный** `\n`. Плюс на строке 67 парсер использует `СтрРазделить(ТекстФайла, Символы.ПС, Истина)`, который **схлопывает** пустые строки исходного файла. Итог: в `ТекстMarkdown`, который приходит в `MarkdownВHTMLСАлертами`, **никогда нет `\n\n`** между абзацами — только `\n`. Даже если в исходном `.md` между блоками был перевод строки, после парсера он исчезает.

Поэтому даже с фиксом v2.32.30 (`СтрРазделить(..., Ложь)` в `MarkdownВHTML`) весь файл уходит в один большой `<p>...<br>[!CAUTION]<br>...</p>`, и `ЗаменитьОбёрткуНаDiv` (`СтрНайти(<p>[!TYPE)`) ничего не находит. Уменьшение длины на 4 символа — побочный эффект от удаления `\r` в `MarkdownВHTML`: даже после парсера отдельные `\r` могут остаться (например, на стыках, или если в каких-то ветках парсера не было удаления — на этот случай лучше перестраховаться очисткой в конвертере).

### Решение

Добавляем preprocessing **в `MarkdownВHTMLСАлертами`** — принудительно вставляем `\n\n` перед каждым вхождением `[!TYPE]` (WARNING, NOTE, TIP, IMPORTANT, CAUTION) в исходном markdown. Это узкая локальная нормализация, которая **не** трогает обычный prose и работает только для блоков алертов:

```bsl
Функция MarkdownВHTMLСАлертами(ТекстMarkdown) Экспорт

    Возврат ГКСИ_MarkdownСерверВызовСервера.ОбработатьАлертыВHTML(
        MarkdownВHTML(ОбеспечитьРазрывПередМаркерамиАлертов(ТекстMarkdown)));

КонецФункции

Функция ОбеспечитьРазрывПередМаркерамиАлертов(Текст) Экспорт

    Если НЕ ЗначениеЗаполнено(Текст) Тогда
        Возврат Текст;
    КонецЕсли;

    Результат = Текст;

    // Порядок замен не важен — обрабатываем каждый тип независимо.
    Результат = СтрЗаменить(Результат, "[!WARNING]",   Символы.ПС + Символы.ПС + "[!WARNING]");
    Результат = СтрЗаменить(Результат, "[!NOTE]",      Символы.ПС + Символы.ПС + "[!NOTE]");
    Результат = СтрЗаменить(Результат, "[!TIP]",       Символы.ПС + Символы.ПС + "[!TIP]");
    Результат = СтрЗаменить(Результат, "[!IMPORTANT]", Символы.ПС + Символы.ПС + "[!IMPORTANT]");
    Результат = СтрЗаменить(Результат, "[!CAUTION]",   Символы.ПС + Символы.ПС + "[!CAUTION]");

    Возврат Результат;

КонецФункции
```

После preprocessing `[!CAUTION]` всегда стоит в начале нового параграфа — либо потому что в исходнике уже была пустая строка, либо потому что мы её добавили. Дальше `MarkdownВHTML` корректно отделяет `[!CAUTION]` в `<p>[!CAUTION]...</p>`, и `ЗаменитьОбёрткуНаDiv` находит `<p>[!CAUTION`.

### Почему preprocessing в обёртке, а не правка парсера

Альтернативы, которые я **не** выбрал:

1. **Менять `РазобратьMarkdownВДерево`, чтобы сохранять `\n\n` между абзацами.** Это правильнее с точки зрения семантики markdown, но рискованно: меняется поведение всей функции, любые будущие потребители `ТекстMarkdown` (и текущие — `MarkdownВHTML` и `MarkdownВHTMLСАлертами`) начнут получать текст другого формата. Может сломать неочевидные вещи.

2. **Расширить `ЗаменитьОбёрткуНаDiv` в `ОбработатьАлертыВHTML`, чтобы искать `[!TYPE` в любом месте HTML.** Это решило бы проблему «с другой стороны», но: (а) `ОбработатьАлертыВHTML` уже сейчас обрабатывает три разных формата алертов (showdown-output, готовый `<div>`, `<blockquote>`), и усложнять четвёртый вариант «в любом месте HTML» — это размывание контракта; (б) это изменение в общем модуле, используемом многими потребителями (форма элемента, форма группы, альбом процессов), а не только загрузкой из markdown.

3. **Менять `MarkdownВHTML` на умный сплиттер абзацев.** Слишком инвазивно — `MarkdownВHTML` и так на минимальном наборе правил, добавлять туда эвристику «искать `[!TYPE` в строках и считать их началом абзаца» — это смешение ответственности (конвертер vs обработчик алертов).

Выбранный вариант — preprocessing в `MarkdownВHTMLСАлертами` — локален, узок, идемпотентен (повторный прогон добавит ещё `\n\n`, но MarkdownВHTML трактует несколько пустых строк подряд как одну) и не трогает другие функции.

### Безопасность

Функция `ОбеспечитьРазрывПередМаркерамиАлертов` не различает `[!TYPE]` внутри других конструкций markdown (ссылок `[текст](url)`, блоков кода `` `...` ``, code fences ` ``` `). В текущих сценариях таких конструкций нет — алерты всегда идут отдельной строкой. Если в будущем такая коллизия появится, можно ограничить поиск позицией начала строки через `СтрНайти` + реверс-поиск ближайшего `\n`.

### Что сохраняется из v2.32.30

- `СтрРазделить(..., Ложь)` в `MarkdownВHTML` — оставляем. Это правильное поведение конвертера: пустая строка = разрыв параграфа, согласно стандарту CommonMark. Раньше `MarkdownВHTML` был упрощён до одного большого `<p>`, и любой потребитель, который когда-нибудь захочет передать туда текст с пустыми строками, получит корректное поведение «из коробки».
- Удаление `Символы.ВК` в `MarkdownВHTML` — оставляем. Страховка от CRLF.

То есть v2.32.31 — это **не откат** v2.32.30, а дополнение: «конвертер теперь правильный, но парсер не передаёт ему пустые строки — нормализуем на стыке».

1. Перезагрузить `.md`-файл, который раньше давал `byType=CAUTION=1; delta=0; changed=Нет` (тот самый, что прислал пользователь с длиной `69 956`). В ЖР теперь должно быть `byType=CAUTION=1; delta=N>0; changed=Да`.
2. Открыть загруженный элемент → форма элемента → вкладка «Просмотр» → блок `[!CAUTION]` стилизован.
3. Прогнать полный набор инструкций: файлы без `[!TYPE]` — поведение не меняется (`ОбработатьАлертыВHTML` остаётся no-op); файлы с заголовками `##/###` и картинками — `MarkdownВHTML` отрабатывает так же, как раньше (v2.32.30 уже исправил разбиение на параграфы).

## v2.32.32 — диагностическое логирование для `MarkdownВHTMLСАлертами`

### Симптом (сообщение пользователя после применения v2.32.31)

Пользователь прислал свежий лог ЖР после применения v2.32.31 (скриншот элемента «Открытие ведомости покупных» с тремя строками в редакторе: `[[!67701369-...]]`, `Зайти в 1С...`, `[!CAUTION]ЗАГЛУШКА`):

```
START len=69 956; byType=CAUTION=1,; firstBlockquote=
DONE lenBefore=69 956; lenAfter=69 956; delta=0; changed=Нет
```

Длина HTML **не изменилась** относительно v2.32.30 (`69 956` совпадает побайтово). Это значит, что моя preprocessing `ОбеспечитьРазрывПередМаркерамиАлертов` **не выполнилась** в этом запуске 1С. При этом скриншот показывает, что в редакторе сценария `[!CAUTION]ЗАГЛУШКА` идёт отдельной строкой (а не слитно с предыдущим текстом), а в просмотре — plain-текстом без стилей. То есть фикс логически должен работать, но он не применяется.

### Корневая причина (диагноз)

В 1С модули расширения компилируются при первом обращении в сеансе. Если сеанс был запущен **до** применения v2.32.31, то функция `MarkdownВHTMLСАлертами` будет работать по **старой** закэшированной версии (без вызова `ОбеспечитьРазрывПередМаркерамиАлертов`). Доказательство:

- В файле `src/CommonModules/ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl` (строки 867-872) `MarkdownВHTMLСАлертами` **точно** содержит `ОбеспечитьРазрывПередМаркерамиАлертов` в цепочке вызовов.
- Поиск `MarkdownВHTML(` по `src/` показывает единственного потребителя — `MarkdownВHTMLСАлертами`. Других путей генерации HTML нет (см. v2.32.31 раздел «Что сохраняется из v2.32.30»).
- `MarkdownВHTMLСАлертами` вызывается из двух мест `ОбработатьУзелРекурсивно` (строки 1062, 1141) — оба используют ту же функцию.
- `СоздатьПрисоединенныеHTMLФайлыПакетно` не генерирует HTML, а только записывает уже готовый из `МассивHTMLПоУзлам`.
- Если бы `ОбеспечитьРазрывПередМаркерамиАлертов` сработала на тексте с `[!CAUTION]`, длина увеличилась бы минимум на 2 символа (`\n\n`). Длина осталась **точно** такой же, как после v2.32.30 — preprocessing не выполнилась.

### Решение

В `MarkdownВHTMLСАлертами` добавлено **диагностическое логирование** на событие `ГКСИ.MarkdownServer.Alerts.Preprocess`. Каждый вызов функции пишет в ЖР:

```
PREPROC hit={количество [!TYPE] во входном тексте};
lenBefore={длина до preprocessing};
lenAfter={длина после preprocessing};
delta={lenAfter - lenBefore}
```

Это позволяет при следующей загрузке **сразу** отличить две ситуации:

1. **В ЖР нет записей `PREPROC`** → 1С использует старую закэшированную версию модуля. Нужно **перезапустить сеанс 1С** (закрыть приложение и открыть заново), чтобы модуль расширения перекомпилировался с новой версией.

2. **В ЖР есть `PREPROC hit=N; delta=0`** → preprocessing сработала, но `[!TYPE]` не найдены во входных данных. Значит, проблема в другом месте — например, в исходном файле markdown нет `[!TYPE]`, или в `MarkdownВHTML`/`ОбработатьАлертыВHTML`.

3. **В ЖР есть `PREPROC hit=N; delta=M>0`** → preprocessing сработала корректно, добавила `\n\n`. Если при этом в основном логе `byType` всё ещё показывает проблему — баг в `MarkdownВHTML` или `ЗаменитьОбёрткуНаDiv`, а не в preprocessing.

Также логирование помогает отслеживать **сколько именно `\n\n`** добавляется в каждом конкретном файле, чтобы при будущих изменениях видеть эффект.

### Почему логирование, а не «просто перезапустить»

Перезапуск 1С — правильный шаг, но без подтверждения в ЖР он ничего не доказывает: если после перезапуска проблема останется (например, из-за другого бага в коде), будет непонятно, в чём дело. С логированием видно точный путь выполнения.

### Изменённые файлы

- `src/CommonModules/ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl` — в `MarkdownВHTMLСАлертами` добавлен блок логирования перед цепочкой вызовов. Функция `ОбеспечитьРазрывПередМаркерамиАлертов` не тронута.
- `src/Configuration/Configuration.mdo` — версия 2.32.31 → 2.32.32 (patch).

### Что проверить после обновления конфигурации БД

1. **Обязательно перезапустить сеанс 1С** (закрыть и открыть приложение). Без перезапуска модуль `MarkdownВHTMLСАлертами` продолжит работать по старой версии из кэша.
2. Перезагрузить `.md`-файл с блоками `[!CAUTION]` через `ГКСИ_ЗагрузкаСценариевИзMarkdown`.
3. Проверить ЖР по событию `ГКСИ.MarkdownServer.Alerts.Preprocess`:
   - Должна появиться запись `PREPROC hit=N; lenBefore=X; lenAfter=Y; delta=Z`, где `N > 0` для файлов с `[!TYPE]`, `Z > 0` для файлов, где preprocessing вставила `\n\n`.
   - Если записи нет — значит, кэш всё ещё держит старую версию. Перезапустить сеанс принудительно.
4. Проверить основной лог (`ГКСИ.MarkdownServer.Alerts.ServerPreprocess`):
   - Должно быть `byType=CAUTION=1; delta > 0; changed=Да` для файлов, где раньше было `delta=0`.
5. Открыть загруженный элемент → форма → вкладка «Просмотр» → блок `[!CAUTION]` стилизован.

## v2.32.33 — корневой фикс: нормализация HTML в `ОбработатьАлертыВHTML`

### Симптом (сообщение пользователя после применения v2.32.32)

Пользователь прислал лог с записями `PREPROC` и скриншот элемента «Открытие ведомости покупных». Ключевое из лога:

```
PREPROC hit=0; lenBefore=155; lenAfter=155; delta=0
START len=69 956; byType=CAUTION=1,; firstBlockquote=
DONE lenBefore=69 956; lenAfter=69 956; delta=0; changed=Нет
```

`PREPROC hit=0` при `lenBefore=155` и `START len=69 956` — **это разные сценарии**. 155 символов — это markdown другого узла, где `[!TYPE]` действительно нет. А 69 956 символов — HTML другого сценария, который **не проходил** через `MarkdownВHTMLСАлертами`. То есть диагностика сработала и показала: preprocessing работает, но **не на том пути**.

### Корневая причина

HTML в присоединённые файлы попадает **тремя независимыми путями**, и `MarkdownВHTMLСАлертами` (в `ГКСИ_ЗагрузкаСценариевИзMarkdown`) — только один из них:

1. **Загрузка из markdown-файла** → `ГКСИ_ЗагрузкаСценариевИзMarkdown.ОбработатьУзелРекурсивно` → `MarkdownВHTMLСАлертами` → `МассивHTMLПоУзлам` → `СоздатьПрисоединенныеHTMLФайлыПакетно`. ✅ Здесь preprocessing из v2.32.31 работает.

2. **Форма элемента/группы** (то, что на скриншоте) → клиент `ГКСИ_MarkdownФормаКлиент.ЗаписатьHTMLИзMarkdown` генерирует HTML через `showdown.js` (подсистема `ГКСИ_РМ_РедакторMarkdown`) и кладёт в `ПараметрыЗаписи["ГКСИ_АдресHTMLПоЯзыкам"]` → сервер `ГКСИ_MarkdownФормаСервер.СоздатьПрисоединенныеФайлыИзДопСвойств` / `ObjectModule.ГКСИ_СоздатьПрисоединенныеФайлыИзДопСвойств:115` → **прямой вызов** `ГКСИ_MarkdownСерверВызовСервера.ОбработатьАлертыВHTML`. ❌ Здесь preprocessing отсутствовал.

3. **Альбом процессов** → `ГКСИ_АльбомПроцессов.ГКСИ_СобратьДокумент:1296` → **прямой вызов** `ОбработатьАлертыВHTML`. ❌ Здесь preprocessing отсутствовал.

`showdown.js` (путь 2) распознаёт GitHub Alerts **только с префиксом `>`** (см. регулярку в отчёте v2.32.1: `(?:[ ]{0,3}>[ ]?)+\...`). Если пользователь пишет `[!CAUTION]ЗАГЛУШКА` без `>`, showdown оставляет это как обычный текст, и весь блок оказывается в общем `<p>` после `<br>`. Дальше `ОбработатьАлертыВHTML` ищет `<p>[!CAUTION` и не находит.

### Решение

Нормализация перенесена **в саму `ОбработатьАлертыВHTML`** (общий модуль `ГКСИ_MarkdownСерверВызовСервера`) — тогда **все три пути** получают её автоматически, без правок в каждом вызывающем месте.

Добавлена служебная функция `ОбеспечитьНачалоПараграфаДляМаркеровАлертов(Текст)`, которая перед основной обработкой проходит по HTML и для каждого `[!WARNING]/[!NOTE]/[!TIP]/[!IMPORTANT]/[!CAUTION]` проверяет, стоит ли он в начале `<p>`:

- Если перед маркером уже `<p>` — ничего не делает (идемпотентность).
- Если маркер в середине `<p>` (после `<br>`) — вставляет `</p><p>` перед ним, разрывая текущий параграф.
- Если маркер в самом начале HTML — добавляет `<p>` в начало.

После этого `ЗаменитьОбёрткуНаDiv` гарантированно находит `<p>[!TYPE` и корректно оборачивает блок в `<div class="markdown-alert markdown-alert-{type}">`.

Вызов вставлен в `ОбработатьАлертыВHTML` между логированием `START` и пунктом «1. Showdown-вывод» — то есть preprocessing применяется **до** всех замен, и `delta` в `DONE` учитывает её эффект.

### Что сохраняется из v2.32.31

`ОбеспечитьРазрывПередМаркерамиАлертов` в `MarkdownВHTMLСАлертами` **оставлен**. Он нормализует markdown на входе конвертера — это более «чистый» путь (правильные `<p>` сразу, без вставки `</p><p>` в середину). HTML-нормализация в `ОбработатьАлертыВHTML` — это защита для путей, которые идут мимо `MarkdownВHTMLСАлертами`. Обе функции идемпотентны и дополняют друг друга.

### Изменённые файлы

- `src/CommonModules/ГКСИ_MarkdownСерверВызовСервера/Module.bsl`:
  - в `ОбработатьАлертыВHTML` добавлен вызов `Текст = ОбеспечитьНачалоПараграфаДляМаркеровАлертов(Текст);` (перед пунктом «1. Showdown-вывод»);
  - добавлена служебная функция `ОбеспечитьНачалоПараграфаДляМаркеровАлертов` с документирующим комментарием.
- `src/Configuration/Configuration.mdo` — версия 2.32.32 → 2.32.33 (patch).

### Что проверить после обновления конфигурации БД

1. **Перезапустить сеанс 1С** (изменён общий модуль `ГКСИ_MarkdownСерверВызовСервера` — без перезапуска будет старая версия из кэша).
2. Открыть элемент «Открытие ведомости покупных» (со скриншота) → вкладка «Просмотр»: блок `[!CAUTION]` должен быть стилизован (фон, левая граница, заголовок CAUTION).
3. Проверить ЖР (`ГКСИ.MarkdownServer.Alerts.ServerPreprocess`): для этого сценария должно стать `delta > 0; changed=Да` (preprocessing вставит `</p><p>`, затем `ЗаменитьОбёрткуНаDiv` заменит блок).
4. Перезагрузить markdown-файл через `ГКСИ_ЗагрузкаСценариевИзMarkdown` — путь 1 не должен сломаться (там preprocessing идемпотентен).
5. Открыть «Альбом процессов» для группы с алертами — блоки тоже должны быть стилизованы (путь 3).
