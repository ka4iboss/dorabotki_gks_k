# ОТЧЁТ: обход ошибки «Некорректный тип хранилища» при обновлении HTML-присоединённого файла

## Суть бага

Типовая функция `РезультатОбновленияПрисоединенногоФайла` (из
`РаботаСФайламиСлужебный`) при попытке обновить уже существующий присоединённый
HTML-файл сценария падает с исключением **«Некорректный тип хранилища файлов»**.

Причина (видна по обвязке):

1. Перед обновлением `СведенияОФайла.АдресВременногоХранилищаФайла`
   содержит валидный URL временного хранилища с бинарным пакетом.
2. После сохранения файла на диск внутри типовой функции эта переменная
   мутирует: вместо адреса хранилища туда попадает уже распакованный HTML-текст.
3. Последующий вызов `ДвоичныеДанныеИзСведенийОФайле` пытается читать
   «хранилище» по этому URL и падает — там уже не двоичные данные,
   а строка HTML.

## Решение

Отказались от штатной функции обновления в пользу паттерна
**«создать новый + удалить старый»**:

- На каждый цикл перезаписи HTML сценария создаём новый присоединённый файл
  через `РаботаСФайлами.ДобавитьПрисоединенныйФайл` (этот путь проверен
  ранее и работает корректно как для `ДвоичныеДанные`, так и для строки).
- Старый файл помечаем на удаление и удаляем вместе с версией.

Это безопасно, потому что присоединённые HTML-файлы сценариев — чисто
служебная сущность, без бизнес-смысла; пересоздание идентично обновлению
с точки зрения пользователя.

## Правки

- `src/CommonModules/ГКСИ_MarkdownФормаСервер/Module.bsl` —
  `СоздатьПрисоединенныеФайлыИзДопСвойств`:
  - в ветке `ЕстьПрисоединенныйФайл` больше не вызывается
    `РезультатОбновленияПрисоединенногоФайла`;
  - вместо этого файл помечается на удаление, новый HTML записывается
    поверх, ссылка на новый файл сохраняется в реквизите строки ТЧ.

## Заодно убраны замечания статического анализатора EDT

- `SU59` (`Пропущено определение параметра для: ДанныеHTML`) — имя
  параметра в документирующем комментарии приведено в соответствие
  с реальным именем параметра функции `СоздатьПрисоединенныйФайлСценария`
  (был рассинхрон: в комментарии `ДвоичныеДанные`, в коде `ДанныеHTML`).
- `SU39` (em-dash в документирующем комментарии) — два em-dash заменены
  на дефис-минус.

После правок `GetMarkers` для модуля возвращает 0 замечаний.

## Дополнение: «Поле объекта не обнаружено (ПрисоединенныйФайл)»

При первой прогонке на форме элемента справочника `ДемонстрационныеСценарии`
всплыла вторая ошибка:

```
Поле объекта не обнаружено (ПрисоединенныйФайл)
{ГКС_Инструкции ОбщийМодуль.ГКСИ_MarkdownФормаСервер.Модуль(101)}
```

### Причина

В `СоздатьПрисоединенныеФайлыИзДопСвойств` цикл шёл по
`Форма.ОписанияСценария` (это ТЧ формы) и пытался читать
`ОписаниеСценария.ПрисоединенныйФайл`. Но такой колонки в ТЧ формы нет —
она есть только в ТЧ объекта (`Форма.Объект.ОписанияСценария` и,
соответственно, в `ТекущийОбъект.ОписанияСценария`).

Типовая функция `ДемонстрационныеСценарииКлиентСервер.ПрисоединенныйФайлСценария(Форма, КодЯзыка)`
(см. `CommonModules/ДемонстрационныеСценарииКлиентСервер/Module.bsl`, стр. 220)
работает именно так: лезет в `Форма.Объект.ОписанияСценария.НайтиСтроки(...)`
и достаёт `ПрисоединенныйФайл` уже оттуда.

### Правка

- Ссылку на существующий присоединённый файл получаем через
  `ДемонстрационныеСценарииКлиентСервер.ПрисоединенныйФайлСценария(Форма, КодЯзыка)`.
- Результат кладём в локальную переменную `ПрисоединенныйФайл` и
  дальше работаем с ней.
- После создания нового файла ищу строку с тем же `КодЯзыка` в
  `ТекущийОбъект.ОписанияСценария` (это объект, который будет записан
  в БД) и обновляю там `ПрисоединенныйФайл`. Если строка по какой-то
  причине ещё не синхронизирована с формой — добавляю новую
  (по аналогии с типовой `ЗаписатьНовыеОписанияСценариевИзФормыОбъекта`).

## Дополнение: «файл становится пустым после перезаписи»

После успешного закрытия ошибки «Некорректный тип хранилища» на рабочей
базе всплыл второй симптом: после сохранения сценария присоединённый
HTML-файл существует, но при открытии оказывается пустым (или не
находится по сохранённой ссылке).

### Что пробовали

Сначала была гипотеза, что проблема в типовой
`РезультатОбновленияПрисоединенногоФайла`. Её обошли через паттерн
«создать новый + удалить старый» (см. разделы выше). Но на свежей
прогонке выяснилось, что проблема остаётся и после обхода — то есть
она в **другом** месте.

### Три рабочие гипотезы

1. **Рассинхрон `ТекущийОбъект.ОписанияСценария` ↔ `Форма.Объект.ОписанияСценария`.**
   Запись в БД идёт по `Форма.Объект`, а мы обновляем ссылку только в
   `ТекущийОбъект`. Если это два разных объекта в памяти — в БД
   попадает **старая** ссылка на **уже удалённый** нами файл.
2. **Откат транзакции.** Где-то в базовой цепочке
   (`ЗаписатьНовыеОписанияСценариевИзФормыОбъекта` или дальше) ставится
   `Отказ = Истина`, транзакция откатывается, наш новый файл исчезает
   вместе с удалением старого.
3. **Пост-обработка файла.** Подписка/обработчик на сам справочник
   присоединённых файлов очищает или перезаписывает наш файл.

Однозначно подтвердить одну из гипотез вслепую (по коду) нельзя —
нужны данные живой базы.

### Диагностический блок v2.32.16

Чтобы локализовать проблему, в `СоздатьПрисоединенныеФайлыИзДопСвойств`
добавлены три точки записи в журнал регистрации (события
`ГКС_Инструкции.Диагностика.*`):

| # | Событие | Что пишется |
|---|---------|-------------|
| 1 | `Шаг1_ДоСозданияНовогоФайла` | старая ссылка `ПрисоединенныйФайл`, длина HTML |
| 2 | `Шаг1_ПослеСозданияНовогоФайла` | новая ссылка `НоваяСсылкаФайла`, размер двоичных данных |
| 3 | `Шаг1_ПослеОбновленияСсылкиВОбъекте` | что в `ТекущийОбъект.ОписанияСценария[КодЯзыка].ПрисоединенныйФайл`, что в `Форма.Объект.ОписанияСценария[КодЯзыка].ПрисоединенныйФайл`, результат сравнения `ТекущийОбъект = Форма.Объект` |

И четвёртая точка в новой экспортной процедуре
`ДиагностикаПрисоединенногоФайлаПослеЗаписи` (вызывается из
`&После("ПослеЗаписиНаСервере")` в `ФормаЭлемента/Module.bsl`):

| # | Событие | Что пишется |
|---|---------|-------------|
| 4 | `ПослеЗаписи_СостояниеВБД` | запрос в БД: `КодЯзыка`, `ПрисоединенныйФайл` для каждой строки ТЧ; сравнение с `Форма.Объект.ОписанияСценария`; `ОбщегоНазначения.СсылкаСуществует` по ссылке из БД |

### Как снять диагностику

1. Открыть сценарий, отредактировать HTML, нажать «Записать».
2. В конфигураторе: **Администрирование → Журнал регистрации**.
   Отфильтровать по событию `ГКС_Инструкции.Диагностика`.
3. Сопоставить значения по точкам 1–4.

### Что ожидать по гипотезам

- **Гипотеза 1 подтверждается**, если в точке 3 `В_ТекущийОбъект ≠ В_Форма_Объект`,
  а в точке 4 в БД лежит `В_Форма_Объект`. Решение: переписать Шаг 1
  на обновление `ФайлХранилище` существующего файла (через
  `РаботаСФайламиСлужебныйВызовСервера.ЗаписатьФайлВИнформационнуюБазу`
  для базы + том-запись для тома) — без `Удалить()` и без
  переприсвоения ссылки.
- **Гипотеза 2 подтверждается**, если в точке 4
  `ФайлСуществует = Ложь` (наш новый файл исчез), но
  `Отказ` нигде не выставлялся — нужно смотреть базовую процедуру.
- **Гипотеза 3 подтверждается**, если в точке 4 `ФайлСуществует = Истина`
  и ссылка в БД правильная, но содержимое «пустое» — искать подписку
  на сам справочник `ДемонстрационныеСценарииПрисоединенныеФайлы`.

После локализации причины диагностический блок удаляется одним заходом
(4 вызова `ЗаписьЖурналаРегистрации` в `ГКСИ_MarkdownФормаСервер.Module.bsl`
+ 1 вызов из формы `ФормаЭлемента/Module.bsl` + новая экспортная
процедура `ДиагностикаПрисоединенногоФайлаПослеЗаписи`).

## Дополнение v2.32.17: результаты диагностики и финальное решение

### Результаты диагностики (v2.32.16)

Два прогона на рабочей базе подтвердили:

1. `ТекущийОбъект <> Форма.Объект` — две разные сущности в памяти.
   Сравнение в коде даёт `ТекущийОбъект = Форма.Объект: Нет`.
2. **Прогон #1:** обновили `ТекущийОбъект.ОписанияСценария[ru] = c174c13f`
   (наша новая), но в БД попало `c174c06b` (старая, из `Форма.Объект`).
   **Обновление потерялось при записи.**
3. **Прогон #2:** обновили `ТекущийОбъект.ОписанияСценария[ru] = c174c197`
   (наша новая), и в БД попало `c174c197`. **Сработало.**
4. В обоих прогонах `Форма.Объект.ОписанияСценария[ru]` на момент
   записи содержала **старую** ссылку (`c174c06b`).
5. После записи `Форма.Объект` перечитывается платформой из БД
   (точка 4 показывает совпадение `В_БД` и `В_Форме`).

### Вывод

Запись элемента справочника идёт по `Форма.Объект`, а не по
`ТекущийОбъект`. Когда обновление ссылки в `Форма.Объект` запаздывает /
теряется (прогон #1), в БД попадает старая ссылка, а свежесозданный
файл остаётся «осиротевшим».

Паттерн «создать новый + удалить старый + обновить ссылку в
`ТекущийОбъект`» нестабилен: его работоспособность зависит от того,
синхронизирует ли платформа `ТекущийОбъект` → `Форма.Объект` перед
записью в каждом конкретном случае.

### Финальное решение

Перешли на самый надёжный путь — **обновлять содержимое существующего
присоединённого файла без пересоздания ссылки**:

- Для `ТипХраненияФайла = ВИнформационнойБазе`:
  - `ПрисоединенныйФайл.ПолучитьОбъект()`.
  - `ФайлОбъект.ФайлХранилище = Новый ХранилищеЗначения(ДвоичныеДанныеHTML, Новый СжатиеДанных(9))`.
  - `ФайлОбъект.Размер = ДвоичныеДанныеHTML.Размер()`.
  - `ФайлОбъект.Записать()`.

В новой вспомогательной процедуре
`ГКСИ_MarkdownФормаСервер.ОбновитьФайлХранилищеСценария` (экспортная).

### Преимущества нового подхода

- **Исключён рассинхрон** `ТекущийОбъект` ↔ `Форма.Объект` — мы
  вообще не пишем в `ТекущийОбъект.ОписанияСценария`, ссылка
  `ПрисоединенныйФайл` остаётся прежней.
- **Исключена мутация** `АдресВременногоХранилищаФайла` — идём мимо
  `СохранитьИзмененияИОсвободитьФайл`.
- **Исключены «осиротевшие» файлы** — старый файл не удаляется,
  новый не создаётся, в БД остаётся ровно одна запись
  с тем же `ПрисоединенныйФайл`.

### Правки

- `src/CommonModules/ГКСИ_MarkdownФормаСервер/Module.bsl`:
  - в ветке `ЕстьПрисоединенныйФайл` теперь вызывается
    `ОбновитьФайлХранилищеСценария(ПрисоединенныйФайл, ОписаниеСценария.ТекстHTML)`
    вместо «создать новый + удалить старый»;
  - добавлена экспортная процедура
    `ОбновитьФайлХранилищеСценария(ПрисоединенныйФайл, ДанныеHTML)`;
  - удалены 3 точки `ЗаписьЖурналаРегистрации`
    (`Шаг1_ДоСозданияНовогоФайла`, `Шаг1_ПослеСозданияНовогоФайла`,
    `Шаг1_ПослеОбновленияСсылкиВОбъекте`) — диагностика выполнила
