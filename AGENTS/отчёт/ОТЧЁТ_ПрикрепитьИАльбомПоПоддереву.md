### 6. Исправление ошибки «Неправильный путь к файлу» (bugfix 1.92)

При первой реализации `Поддерево` помещалось во ВХ с УИДом формы списка на стороне клиента, а форма альбома читала его через `ПолучитьИзВременногоХранилища(ПоддеревоАльбомаАдрес)` без указания УИД. Это вызывало ошибку:

```
Ошибка при вызове метода контекста (ПолучитьИзВременногоХранилища)
{…АльбомПроцессов.Форма(54)}: Поддерево = ПолучитьИзВременногоХранилища(ПоддеревоАльбомаАдрес);
по причине:
Неправильный путь к файлу 'e1cib/tempstorage/cfcad6d4-d576-4c89-98ae-fb9c2de4'
```

**Корень:** `ПолучитьИзВременногоХранилища(<Адрес>)` без второго параметра читает ВХ с привязкой к УИД **текущей формы** (формы альбома). Но ВХ был создан с УИД формы списка — несовпадение.

**Исправлено:** форма списка теперь передаёт `Поддерево` (массив структур) через `ПараметрыФормы.Поддерево` напрямую — `ПараметрыФормы` сериализуются платформой без ВХ. Форма альбома в `ГКСИ_ПриСозданииНаСервере` сохраняет `Параметры.Поддерево` в новое ВХ с УИД **текущей формы** (формы альбома), и `ГКСИ_СобратьАльбомНаСервере` читает это ВХ без УИД — УИД текущей формы совпадает с УИДом формы альбома, чтение валидно.

### 7. Bugfix 1.93 — реальная фильтрация по поддереву

**Симптом (из отзыва пользователя):** в альбоме по поддереву отображается «дохера всего» — больше, чем выделено в форме списка.

**Корень проблемы:** в первой реализации версии 1.9 функция `СобратьДокументАльбомаПоПоддереву` использовала поддерево только для извлечения **корневых групп** (тех, у которых `РодительскаяГруппа = Пустая`). Дальше она делегировала эти корни в `СобратьДокументАльбомаПоГруппам`, которая через `ГКСИ_СобратьВсеУзлыДерева` обходила РС `ГКСИ_ГруппыСценариев` для каждого корня заново и тянула **всех** его потомков из БД, игнорируя поддерево.

Сценарии, на которых это проявлялось:
- выделена корневая группа инструкции (001 или 018) — случайно совпадало с тем, что нужно;
- выделена подгруппа (например, 001.002 «Выбор проекта» при незагруженных соседях) — `КорневыеГруппы` содержала саму подгруппу, но обход РС тянул ВСЁ под ней;
- прикреплённые через «Прикрепить» узлы из чужой инструкции — попадали в общий обход и портили альбом.

**Исправление** в `CommonModules/ГКСИ_АльбомПроцессов/Module.bsl`:

1. `ГКСИ_СобратьВсеУзлыДерева(КорневыеГруппы, УзлыГотовые = Неопределено)` — если передан `УзлыГотовые`, возвращает его без обхода РС.
2. `СобратьДокументАльбомаПоГруппам(ГруппыДляАльбома, ШиринаКартинок, МаксимальнаяШиринаПикселей, УзлыИзПоддерева = Неопределено)` — новый необязательный параметр. Если передан, `ВсеУзлы = УзлыИзПоддерева` (без обхода РС) **и** фильтр по `КореньИнструкции` (`ГКСИ_ОтфильтроватьУзлыПоИнструкции`) не вызывается.
3. `СобратьДокументАльбомаПоПоддереву(Поддерево, …)` — собирает из поддерева **плоский массив всех узлов** (и группы, и сценарии) и список корневых групп. Передаёт их в `СобратьДокументАльбомаПоГруппам(КорневыеГруппы, ШиринаКартинок, МаксимальнаяШиринаПикселей, ВсеУзлы)`.

**Эффект:** альбом строится **строго по узлам, переданным из формы списка**. Если пользователь выделил группу 001.002 и её содержимое — в HTML попадёт ровно это. Обход РС не выполняется, фильтр по `КореньИнструкции` не применяется (иначе узлы из «Прикрепить» с другим корнем выпали бы). Обратная совместимость сохранена: `СобратьДокументАльбомаПоГруппам(Группы)` без нового параметра работает по-старому.

**Известное ограничение (сохраняется):** иерархия внутри поддерева строится через `ЧленствоПоГруппам` (заполняется из РС для переданных узлов). Если в РС у выделенной группы есть дочерние узлы, которых нет в поддереве, они **не попадут** в альбом — потому что их нет в `ВсеУзлы`. Это правильное поведение для поддерева.

## 8. Bugfix 1.94: `КореньИнструкции` пустой в РС

**Проблема (выявлена пользователем):** после двух загрузок (ДМТО → ГИП с действием «Прикрепить» по всем строкам) колонка `КореньИнструкции` в `ГКСИ_ГруппыСценариев` оказалась **полностью пустой** для всех записей, в том числе у детей корневых `#`-заголовков.

**Причина:** в `ОбработатьУзелРекурсивно` (`ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl`) в вызов `ГКСИ_ГруппыСценариевСервер.ДобавитьСценарийВГруппу(Сценарий, Группа, ИнструкцияИсточник)` передавался параметр **текущего** вызова `ИнструкцияИсточник`. Расчёт `ИнструкцияИсточникДляДетей` (правильный корень для всех дочерних узлов) выполнялся **после** `ДобавитьСценарийВГруппу`. В итоге для первого уровня вложенности под `#`-заголовком `КореньИнструкции` уходил пустой/неверный. Если форма загрузки не передавала `ГКСИ_ИнструкцияИсточник` явно, пустой корень доставался и более глубоким уровням.

**Исправление в коде загрузки:** расчёт `ИнструкцияИсточникДляДетей` перенесён **перед** `ДобавитьСценарийВГруппу`. Используется именно `ИнструкцияИсточникДляДетей` (а не `ИнструкцияИсточник`). Логика:
- если форма передала `ГКСИ_ИнструкцияИсточник` — для всех уровней `ИнструкцияИсточникДляДетей = ИнструкцияИсточник` (явный приоритет оператора);
- если форма не передала и `Узел.Уровень = 2` (`#`-заголовок) — `ИнструкцияИсточникДляДетей = СсылкаНаУзел` (сам `#`-заголовок становится инструкцией для детей);
- иначе — наследование от родителя.

**Исправление для существующих данных:** добавлена `ГКСИ_ДозаполнитьКореньИнструкции` (Экспорт). Она:
1. Выбирает все записи РС с пустым `КореньИнструкции`.
2. Для каждой через `ГКСИ_СобратьКорневыеИнструкцииУзла` поднимается по графу РС до корневой группы (той, у которой нет родителя).
3. Если у узла **ровно одна** корневая инструкция — записывает её в `КореньИнструкции`.
4. Если узел общий (несколько корней) — оставляет `КореньИнструкции` пустым (признак общего узла).
5. Если узел сам корневой — оставляет пустым.
6. В конце вызывает `ГКСИ_ПересчитатьВсеКодыВРегистре`, чтобы `ПолныйКодКонтекстный` и `КодВКонтексте` получили правильный префикс системного кода корня.

Вспомогательная функция `ГКСИ_ПолучитьКореньУзлаСКешем` (в служебной секции) использует кеш, чтобы не обходить граф заново для каждого ребёнка одной и той же ветки.

**Как применить на существующих данных:** из EDT/предприятия вызвать `ГКСИ_ГруппыСценариевСервер.ГКСИ_ДозаполнитьКореньИнструкции()` (можно через внешнюю обработку с одной строкой кода или через `Выполнить` в консоли кода). После — обновить форму списка сценариев (Ctrl+F5 или перезайти), чтобы форма перечитала граф.

## 10. Bugfix 1.96: переделка построителя дерева формы списка

**Проблема (выявлена пользователем):** в форме `ФормаСпискаДеревоГрупп` дерево строится по всем записям РС `ГКСИ_ГруппыСценариев` без фильтрации по корню инструкции. В итоге в ветке `«Инструкция ДМТО, 001»` оказывались узлы из ветки `«Инструкция ГИП, 018»` (например, «Выбор проекта» с кодом 018.002, «Согласование ТКП» с кодом 018.003 — свёрнутая и без детей). Контекстные коды в форме не совпадали с теми, что записаны в РС, и иерархия «родитель — ребёнок» в дереве не соответствовала иерархии кодов в регистре.

**Причина:** построитель дерева (`ГКСИ_ПостроитьДерево` + `ГКСИ_ДобавитьВеткуГруппы`) опирался на связи `(Сценарий, Группа)` из регистра как на первичную иерархию и рекурсивно собирал членов группы через `ЧленыГрупп[Группа]`. Это примешивало в ветку ДМТО все группы, у которых в регистре была хоть какая-то запись `(Сценарий, Группа=«Инструкция ДМТО, 001»)`, **включая** записи с другим `КореньИнструкции` (т.е. ГИП-контекст).

Кроме того, рекурсивный обход требовал сложного кеша `КешКорневыхИнструкций` с подъёмом по графу до самого верхнего предка (функция `ГКСИ_ПолучитьКорневуюИнструкциюГруппы`). Логика была нестабильной на общих узлах.

**Принцип нового подхода:** отказались от связей `(Сценарий, Группа)` как первичной иерархии. Теперь иерархия строится **только по кодам** из регистра.

Формат `КодВКонтексте` уже содержит всю нужную информацию:
- `<КодКорня>.<ЛокальныйКод>` (например, `001.002.001`),
- `КодКорня` = системный код корневой `#-группы инструкции`,
- `ЛокальныйКод` = позиция узла в поддереве инструкции.

Родитель определяется просто: `КодВКонтексте` родителя = `КодВКонтексте` без последней секции после последней точки.
- `«001.002.001»` → родитель `«001.002»`
- `«001.002»` → родитель `«001»`
- `«001»` → нет родителя (это сама корневая `#-группа`).

Корни дерева — записи с `КодВКонтексте` без точек, т.е. сами корневые `#-группы` инструкций.

**Алгоритм `ГКСИ_ПостроитьДерево`:**
1. Один пакетный запрос: все записи РС с непустым `КодВКонтексте` + свойства справочника.
2. `ЗаписиПоКоду[КодВКонтексте] = Запись` — для поиска записи по коду.
3. `ДочерниеКоды[КодРодителя] = МассивДочернихКодов` — для рекурсивного обхода.
4. Корневые коды (`КодВКонтексте` без точек) сортируются и становятся верхними узлами дерева.
5. Для каждого корня рекурсивно раскрываются дочерние коды (`ГКСИ_ДобавитьУзелПоКоду`).
6. Осиротевшие записи (родительская запись в РС не найдена) собираются в отдельной ветке `(Сироты)` в конце дерева.

**Что удалено из модуля формы** (логика устарела):
- `ГКСИ_ДобавитьВеткуГруппы` — заменена на `ГКСИ_ДобавитьУзелПоКоду`.
- `ГКСИ_ПолучитьКорневуюИнструкциюГруппы` — больше не нужна.
- `ГКСИ_ОтсортироватьМассивСсылокПоПолномуКоду` — заменена на `ГКСИ_ОтсортироватьМассивСтрок`.
- `ГКСИ_СоздатьУзелГруппы`, `ГКСИ_СоздатьУзелСценария` — узлы создаются прямо в `ГКСИ_ДобавитьУзелПоКоду`.

**Что НЕ менялось** в этой итерации (намеренно отложено):

## 11. Bugfix 1.97: корень дерева строится динамически из префиксов кодов

**Проблема (выявлена пользователем):** в дереве формы `ФормаСпискаДеревоГрупп` после загрузки ДМТО + ГИП с действием «Прикрепить» все элементы отображались **плоским списком** (без отступов иерархии) внутри одной корневой ветки `(Сироты)`. Контекстные коды в форме были правильные (`001.xxx`, `018.xxx`), но сама иерархия «родитель → ребёнок» в дереве не отрисовывалась.

**Причина:** в предыдущей реализации `ГКСИ_ПостроитьДерево` корневые узлы дерева собирались так:

```1c
МассивКорневыхКодов = Новый Массив;
Для Каждого КлючИЗначение Из ЗаписиПоКоду Цикл
    Если СтрНайти(КлючИЗначение.Ключ, ".") = 0 Тогда
        МассивКорневыхКодов.Добавить(КлючИЗначение.Ключ);
    КонецЕсли;
КонецЦикла;
```

То есть корнем считалась **только** запись РС, у которой `КодВКонтексте` — строка без точек (например, `"001"`). Однако в РС `ГКСИ_ГруппыСценариев` для корневой `#`-группы инструкции (например, «Инструкция по ДМТО, 001») **нет записи с `Сценарий = «Инструкция по ДМТО»`** — потому что корневая `#`-группа записывается только как поле `Группа` у своих детей, а не как отдельный `Сценарий`. В итоге:
- `МассивКорневыхКодов` оказывался пустым (или содержал только случайные записи);
- все дочерние коды (`001.001`, `001.002`, …, `018.001`, …) считались «сиротами» и сваливались в одну общую ветку `(Сироты)`;
- внутри `(Сироты)` все строки оказывались на одном уровне — потому что сами они являются листьями (рекурсия не углубляется дальше листа).

**Принцип исправления:** корневые узлы дерева строятся **динамически из префиксов существующих кодов** — часть `КодВКонтексте` до первой точки. Если для корневого кода в РС есть собственная запись (поле `Сценарий` совпадает с `#`-группой) — берётся она. Если записи нет (что и происходит на практике) — ссылка на `#`-группу берётся из поля `Группа` любой дочерней записи с этим префиксом.

**Новый алгоритм `ГКСИ_ПостроитьДерево`:**
1. Пакетный запрос — все записи РС с непустым `КодВКонтексте` + свойства справочника.
2. `ЗаписиПоКоду[КодВКонтексте] = Запись` — поиск записи по коду.
3. `ДочерниеКоды[КодРодителя] = МассивДочернихКодов` — для рекурсивного обхода.
4. **Сбор корневых узлов:** для каждого `КодВКонтексте` определяется корневой код (часть до первой точки или сам код, если точек нет) и ссылка на `#`-группу. Дедупликация по `КодКорня`. Сортировка по строковому коду.
5. Для каждого корневого узла — создаётся корневая строка дерева **напрямую** в `ГКСИ_ДеревоСценариев.ПолучитьЭлементы()` (в обход `ГКСИ_ДобавитьУзелПоКоду`, чтобы корректно создать «синтетический» корень по переданной `Группа`).
6. Рекурсивное раскрытие детей через `ГКСИ_ДобавитьУзелПоКоду`.
7. **Удалена ветка `(Сироты)`** — в новом алгоритме у каждого кода есть префикс корня, и этот корень всегда создаётся (либо из записи РС, либо из `Группа` любой дочерней записи). Записи с пустым `Группа` или пустым `КодВКонтексте` отбрасываются на этапе фильтрации.

**Что НЕ менялось** (намеренно отложено):
- **Альбом процессов** (`АльбомПоВыделенным`). Текущая логика собирает поддерево через `ПолучитьЧленовГруппы` (рекурсивно по `ЧленыГрупп`), что тоже смешивает инструкции. Переделка Альбома — отдельная задача (см. план `2026_09_19_12_21_57.md`, раздел «Изменения в Альбоме процессов»).

**Проверка в EDT / Предприятии:**
1. Загрузить ГИП.md, затем ДМТО.md (или наоборот).
2. В форме списка раскрыть дерево — каждая инструкция (`001`, `018`, и т.д.) должна быть отдельной корневой строкой с жёлтой иконкой папки.
3. Дети корня `001` имеют коды `001.xxx`, дети корня `018` — `018.xxx`. Перемешивания между инструкциями нет.
4. Прикреплённые через «Прикрепить» узлы должны попадать в ветку той инструкции, к которой они прикреплены (по префиксу своего `КодВКонтексте`).

## 9. Bugfix 1.95: `КореньИнструкции` заполнялся самим узлом вместо корневой группы

**Проблема (выявлена пользователем):** после bugfix 1.94 в колонке `КореньИнструкции` для `#`-заголовков (`«Открытие ведомости покупки, 002»`, `«Выбор проекта, 003»`, `«Согласование заявки»` и т.д.) стало отображаться **название самого сценария** вместо корневой группы-инструкции (`«Инструкция по ДМТО, 001»`, `«Инструкция по ГИП, 018»`, `«Согласование ТКП, 010»`). **Причина 1 — `ОбработатьУзелРекурсивно`:** после bugfix 1.94 расчёт `ИнструкцияИсточникДляДетей` перенесён ДО `ДобавитьСценарийВГруппу`. Но для `#`-заголовка (Узел.Уровень = 2) `ИнструкцияИсточникДляДетей = СсылкаНаУзел` (он сам), и это же значение передавалось в `ДобавитьСценарийВГруппу` для самого `#`-заголовка — то есть `#`-заголовок становился своим собственным корнем.

**Причина 2 — `ГКСИ_СобратьКорневыеИнструкцииУзла`:** для корневого узла (нет родителей в графе) функция добавляла сам узел в `Корневые`, и `ГКСИ_ПолучитьКореньУзлаСКешем` возвращал сам узел как «единственный корень». Семантически это неправильно: корневой узел сам является корнем, его собственный `КореньИнструкции` в регистре должен быть пустым.

**Исправление в коде загрузки (`ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl`):**

Разделены два значения:
- `ИнструкцияИсточникДляУзла` — что писать в `КореньИнструкции` регистра для самого текущего узла;
- `ИнструкцияИсточникДляДетей` — что передавать детям в рекурсивном вызове.

Для `#`-заголовка (Уровень=2): `ИнструкцияИсточникДляУзла = Неопределено` (он сам корневой, его собственный корень пустой), `ИнструкцияИсточникДляДетей = СсылкаНаУзел` (он становится корнем для своих детей). Для вложенных узлов — наследование от родителя/формы.

Если форма явно передала `ИнструкцияИсточник` — приоритет у формы: для `#`-заголовка `ИнструкцияИсточникДляДетей = ИнструкцияИсточник` (форма знает лучше), `ИнструкцияИсточникДляУзла = Неопределено`. Для вложенных — `ИнструкцияИсточник`.

**Исправление в коде групп (`ГКСИ_ГруппыСценариевСервер/Module.bsl`):**

1. `ГКСИ_СобратьКорневыеИнструкцииУзла`: для узла без родителей — `Возврат` без добавления узла в `Корневые`. Множество остаётся пустым, и `ГКСИ_ПолучитьКореньУзлаСКешем` возвращает `Неопределено`. Это исправление также корректно влияет на `ГКСИ_ИсправитьИнструкцииИсточников` — реквизит `ГКСИ_ИнструкцияИсточник` для корневого `#`-заголовка теперь тоже будет оставаться пустым (а не заполняться им самим).

2. `ГКСИ_ДозаполнитьКореньИнструкции`:
   - Запрос расширен: выбираются записи с пустым корнем **или** с самоссылкой `КореньИнструкции = Сценарий` (артефакты bugfix 1.94).
   - В цикле обработки: если найден правильный корень — записываем его; если узел корневой/общий (корень не найден) и текущее значение — пусто или самоссылка — записываем пустую ссылку. Уже корректно заполненные записи не трогаем.

Для самих корневых `#`-групп (`«Инструкция по ДМТО, 001»`, `«Согласование ТКП, 010»`) колонка пустая.

## 13. Bugfix 1.96 → 1.99: дерево списка строится только по строковому коду (ПолныйКод справочника + КодВКонтексте)

### Что наблюдалось

После bugfix 1.97/1.98 статистика `ГКСИ_ОтладкаДерева` показывала `корней 7, всего 21` — алгоритм запускался и строил **плоский список с ложными корнями**: на корневом уровне появлялись отдельные строки `Выбор проекта (003)`, `Заполнение заявки (006)`, `Согласование ТКП (010)`, `Закупка (014)`, `Согласование заявки (023)`, хотя ожидалось, что внутри инструкции ДМТО/ГИП будут видны все их подгруппы. В скриншоте РС `ГКСИ_ГруппыСценариев` подтвердилось: в РС **нет записи для самих корневых `#`-групп инструкций** — они встречаются только как `Группа` у своих дочерних записей.

### Причина

Алгоритм `ГКСИ_ПостроитьДерево` для каждого префикса корневого кода брал `Запись.Группа` (любую дочернюю группу) как корневую группу инструкции. Но `Запись.Группа` — это просто группа, в которой состоит сценарий; для записи `003.001.002.001 Проверка остатков` это «Выбор проекта» — отдельная `#`-группа инструкции 003, **не подгруппа ДМТО**.

Дополнительная проблема: дети корневой `#`-группы искались через `ДочерниеКоды["КорневойКод"]`, где ключ — это `КодРодителя(КодВКонтексте)`. Для `КодВКонтексте = "003.001.002.001"` `КодРодителя = "003.001.002"`, поэтому `003.001.002.001` не попадал в `ДочерниеКоды["003"]` и под корнем `003` детей не было видно.

### Решение (bugfix 1.99)

Переписан `ГКСИ_ПостроитьДерево` на **двухпроходный алгоритм по `КодВКонтексте`**:

1. В запрос к справочнику `ДемонстрационныеСценарии` добавлены поля `ПолныйКод` и `Родитель`. Дополнительно строится индекс `КэшПоПолномуКоду[ПолныйКод] = Ссылка`.
2. **Корневая `#`-группа инструкции** определяется так: для каждого уникального `КодКорня` (часть `КодВКонтексте` до первой точки) ищется в справочнике группа с `ПолныйКод = КодКорня` **и** пустым `Родитель`. Это надёжно отделяет корневые `#`-группы от подгрупп.
3. **Все строки** (корневые, из РС, промежуточные префиксные узлы) создаются в плоском виде и сохраняются в `ВеткаПоКоду[КодВКонтексте]`.
4. **Промежуточные узлы** (например, `003.001.002`, `003.001`) создаются фиктивными строками, если их нет ни в РС, ни в справочнике — но они **не считаются корневыми**, так как не соответствуют корневой `#`-группе инструкции.
5. **Второй проход** перестраивает иерархию: для каждого `КодВКонтексте` ищется его `КодРодителя` (часть до последней точки), и строка перемещается из текущей коллекции в дочернюю коллекцию найденного родителя.

Старая рекурсивная функция `ГКСИ_ДобавитьУзелПоКоду` помечена как устаревшая (deprecated) и более не вызывается.

### Что делает bugfix

- Корневая ветка дерева — это только корневая `#`-группа инструкции (`ПолныйКод = КодКорня`, `Родитель = пусто`).
- Все записи с `КодВКонтексте = "001.001"`, `"001.002"` и т.д. — **дочерние** `001`, потому что у них `КодРодителя = "001"`.
- Записи с промежуточным кодом (`003.001.002.001`) — дочерние фиктивного промежуточного узла, который сам является дочерним корня `003`.
- Узлы `001.002`, `001.003`, …, `001.008` (выбранные проекта, выбор товаров, и т.д.) отображаются как дочерние `001`, как и ожидается.

### Файлы изменены в bugfix 1.99

- `src/Catalogs/ДемонстрационныеСценарии/Forms/ФормаСпискаДеревоГрупп/Module.bsl`:
  - `ГКСИ_ПостроитьДерево` полностью переписан: двухпроходный алгоритм по `КодВКонтексте` + поиск корневой `#`-группы по `ПолныйКод + Родитель = пусто`.
  - `ГКСИ_ДобавитьУзелПоКоду` оставлен deprecated.
- `src/Configuration/Configuration.mdo` — версия `1.98` → `1.99`.

## 14. Bugfix 2.0 — корень инструкции как `КореньИнструкции` для всех её узлов

### Симптом

После bugfix 1.99 на скриншоте всё ещё 7 корневых веток дерева:
«Инструкция по ДМТО (001)», «Инструкция по ГИП (018)», плюс «Выбор проекта (003)», «Заполнение заявки (006)», «Согласование ТКП (010)», «Закупка (014)», «Согласование заявки (023)». Пользователь загружал только 2 инструкции, а в дереве 7 корневых веток.

### Причина

Корень проблемы — в `ОбработатьУзелРекурсивно` (`CommonModules/ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl`, ~строка 1040). После bugfix 1.95 действовала логика:

```1c
ЭтоКорневойЗаголовок = (Узел.Уровень = 2 И ЗначениеЗаполнено(СсылкаНаУзел));
Если ЗначениеЗаполнено(ИнструкцияИсточник) Тогда
    ИнструкцияИсточникДляДетей = ИнструкцияИсточник;
    ИнструкцияИсточникДляУзла  = ?(ЭтоКорневойЗаголовок, Неопределено, ИнструкцияИсточник);
Иначе
    ИнструкцияИсточникДляДетей = ?(ЭтоКорневойЗаголовок, СсылкаНаУзел, ИнструкцияИсточник);
    ИнструкцияИсточникДляУзла  = ?(ЭтоКорневойЗаголовок, Неопределено, ИнструкцияИсточник);
КонецЕсли;
```

Для `#`-заголовка Уровень=2 (например, `# Инструкция по ДМТО`) `ИнструкцияИсточникДляУзла = Неопределено`. Это значит, что в регистр `ГКСИ_ГруппыСценариев` НЕ пишется запись `(Инструкция по ДМТО, Инструкция по ДМТО, КореньИнструкции=Инструкция по ДМТО)`. И в `КодВКонтексте` для всех дочерних `##`-заголовков этой инструкции префикс корня не появляется:

```1c
// В ГКСИ_ЗаписатьПолныйКодКонтекстный
КодКорня = ОбщегоНазначения.ЗначениеРеквизитаОбъекта(КореньИнструкции, "Код");
Запись.КодВКонтексте = Строка(КодКорня) + "." + ПолныйКод;
```

Без `КореньИнструкции` `КодВКонтексте` остаётся равным только собственному `ПолныйКод` (`002`, `003`, ...). Дерево строит иерархию именно по `КодВКонтексте`, поэтому `## Открытие ведомости покупки` с `КодВКонтексте = "002"` оказывается **корневой** веткой, а не дочерней ветки `001 Инструкция по ДМТО`.

### Решение (bugfix 2.0)

#### 14.1. Откат bugfix 1.95 в загрузке

В `ОбработатьУзелРекурсивно` убран `ЭтоКорневойЗаголовок` и зависимая от него ветка тернарника. Теперь `#`-заголовок верхнего уровня получает `ИнструкцияИсточникДляУзла = СсылкаНаУзел` (т.е. `КореньИнструкции = сам себе`), а его дети наследуют это значение через `ИнструкцияИсточникДляДетей`:

```1c
Если ЗначениеЗаполнено(ИнструкцияИсточник) Тогда
    ИнструкцияИсточникДляУзла  = ИнструкцияИсточник;
    ИнструкцияИсточникДляДетей = ИнструкцияИсточник;
Иначе
    ИнструкцияИсточникДляУзла  = ?(ЗначениеЗаполнено(СсылкаНаУзел), СсылкаНаУзел, ИнструкцияИсточник);
    ИнструкцияИсточникДляДетей = ИнструкцияИсточникДляУзла;
КонецЕсли;
```

Это даёт эффект: при следующей загрузке ДМТО все узлы инструкции (включая `## Открытие ведомости покупки`, `## Выбор проекта`, и т.д.) получают `КореньИнструкции = Инструкция по ДМТО`, и в `КодВКонтексте` появляется префикс корня (`001.002`, `001.003`, ...).

#### 14.2. Упрощение `ГКСИ_ПостроитьДерево`

После отката bugfix 1.95 данные в РС уже содержат правильный `КодВКонтексте` с префиксом корневой инструкции — `#`-группа инструкции имеет запись с `КодВКонтексте = "001"` (или `"018"` для ГИП), `##`-заголовки — с `КодВКонтексте = "001.002"`, и т.д. Специальная логика поиска корневой `#`-группы через `КэшПоПолномуКоду` + `Родитель` стала избыточной.

`ГКСИ_ПостроитьДерево` и `ГКСИ_СоздатьСтрокуДерева` упрощены:
- Удалён второй пакет запроса справочника (`ПолныйКод`, `Родитель` не нужны — префикс инструкции уже в `КодВКонтексте`).
- Удалён `КэшПоПолномуКоду` и `ПринудительнаяСсылкаГруппы` — параметр больше не нужен.
- Алгоритм сводится к однопроходному циклу по отсортированным `КодВКонтексте`: для корневого кода (без точек) строка создаётся в корне дерева, для дочернего — в `ВеткаПоКоду[КодРодителя]`. Благодаря трёхзначному формату кодов (`001`, `002`, ..., `018`) строковая сортировка даёт правильный порядок иерархии от корня к листьям.

Логика стала ровно той, что просил пользователь: «иерархия строится исключительно по строковому префиксу `КодВКонтексте`».

### Что увидит пользователь после перезагрузки

1. В EDT: Конфигурация → Обновить конфигурацию БД (F7). Перезапустить клиент Предприятия (Ctrl+F5).
2. Открыть обработку `ГКСИ_ЗагрузкаСценариевИзMarkdown` и **перезагрузить ДМТО и ГИП**.
3. После перезагрузки:
   - В регистре у всех узлов ДМТО появится `КореньИнструкции = Инструкция по ДМТО`, и `КодВКонтексте` будет иметь префикс `001.` (например, `001.002` для `## Открытие ведомости покупки`).
   - В регистре у всех узлов ГИП — `КореньИнструкции = Инструкция по ГИП`, префикс `018.` (например, `018.001` для `## Открытие ведомости покупки` ГИП).
   - В дереве — **ровно 2 корневые ветки**: «Инструкция по ДМТО» и «Инструкция по ГИП», все `##`-заголовки внутри них.

- `src/CommonModules/ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl` — `ОбработатьУзелРекурсивно`: удалена логика `ЭтоКорневойЗаголовок` и `?(ЭтоКорневойЗаголовок, Неопределено, ...)`, упрощены блоки присвоения `ИнструкцияИсточникДляУзла` и `ИнструкцияИсточникДляДетей`.

## 15. Bugfix 2.21: плоский вывод альбома процессов по выделенным группам

### Симптом (из отзыва пользователя)
Пользователь выделял на форме списка одну или несколько групп и нажимал «Альбом процессов». В итоговом HTML попадали **только прямые потомки корневых групп** (`#`-заголовки), но не их `##`-потомки. Например, для инструкции ДМТО (001) в альбоме были «Открытие ведомости покупных», «Выбор проекта», «Проверка остатков» (как отдельные корни), но **сама инструкция** с её 16 шагами не показывалась единым блоком — нужно было отдельно выделять корневую группу «Инструкция по ДМТО» И каждый `##`-заголовок.

Также при множественном выделении (группа + её потомок) один и тот же сценарий мог попасть в альбом дважды: как прямой потомок корня и как потомок подвыделенной группы.

### Причина
В `СобратьДокументАльбомаПоГруппам` для режима поддерева (`УзлыИзПоддерева <> Неопределено`) вызывалась та же `ГКСИ_ВывестиГруппуВМассивСтрок`, что и для режима «весь каталог». Эта функция — рекурсивная: для каждой подгруппы она создаёт `<hN>+<table>` с её **прямыми** сценарными потомками. Для случая «пользователь выделил корневую группу инструкции» результат корректный: `<h1>Инструкция по ДМТО</h1>` + таблица с прямыми потомками (`001.001 Открытие ведомости`, `001.002 Выбор проекта`, …). Но `##`-потомки подгрупп (например, `001.001.001 Проверка остатков` под `Выбор проекта`) выводятся **отдельным блоком** под своим `<h2>`, что усложняет чтение альбома.

### Решение (bugfix 2.21)

#### 15.1. Новый плоский режим вывода поддерева

В `CommonModules/ГКСИ_АльбомПроцессов/Module.bsl` добавлены две процедуры в `#Область СлужебныеПроцедурыИФункции`:

1. **`ГКСИ_ВывестиГруппуПлоско(Группа, КодЯзыка, ФрагментыДокумента, ДанныеУзлов, Обработанные)`** — выводит фрагмент HTML-документа альбома для поддерева одной группы в плоском виде:
   - Один заголовок `<h2 class="album-group">` для самой корневой группы.
   - **Одна** общая таблица со всеми сценарными потомками поддерева (включая внучатых на любом уровне вложенности), отсортированная по контекстному коду.
   - Без вложенных `<hN>` и отдельных таблиц для подгрупп.

2. **`ГКСИ_СобратьВсехСценарныхПотомковРекурсивно(Узел, ДанныеУзлов, Результат, Обработанные)`** — рекурсивно обходит `ЧленствоПоГруппам` от узла и собирает плоский список сценариев:
   - Группы **не** добавляются в результат — только сценарии.
   - **Дедупликация** через единый `Обработанные`: каждый сценарий добавляется ровно один раз.
   - **Защита от циклов**: подгруппа, уже посещённая в рамках обхода, не обрабатывается повторно.

#### 15.2. Переключатель режима в `СобратьДокументАльбомаПоГруппам`

В цикле обхода корневых групп поддерева:

```1c
Для Каждого Группа Из МассивГрупп Цикл
    Если УзлыИзПоддерева <> Неопределено Тогда
        ГКСИ_ВывестиГруппуПлоско(Группа, КодЯзыка,
            ФрагментыДокумента, ДанныеУзлов, Обработанные);
    Иначе
        ГКСИ_ВывестиГруппуВМассивСтрок(Группа, КодЯзыка, 1,
            ФрагментыДокумента, ДанныеУзлов, Обработанные);
    КонецЕсли;
КонецЦикла;
```

Для поддерева — плоский режим (одна таблица на корневую группу). Для каталога или обычного `ГруппыДляАльбома` — старая иерархическая логика (вложенные `<hN>` + таблицы для каждой подгруппы).

### Эффект для пользователя

После исправления:
1. **Выделение корневой `#`-группы инструкции** (`«Инструкция по ДМТО»`) даёт в альбоме:
   - Один блок `<h2>Инструкция по ДМТО</h2>`.
   - **Одну таблицу** со всеми 16 шагами инструкции (`001.001.001 Открытие ведомости покупных`, `001.001.002 Выбор проекта`, `001.001.002.001 Проверка остатков`, …, `001.001.008.003 Создание заявки на расходование`), отсортированными по `КодВКонтексте`.
2. **Множественное выделение** (группа + её потомок) — потомок появляется в таблице ровно один раз: общий `Обработанные` Соответствие защищает от дублей.
3. **Выделение нескольких инструкций одновременно** (например, ДМТО + ГИП) — каждая инструкция выводится отдельным блоком со своей таблицей, без перемешивания шагов.

### Совместимость
Старая иерархическая логика (`ГКСИ_ВывестиГруппуВМассивСтрок`) **сохранена** и используется для:
- старого контракта `СобратьДокументАльбомаПоГруппам(Группы)` без `УзлыИзПоддерева` (каталог или ручной список групп);
- формы «АльбомПроцессов» (типовой сценарий).

Плоский режим применяется **только** когда поддерево передано из формы списка через `СобратьДокументАльбомаПоПоддереву`.

## 16. Bugfix 2.22: защита от циклов блокировала рекурсивный сбор поддерева

### Симптом (из отзыва пользователя)
После bugfix 2.21 пользователь сообщил: «не поменялось ничего». При выделении корневой `#`-группы инструкции в форме списка и нажатии «Альбом процессов» в HTML попадала только шапка с названием корневой группы — **без таблицы со сценарными потомками**. То же самое — при выделении нескольких групп.

### Причина
В `Catalogs/ДемонстрационныеСценарии/Forms/ФормаСпискаДеревоГрупп/Module.bsl` функция `ГКСИ_ДобавитьУзелПоддерева` в начале делала проверку:

```1c
Если Обработанные.Получить(Группа) <> Неопределено Тогда
    Возврат;
КонецЕсли;
Обработанные.Вставить(Группа, Истина);
```

Но вызывающий код `ГКСИ_СобратьПоддеревоАльбомаНаСервере` **уже** добавлял `Корень` в `Обработанные` ДО вызова `ГКСИ_ДобавитьУзелПоддерева(Поддерево, Корень, Обработанные)`:

```1c
Обработанные.Вставить(Корень, Истина);
Поддерево.Добавить(Новый Структура(
    "Сценарий, ЭтоГруппа, РодительскаяГруппа",
    Корень, Истина, Справочники.ДемонстрационныеСценарии.ПустаяСсылка()));
ГКСИ_ДобавитьУзелПоддерева(Поддерево, Корень, Обработанные);
```

В результате на первом же вызове `ГКСИ_ДобавитьУзелПоддерева` срабатывала защита, и процедура возвращала управление **до обхода членов группы**. В итоге `Поддерево` всегда содержало ровно одну запись — корневую группу без потомков. Дальше `СобратьДокументАльбомаПоПоддереву` собирал `ВсеУзлы = [Корень]`, и `ЧленствоПоГруппам[Корень]` оказывалось пустым — в таблице альбома нечего показывать.

Защита от повторов для самой `Группа` была избыточной: вызывающий код уже пометил её как обработанную перед рекурсивным входом. Защита нужна только для **членов** группы (от зацикливания на перекрёстных ссылках между узлами).

### Решение (bugfix 2.22)
В `ГКСИ_ДобавитьУзелПоддерева` убрана проверка `Обработанные.Получить(Группа) <> Неопределено` в начале процедуры. Защита от повторов сохранена только для членов группы внутри цикла.

До:
```1c
Процедура ГКСИ_ДобавитьУзелПоддерева(Поддерево, Группа, Обработанные)

    Если НЕ ЗначениеЗаполнено(Группа) Тогда
        Возврат;
    КонецЕсли;
    Если Обработанные.Получить(Группа) <> Неопределено Тогда  // ← ломало обход
        Возврат;
    КонецЕсли;
    Обработанные.Вставить(Группа, Истина);

    ЧленыГруппы = ГКСИ_ГруппыСценариевСервер.ПолучитьЧленовГруппы(Группа);
    ...
```

После:
```1c
Процедура ГКСИ_ДобавитьУзелПоддерева(Поддерево, Группа, Обработанные)

    Если НЕ ЗначениеЗаполнено(Группа) Тогда
        Возврат;
    КонецЕсли;
    // Саму Группу в Поддерево уже добавил вызывающий код и пометил
    // в Обработанные. Защита нужна только для членов Группы.

    ЧленыГруппы = ГКСИ_ГруппыСценариевСервер.ПолучитьЧленовГруппы(Группа);
    ...
```

Защита от циклов сохранена: внутри цикла `Для Каждого ЧленГруппы Из ЧленыГруппы` для каждого члена проверяется `Обработанные.Получить(ЧленГруппы) <> Неопределено`. Это правильно: один и тот же узел не должен попасть в поддерево дважды, даже если он достижим из разных ветвей (например, в случае перекрёстных ссылок между инструкциями после прикрепления узлов).

### Эффект для пользователя
1. Выделение корневой `#`-группы инструкции даёт в альбоме один блок с шапкой `<h2>Инструкция по ДМТО</h2>` и одну таблицу со всеми сценариями поддерева (отсортированы по контекстному коду).
2. Выделение нескольких корневых групп одновременно — каждая выводится отдельным блоком со своей таблицей.
3. Множественное выделение (группа + её потомок) — потомок появляется ровно один раз (дедупликация через общий `Обработанные`).

### Файлы изменены в bugfix 2.22
- `src/Catalogs/ДемонстрационныеСценарии/Forms/ФормаСпискаДеревоГрупп/Module.bsl` — `ГКСИ_ДобавитьУзелПоддерева`: убрана преждевременная защита от повтора для самой `Группа`. Добавлен комментарий, поясняющий, что вызывающий код уже пометил `Группа` в `Обработанные`.

## 17. Bugfix 2.23: код сценариев в плоском альбоме по поддереву

**Проблема (выявлена пользователем):** после bugfix 2.22 плоский альбом (`ГКСИ_ВывестиГруппуПлоско`) стал корректно отображать потомков выделенной группы (а не только корень), но у элементов-сценариев в HTML-таблице не показывалась колонка «Код». У корневых групп код отображался.

**Причина:** `ГКСИ_ВывестиГруппуПлоско` передавал в `ГКСИ_СтрокаТаблицыСценария(Потомок, Группа, ...)` параметр `Группа`, равный корню поддерева (та группа, которую выделил пользователь). Внутри `ГКСИ_СтрокаТаблицыСценария` для получения кода вызывается `ГКСИ_КонтекстныйКодПотомка(Потомок, Группа, ДанныеУзлов)`, который ищет запись в `КонтекстныеКодыПоПарам[Потомок][Группа]`.

В РС `ГКСИ_ГруппыСценариев` для сценария `001.001.001` запись `КонтекстныеКодыПоПарам[001.001.001][001.001]` есть (это прямая связь `(Группа=001.001, Сценарий=001.001.001)` в РС). А для пары `(001.001.001, 001)` (транзитивная связь) — записи нет. Поэтому код возвращался пустой строкой для всех сценариев в плоском режиме, потому что мы передавали именно корень поддерева.

При этом `ГКСИ_СобратьВсехСценарныхПотомковРекурсивно` уже вычислял правильный `КодПотомка` (с использованием непосредственной родительской группы), но этот код использовался только для сортировки `СписокПотомков.СортироватьПоПредставлению()` и терялся при вызове `ГКСИ_СтрокаТаблицыСценария`.

### Решение (bugfix 2.23)
Передаём непосредственную родительскую группу явно, чтобы `ГКСИ_КонтекстныйКодПотомка` нашёл запись в `КонтекстныеКодыПоПарам`:

1. В `ГКСИ_СобратьВсехСценарныхПотомковРекурсивно` значение `Результат.Значение` теперь хранит не ссылку на сценарий, а **структуру** `Новый Структура("Сценарий, РодительскаяГруппа", ...)`. Поле `Представление` по-прежнему хранит `КодПотомка` для сортировки.

2. В `ГКСИ_ВывестиГруппуПлоско` вместо `Потомок = Элемент.Значение` теперь `ПараметрыСценария = Элемент.Значение`, и в `ГКСИ_СтрокаТаблицыСценария` передаются `ПараметрыСценария.Сценарий` и `ПараметрыСценария.РодительскаяГруппа`.

3. Сигнатура `ГКСИ_СтрокаТаблицыСценария` не изменена (осталось 4 параметра) — это важно, иначе сработает SU254 «слишком много параметров [Сервер]».

- `src/CommonModules/ГКСИ_АльбомПроцессов/Module.bsl` — `ГКСИ_СобратьВсехСценарныхПотомковРекурсивно`: `Значение` теперь хранит `Структура` с полями `Сценарий` и `РодительскаяГруппа`. `ГКСИ_ВывестиГруппуПлоско`: вместо `Потомок = Элемент.Значение` используется `ПараметрыСценария = Элемент.Значение` и в `ГКСИ_СтрокаТаблицыСценария` передаётся непосредственная родительская группа из структуры.

## 18. Bugfix 2.24: возврат иерархического вывода альбома по поддереву

**Проблема (выявлена пользователем):** после bugfix 2.21 в альбоме по поддереву пропало отображение **промежуточных групп**. Был только `<h2>` для корневой группы (то, что выделил пользователь) и одна общая таблица со всеми сценарными потомками — но без `<h3>`, `<h4>` и т.п. для `#`- и `##`-групп внутри поддерева.

Этот режим генерировал ровно один заголовок `<h2>` (для корневой группы) и одну общую HTML-таблицу со всеми сценарными потомками поддерева (включая глубоко вложенных), отсортированными по контекстному коду. Промежуточные `#`- и `##`-группы в этом режиме не выводились отдельными `<hN>+<table>`.

Пользователь же ожидал видеть в альбоме **иерархию** — отдельный `<hN>+<table>` для каждой группы, как это было до bugfix 2.21 (т.е. в обычном иерархическом режиме `ГКСИ_ВывестиГруппуВМассивСтрок`).

### Решение (bugfix 2.24)
1. **Возврат иерархического режима для поддерева.** В `СобратьДокументАльбомаПоГруппам` убрано условие `Если УзлыИзПоддерева <> Неопределено` — теперь для поддерева тоже вызывается `ГКСИ_ВывестиГруппуВМассивСтрок`, который рекурсивно обходит группы и для каждой рисует `<hN>` и таблицу со сценариями.

2. **Фильтрация `ЧленствоПоГруппам` по `ВсеУзлы`.** Запрос пакета 4 в `ГКСИ_ЗагрузитьДанныеУзлов` ограничивает выборку только условием «Группа В (&Узлы)», но не «Сценарий В (&Узлы)». Поэтому в `ЧленствоПоГруппам` могли попасть записи, где `Сценарий` вне поддерева — и иерархический обход вышел бы за пределы поддерева. Добавлена новая процедура `ГКСИ_ОтфильтроватьЧленствоПоПоддереву`, которая фильтрует `ЧленствоПоГруппам`, оставляя только тех членов, которые входят в `ВсеУзлы`. Если после фильтрации массив членов группы пустой, ключ удаляется из `ЧленствоПоГруппам`.

3. **Удалены неиспользуемые функции плоского режима:** `ГКСИ_ВывестиГруппуПлоско` и `ГКСИ_СобратьВсехСценарныхПотомковРекурсивно` (они больше не вызываются).

2. Для каждой `#`-подгруппы внутри инструкции — отдельный блок `<h3>` и таблица со сценариями этой подгруппы.
3. Для `##`-подгрупп внутри `#`-подгрупп — блок `<h4>` и таблица с их сценариями.
4. Иерархический обход ограничен `ВсеУзлы` — в альбом не попадают сценарии, которые пользователь не выделял (включая тех, что были в РС, но не вошли в поддерево).

## 19. Bugfix 2.25: фильтрация по КореньИнструкции в поддереве

**Проблема (выявлена пользователем):** после загрузки второй инструкции (ГИП, `018`) с действием «прикрепить к нашей группе» в разрешении конфликтов часть узлов ГИП попадала в альбом ДМТО. На скриншоте регистра `ГКСИ_ГруппыСценариев` (отфильтрованного по корню `018`) видно: сценарий «Задачи и процессы согласований, 011» физически входит в группу `Согласование ТКП, 010` (которая принадлежит ДМТО) и имеет контекстный код `018.001.007.001` — то есть это ГИП-узел, прикреплённый к ДМТО-группе.

**Причина:** в РС `ГКСИ_ГруппыСценариев` есть измерение `КореньИнструкции` (заполняется при загрузке), которое фиксирует факт: связь `(Сценарий → Группа)` существует именно в контексте конкретного корня. Функция `ГКСИ_ОтфильтроватьУзлыПоИнструкции` уже умела фильтровать по нему — но она вызывалась только в обычном режиме альбома (`УзлыИзПоддерева = Неопределено`). В режиме поддерева (при выделении пользователем группы в форме списка) фильтрация не применялась, и в альбом попадали все узлы выделенной группы, в том числе принадлежащие другой инструкции.

**Эффект до bugfix 2.25:** при выделении корневой `#`-группы инструкции ДМТО в альбом попадала группа `Согласование ТКП` со всеми её членами — в том числе ГИП-узлами (`Задачи и процессы согласований, 011`, `Выбор согласантов или самостоятельное согласование поставщика, 021`, `Завершение согласования ТКП, 022`), физически прикреплёнными к этой группе.

### Решение (bugfix 2.25)
В `СобратьДокументАльбомаПоГруппам` убрано условие `Если УзлыИзПоддерева = Неопределено` — теперь фильтрация по `КореньИнструкции` через `ГКСИ_ОтфильтроватьУзлыПоИнструкции` применяется и для поддерева. После фильтрации `ВсеУзлы` содержит только узлы, у которых есть запись в РС с `КореньИнструкции = одна из корневых групп альбома`. ГИП-узлы (с `КореньИнструкции = 018`) будут отсеяны из альбома ДМТО (с корнем `001`).

Фильтрация `ГКСИ_ОтфильтроватьЧленствоПоПоддереву` (добавленная в bugfix 2.24) работает уже после этой — она отсекает членов группы, не вошедших в отфильтрованный `ВсеУзлы`. То есть `ЧленствоПоГруппам[Согласование ТКП]` останется только с ДМТО-узлами.

### Эффект для пользователя
1. Альбом корня ДМТО содержит только ДМТО-узлы (даже если они лежат в общих с ГИП группах).
2. Альбом корня ГИП содержит только ГИП-узлы.
3. Группы, у которых после фильтрации не осталось членов в нужной инструкции, отображаются без таблицы.

- `src/CommonModules/ГКСИ_АльбомПроцессов/Module.bsl` — `СобратьДокументАльбомаПоГруппам`: убрано условие вокруг `ГКСИ_ОтфильтроватьУзлыПоИнструкции`, фильтрация теперь применяется для поддерева тоже.
- `src/Configuration/Configuration.mdo` — версия `2.24` → `2.25`.

## 20. Bugfix 2.26: некорректный ПолныйКодКонтекстный у общих узлов в ГИП

**Проблема (выявлена пользователем):** при загрузке второй инструкции (ГИП, `018`) с действием «прикрепить к нашей группе» общие узлы в ГИП получают «ДМТО-префикс» в `ПолныйКодКонтекстный` вместо «ГИП-префикса». Конкретные примеры из скрина пользователя (после применения bugfix 2.25, без отбора по ГИП):

| Сценарий | Группа | Корень | ПолныйКодКонтекстный (факт) | Корректное значение |
| --- | --- | --- | --- | --- |
| `Задачи и процессы согласований (011)` | `Согласование ТКП (010)` | ГИП | `001.007.001` | `018.003.001` |
| `Выбор согласовантов или самостоятельное согласование поставщика (021)` | `Согласование ТКП (010)` | ГИП | `001.007.004` | `018.003.004` |
| `Завершение согласования ТКП (022)` | `Согласование ТКП (010)` | ГИП | `001.007.005` | `018.003.005` |

То есть `КодВКонтексте` для ГИП-записей получал вид `018.001.007.001` (префикс корня `018` + ДМТО-префикс `001.007` + позиция сиблинга `001`). Это не просто косметический дефект: альбом ГИП после bugfix 2.25 уже не «подмешивает» чужие узлы, но коды у правильно отфильтрованных ГИП-узлов всё равно оставались ДМТО-префиксами.

### Причина

`ПолныйПолныйКодКонтекстныйГрафа(Сценарий, Группа, Граф)` вычисляет код через `ПолныйКодГруппыГрафа(Группа, Граф)`. Последняя берёт **первого встреченного родителя** в `Граф.РодителиГрупп` через `Для Каждого КлючИЗначение Из Родители Цикл; Прервать; КонецЦикла`. Для общих групп (например, `Согласование ТКП, 010`) в общем графе зарегистрировано **два** родителя — ДМТО-корень (`001`) и ГИП-корень (`018`). Поскольку запрос `ГКСИ_ГрафГрупп` не упорядочен, первым в обходе мог оказаться ДМТО-корень, и для ГИП-узла в ГИП-контексте возвращался код `001.007.xxx` вместо корректного `018.003.xxx`.

Комментарий в `ПолныйКодГруппыГрафа` явно фиксирует ограничение модели: «У иерархического узла берётся первый встреченный родитель (один родитель на группу в текущей модели данных)» — но в общем графе для общих групп это правило уже не работает: родителей два.

### Решение (bugfix 2.26)

В `ГКСИ_ПересчитатьВсеКодыВРегистре` введена группировка записей по `КореньИнструкции`: для каждого корня собирается **отдельный граф**, и `ПолныйПолныйКодКонтекстныйГрафа` считает код только по связям этого корня. Тогда для ГИП-узла `ПолныйКодГруппыГрафа` найдёт в графе единственного ГИП-родителя и вернёт `018.003`, без ДМТО-конкурента.

Чтобы не нарваться на SU95 (запрос в цикле), добавлены две функции:

- **`ГКСИ_ГрафГруппПоКорню(КореньИнструкции)`** — публичный API: возвращает граф по одному корню через прямой запрос к РС с фильтром. Используется в редких случаях, когда нужно получить граф конкретной инструкции одиночно.
- **`ГКСИ_СобратьГрафГруппПоСвязям(Связи, КодыПоСсылкам, ЭтоГруппа)`** — внутренняя функция без запросов: собирает граф из уже загруженного массива связей. Используется в `ГКСИ_ПересчитатьВсеКодыВРегистре`, чтобы после одного пакетного запроса к РС построить по корням столько графов, сколько инструкций в базе.

В `ГКСИ_ПересчитатьВсеКодыВРегистре` переписана логика:

1. Один пакетный запрос к РС `ГКСИ_ГруппыСценариев` + один запрос к справочнику `ДемонстрационныеСценарии` (загрузка кодов и признака группы).
2. Записи группируются по `КореньИнструкции` в массивы `СвязиПоКорням[Корень] = Массив`.
3. Для каждого корня строится граф через `ГКСИ_СобратьГрафГруппПоСвязям`, кэш кладётся в `ГрафыПоКорням`.
4. Записи с пустым `КореньИнструкции` (старая логика, до миграции на измерение) пересчитываются через общий `ГКСИ_ГрафГрупп()`.
5. Цикл по записям: для каждой записи выбирается граф её корня (если есть), и `ПолныйПолныйКодКонтекстныйГрафа` возвращает код, корректный именно для этого корня.

### Эффект для пользователя

1. После выполнения `ГКСИ_ПересчитатьВсеКодыВРегистре` все общие узлы в ГИП получают правильный префикс `018.003.xxx` в `ПолныйКодКонтекстный` и `018.018.003.xxx` в `КодВКонтексте`.
2. Альбомы (включая режим поддерева после bugfix 2.25) показывают коды, согласованные с принадлежностью узла к инструкции.
3. Узлы с пустым `КореньИнструкции` (если такие остались после миграции на 2.25) пересчитываются по старой логике через общий граф.

### Файлы изменены в bugfix 2.26
- `src/CommonModules/ГКСИ_ГруппыСценариевСервер/Module.bsl`:
  - Добавлена `ГКСИ_ГрафГруппПоКорню(КореньИнструкции)` (фильтрованный граф по корню через прямой запрос).
  - Добавлена `ГКСИ_СобратьГрафГруппПоСвязям(Связи, КодыПоСсылкам, ЭтоГруппа)` (сборка графа из готовых связей без запросов).
  - `ГКСИ_ПересчитатьВсеКодыВРегистре` — перестроена на группировку по корням и кэш графов (без запросов в цикле).
- `src/Configuration/Configuration.mdo` — версия `2.25` → `2.26`.

## 21. Bugfix 2.27: пересчёт кодов при загрузке тоже должен использовать граф по корню

**Проблема (выявлена пользователем после bugfix 2.26):** `ГКСИ_ПересчитатьВсеКодыВРегистре` правильно пересчитывал коды (заменял ДМТО-префикс у ГИП-узлов на правильный ГИП-префикс), но при повторной загрузке инструкции коды опять становились неправильными — общий граф `ГКСИ_ГрафГрупп()` использовался не только при глобальном пересчёте, но и при каждом добавлении/изменении узла в дереве. В итоге правильные коды, выставленные bugfix 2.26, тут же перетирались назад.

**Корень бага:** `ПолныйПолныйКодКонтекстныйГрафа` через общий граф `ПолныйКодГруппыГрафа` берёт первого встреченного родителя через `Для Каждого ... Прервать`. Эта ошибка была исправлена в 2.26 для глобального пересчёта `ГКСИ_ПересчитатьВсеКодыВРегистре`, но **все остальные** функции, использующие общий граф, продолжали перезаписывать правильные коды на ДМТО-префикс:

- `ЗаписатьПолныйКодКонтекстный(Сценарий, Группа, КореньИнструкции)` — вызывается из `ДобавитьСценарийВГруппу` после записи новой связи (используется при **каждом** добавлении сценария в группу во время загрузки).
- `ПересчитатьПолныйКодКонтекстныйДляСценария(Сценарий)` — вызывается из `ObjectModule.bsl` справочника `ДемонстрационныеСценарии` при изменении сценария (в том числе автоматически платформой при записи).
- `ПересчитатьПолныйКодДляПоддерева(Группа)` — вызывается из `ObjectModule.bsl` и из `ГКСИ_ЗагрузкаСценариевИзMarkdown/Module.bsl` (строка 1136) при загрузке.

То есть bugfix 2.26 чинил последствия (глобальный пересчёт), но не причину (код пересчитывался неправильно на каждом шаге загрузки).

**Эффект до bugfix 2.27:** даже после запуска `ГКСИ_ПересчитатьВсеКодыВРегистре` достаточно было выполнить любое действие, вызывающее одну из этих функций, чтобы ДМТО-префикс вернулся обратно в записи ГИП.

### Решение (bugfix 2.27)

Все четыре функции переведены на использование **фильтрованного графа по корню инструкции**:

1. **`ЗаписатьПолныйКодКонтекстный(Сценарий, Группа, КореньИнструкции)`** — теперь сначала строит граф по переданному корню через `ГКСИ_ГрафГруппПоКорню(КореньИнструкции)`, и только если корень не передан (старая логика) — использует общий граф. Пары `(Сценарий, Группа)` для только что записанной связи добавляются в граф вручную, как и раньше (эта подкладка нужна, потому что запрос внутри `ГКСИ_ГрафГруппПоКорню` видит только зафиксированные записи).

2. **`ПересчитатьПолныйКодКонтекстныйДляСценария(Сценарий)`** — записи по сценарию группируются по `КореньИнструкции`, графы строятся заранее через `ГКСИ_ПостроитьГрафыПоКорнямБезЗапросаВЦикле(МассивКорней)`, и для каждой записи пересчёт идёт на графе своего корня. Записи без корня пересчитываются через общий граф.

3. **`ПересчитатьПолныйКодДляПоддерева(Группа)`** — поддерево собирается через общий граф (один раз, `ГКСИ_СобратьПотомковРекурсивно`), затем одним запросом получаем все записи РС по `Группа В(&МассивГруппПоддерева)` вместе с их `КореньИнструкции`. Графы по корням строятся через `ГКСИ_ПостроитьГрафыПоКорнямБезЗапросаВЦикле`, и для каждой записи пересчёт идёт на графе своего корня. Цикл с запросом (который был в bugfix 2.26) убран, чтобы не получать SU95.

4. **`ГКСИ_ПостроитьГрафыПоКорнямБезЗапросаВЦикле(МассивКорней)`** — новая вспомогательная функция, единая точка построения фильтрованных графов. Делает один пакетный запрос к РС (фильтр по списку корней) и один запрос к справочнику кодов, дальше собирает графы через `ГКСИ_СобратьГрафГруппПоСвязям` без обращения к СУБД.

### Эффект для пользователя

1. После загрузки любой инструкции коды узлов остаются правильными (без ДМТО-префикса у ГИП-узлов в общих группах) — никакие автоматические пересчёты больше не «портят» результат.
2. `ГКСИ_ПересчитатьВсеКодыВРегистре` остаётся полезным для bulk-исправления существующих данных, но больше не требуется после каждой загрузки.
3. Альбом ГИП показывает корректные коды `018.003.xxx` без артефактов `001.007.xxx`.

### Файлы изменены в bugfix 2.27
- `src/CommonModules/ГКСИ_ГруппыСценариевСервер/Module.bsl`:
  - Добавлена `ГКСИ_ПостроитьГрафыПоКорнямБезЗапросаВЦикле(МассивКорней)` — единая точка построения фильтрованных графов без запроса в цикле.
  - `ЗаписатьПолныйКодКонтекстный` — строит граф по переданному `КореньИнструкции` (если заполнен).
  - `ПересчитатьПолныйКодКонтекстныйДляСценария` — записи группируются по корню, пересчёт на графе своего корня.
  - `ПересчитатьПолныйКодДляПоддерева` — поддерево собирается через общий граф, записи РС получаются одним запросом, графы по корням строятся заранее, пересчёт каждой записи на графе своего корня.
- `src/Configuration/Configuration.mdo` — версия `2.26` → `2.27`.

## 22. Bugfix 2.28: пересчёт кодов ломал самоссылки корневых обёрток инструкций

**Проблема (выявлена пользователем после bugfix 2.27):** после полной очистки регистра `ГКСИ_ГруппыСценариев` и повторной загрузки ДМТО+ГИП форма списка `ФормаСпискаДеревоГрупп` оказалась пустой. Сообщение формы: `ГКСИ_ПостроитьДерево v2.20: корней 0, всего 0`. При этом в РС все записи присутствуют и `КодВКонтексте` для всех корректный (по bugfix 2.27 — с правильными префиксами 001/018).

**Корень бага:** самоссылка корневой обёртки инструкции `(Сценарий = Группа = КореньИнструкции)` обрабатывается в регистре особым образом. В `ЗарегистрироватьКорневуюГруппуИнструкции` для неё явно выставляются `ПолныйКодКонтекстный = ""` и `КодВКонтексте = КодСправочника` (например, `"001"`). Это служебная запись для формы списка, она нужна чтобы найти корень по его системному коду.

При bugfix 2.26/2.27 я переписал `ГКСИ_ПересчитатьВсеКодыВРегистре`, `ПересчитатьПолныйКодКонтекстныйДляСценария` и `ПересчитатьПолныйКодДляПоддерева` так, что они пересчитывают **все** записи по `Сценарий = X` или `Группа В (&МассивГрупп)`, **включая самоссылки**. В результате для самоссылки вызывается `ПолныйПолныйКодКонтекстныйГрафа(Корень, Корень, Граф)` → `ПолныйКодГруппыГрафа(Корень, Граф)` → так как в графе у корня нет родителей (самоссылка отбрасывается при сборке графа), возвращается `Формат(Граф.КодыПоСсылкам.Получить(Корень), "ЧЦ=3; ЧВН=; ЧГ=") = "001"`. Затем `ПолныйКодКонтекстныйГрафа` возвращает `"001."` (с хвостовой точкой, потому что `ПозицияСиблинга` для самоссылки пустая). И `КодВКонтексте = "001" + "." + "001." = "001.001."` вместо правильного `"001"`.

`ГКСИ_ПостроитьДерево` ищет корневые обёртки именно по `КодВКонтексте = <системный код справочника>` (`"001"` / `"018"`). После пересчёта они стали `"001.001."` / `"018.018."` — форма их не видит, дерево пустое.

До bugfix 2.26 проблема не проявлялась, потому что `ПересчитатьПолныйКодДляПоддереваГрафа` содержал явный `Если Выборка.Сценарий = Выборка.Группа Тогда Продолжить; КонецЕсли;`. После моей переделки на единый запрос без этого пропуска самоссылки стали пересчитываться.

**Эффект до bugfix 2.28:** даже после правильного глобального пересчёта корневые обёртки теряли правильный `КодВКонтексте`, форма списка показывала пустое дерево с сообщением `корней 0, всего 0`. Это не было видно до тех пор, пока пользователь не сделал полную очистку и перезагрузку (в рабочей базе самоссылки часто оставались с правильным `КодВКонтексте`, потому что `ГКСИ_ПересчитатьВсеКодыВРегистре` не всегда доходил до самоссылки при локальных пересчётах).

### Решение (bugfix 2.28)

Во всех трёх пересчётных функциях добавлен **явный пропуск самоссылок** `(Сценарий = Группа = КореньИнструкции)` при первичном обходе выборки запроса. Это восстанавливает старое поведение из `ПересчитатьПолныйКодДляПоддереваГрафа`:

- `ГКСИ_ПересчитатьВсеКодыВРегистре` — пропускает самоссылки.
- `ПересчитатьПолныйКодКонтекстныйДляСценария` — пропускает самоссылки.
- `ПересчитатьПолныйКодДляПоддерева` — пропускает самоссылки.

Для записей-самоссылок остаётся в силе исходная установка из `ЗарегистрироватьКорневуюГруппуИнструкции`: `ПолныйКодКонтекстный = ""`, `КодВКонтексте = КодСправочника`.

### Восстановление данных

Чтобы исправить уже сломанные записи (после bugfix 2.27), достаточно один раз вызвать `ЗарегистрироватьКорневуюГруппуИнструкции(ИнструкцияПоДМТО)` и `ЗарегистрироватьКорневуюГруппуИнструкции(ИнструкцияПоГИП)` (или прогнать полный пересчёт `ГКСИ_ПересчитатьВсеКодыВРегистре` после применения bugfix 2.28 — самоссылки теперь пропускаются, и `ЗарегистрироватьКорневуюГруппуИнструкции` перезапишет их правильно). В EDT: F7 → Ctrl+F5 → перезагрузка инструкций.

### Файлы изменены в bugfix 2.28
- `src/CommonModules/ГКСИ_ГруппыСценариевСервер/Module.bsl`:
  - `ГКСИ_ПересчитатьВсеКодыВРегистре` — добавлен `Если Сценарий = Группа Тогда Продолжить; КонецЕсли;`.
  - `ПересчитатьПолныйКодКонтекстныйДляСценария` — то же.
  - `ПересчитатьПолныйКодДляПоддерева` — то же.
- `src/Configuration/Configuration.mdo` — версия `2.27` → `2.28`.

## 23. Bugfix 2.29: дубли общих узлов другой инструкции в альбоме

**Проблема (выявлена пользователем после bugfix 2.28):** в альбоме ДМТО `001.007 Согласование ТКП` появились **две одинаковые строки** `001.007.001 Задачи и процессы согласований` — одна правильная ДМТО-запись, вторая ГИП-запись. При этом в РС `ГКСИ_ГруппыСценариев` для этого сценария корректно две записи: `(Сценарий = Задачи, Группа = Согласование ТКП, Корень = ДМТО, ПолныйКод = 001.007.001, КодВКонтексте = 001.001.007.001)` и `(Сценарий = Задачи, Группа = Согласование ТКП, Корень = ГИП, ПолныйКод = 018.003.001, КодВКонтексте = 018.018.003.001)`. То есть bugfix 2.27 правильно пересчитал коды (ДМТО-код `001.007.001` для ДМТО-записи, ГИП-код `018.003.001` для ГИП-записи), но альбом ДМТО всё равно показывал ГИП-запись — и для неё пересчитывал ДМТО-код, потому что фильтрации по `КореньИнструкции` на уровне пакета членства не было.

**Корень бага:** bugfix 2.25 (фильтрация по корню в альбоме) работал только для верхнего уровня — `ГКСИ_ОтфильтроватьУзлыПоИнструкции` отфильтровывал `ВсеУзлы` (узлы, не имеющие связи в контексте ДМТО, удалялись), а `ГКСИ_ОтфильтроватьЧленствоПоПоддереву` оставлял в `ЧленствоПоГруппам[Группа]` только тех членов, чей `Сценарий` есть в `ВсеУзлы`. Но `Задачи и процессы согласований` **есть** в `ВсеУзлы` (через ДМТО-связь), поэтому фильтр пропускал **обе записи** РС для этого узла — и ДМТО, и ГИП. При обходе дерева в `ГКСИ_ВывестиГруппуВМассивСтрок` `ЧленствоПоГруппам[Согласование ТКП]` содержал ГИП-запись `Задачи`, и для неё пересчитывался ДМТО-код через ДМТО-граф (= `001.007.001`). Результат — дубль строки в альбоме ДМТО.

Проблема была именно в том, что `ЧленствоПоГруппам` хранит массив `Сценариев` без `КореньИнструкции`, и фильтр по `ВсеУзлы` не может отличить ДМТО-запись от ГИП-записи для одного `Сценарий`.

### Решение (bugfix 2.29)

Фильтрация перенесена с уровня "отфильтровать уже загруженные данные" на уровень "не загружать чужие записи вообще". В `ГКСИ_ЗагрузитьДанныеУзлов(Узлы, КодыЯзыков, МассивКорневыхГрупп = Неопределено)` добавлен опциональный параметр `МассивКорневыхГрупп`. Если он передан, к пакету 4 (чтение членства из `ГКСИ_ГруппыСценариев`) дописывается условие:

```
И ГруппыСценариев.КореньИнструкции В(&МассивКорневыхГрупп)
```

В этом случае в `ЧленствоПоГруппам[Группа]` попадают **только** ДМТО-члены группы, ГИП-запись отбрасывается на уровне запроса, и `ГКСИ_ОтфильтроватьЧленствоПоПоддереву` (который фильтрует дальше по `ВсеУзлы`) уже не находит лишнего. Аналогично `КонтекстныеКодыПоПарам` заполняется только ДМТО-кодами — для пары `(Задачи, Согласование ТКП)` хранится только `001.007.001`, и `ГКСИ_КонтекстныйКодПотомка` в ДМТО-альбоме возвращает именно его.

В вызов `ГКСИ_ЗагрузитьДанныеУзлов` из `СобратьДокументАльбомаПоГруппам` передан `МассивГрупп` (= массив корневых групп альбома). Старая двухшаговая фильтрация (`ГКСИ_ОтфильтроватьУзлыПоИнструкции` + `ГКСИ_ОтфильтроватьЧленствоПоПоддереву`) сохранена без изменений — она работает поверх нового фильтра, чтобы гарантировать, что в `ВсеУзлы` тоже останутся только нужные узлы.

Старая сигнатура `ГКСИ_ЗагрузитьДанныеУзлов(Узлы, КодыЯзыков)` сохранена (третий параметр опциональный), так что другие вызовы этой функции (например, в `ГКСИ_СобратьДокументАльбомаПоПоддереву`) продолжают работать без изменений — там фильтрация по корням не нужна, потому что альбом строится ровно по выделенному поддереву.

### Эффект для пользователя

1. В ДМТО-альбоме `001.007 Согласование ТКП` осталась только одна строка `001.007.001 Задачи и процессы согласований` — ДМТО-запись.

3. Альбомы общих групп больше не содержат дублей.

## 24. Bugfix 2.30: фильтрация по `КореньОбхода` в `ГКСИ_ВывестиГруппуВМассивСтрок`

**Проблема (выявлена пользователем после bugfix 2.29):** после bugfix 2.29 в ДМТО-альбоме `001.007 Согласование ТКП` всё ещё появлялись **две одинаковые строки** `001.007.001 Задачи и процессы согласований` — фильтр в пакете 4 не помог для случая `СобратьДокументАльбома()` (вызов без параметров на весь каталог).

**Корень бага:** `СобратьДокументАльбома()` вызывает `СобратьДокументАльбомаПоГруппам(ПустойМассив, ...)`. `ГКСИ_НормализоватьГруппы(ПустойМассив)` возвращает **все корневые группы каталога** = `[ДМТО-корень, ГИП-корень]`. После этого:
- Внешний цикл `Для Каждого Группа Из МассивГрупп Цикл` обходит каждую корневую группу по отдельности.
- Для ДМТО-обхода вызывается `ГКСИ_ВывестиГруппуВМассивСтрок(ДМТО-корень, ...)` → заголовок `001 Инструкция по ... ДМТО`. Обход спускается к подгруппам, в том числе к `001.007 Согласование ТКП`.
- Для ГИП-обхода вызывается `ГКСИ_ВывестиГруппуВМассивСтрок(ГИП-корень, ...)` → заголовок `018 Инструкция по ... ГИП`. Обход спускается к `018.003 Согласование ТКП`.

На этом этапе `ЧленствоПоГруппам[001.007 Согласование ТКП]` содержит **обе записи** для общего узла `Задачи` (ДМТО + ГИП), потому что фильтр `КореньИнструкции В (&МассивКорневыхГрупп)` пропускает обе (и ДМТО, и ГИП входят в `МассивКорневыхГрупп`). А `ГКСИ_ДобавитьВМассивСоответствия` добавляет без проверки дубликатов — `Задачи` оказывается в массиве дважды.

Bugfix 2.29 (фильтр в пакете 4 через `МассивКорневыхГрупп`) работал только для случая, когда `МассивГрупп` содержит **один** корень (например, `СобратьДокументАльбомаПоГруппам([ДМТО-корень])`). Для случая `СобратьДокументАльбома()` с обходом всего каталога фильтр бесполезен: при `МассивГрупп = [ДМТО, ГИП]` он пропускает обе записи. Нужно фильтровать **на уровне обхода конкретного корня**.

### Решение (bugfix 2.30)

В `ДанныеУзлов` добавлен параллельный кеш `ЧленствоКорниПоГруппам[Группа] = Соответствие(Сценарий -> Массив КорнейИнструкции)`. Он заполняется в `ГКСИ_ЗагрузитьДанныеУзлов` (пакет 4) для каждой пары `(Группа, Сценарий, КореньИнструкции)`.

В `ГКСИ_ВывестиГруппуВМассивСтрок` добавлен опциональный параметр `КореньОбхода`. Когда он задан, перед выводом прямых потомков `ПрямыеПотомки` фильтруются через `ЧленствоКорниПоГруппам`: остаются только те `Сценарий`, у которых `КореньИнструкции = КореньОбхода`. Старая сигнатура без этого параметра сохранена, чтобы другие вызовы (например, `СобратьДокументАльбомаПоПоддереву`) продолжали работать без изменений.

В вызов `ГКСИ_ВывестиГруппуВМассивСтрок` из внешнего цикла `Для Каждого Группа Из МассивГрупп Цикл` передан `Группа` (= `КореньОбхода`) — это **сам корень инструкции** (например, `Инструкция по ... для ДМТО`), который одновременно является обходимой группой верхнего уровня.

### Эффект для пользователя

1. В ДМТО-обходе `001.007 Согласование ТКП` остаётся только ДМТО-член `Задачи и процессы согласований` с кодом `001.007.001`.
2. В ГИП-обходе `018.003 Согласование ТКП` остаётся только ГИП-член `Задачи и процессы согласований` с кодом `018.003.001`.
3. Альбомы общих групп больше не содержат дублей.

### Hotfix после bugfix 2.30: установка параметра `МассивКорневыхГрупп` в запросе

**Проблема (выявлена пользователем сразу после bugfix 2.30):** при открытии альбома `АльбомПроцессов` возникала ошибка `Ошибка при вызове метода контекста (ВыполнитьПакет)` — `{(55, 39)}: Не задано значение параметра "МассивКорневыхГрупп" И ГруппыСценариев.КореньИнструкции В(&МассивКорневыхГрупп)`. Стек: `ФормаСпискаДеревоГрупп → АльбомПроцессов → СобратьДокументАльбомаПоПоддереву → СобратьДокументАльбомаПоГруппам → ГКСИ_ЗагрузитьДанныеУзлов → Запрос.ВыполнитьПакет`.

**Корень бага:** во время правок bugfix 2.30 часть кода установки параметра `Запрос.УстановитьПараметр("МассивКорневыхГрупп", МассивКорневыхГрупп)` была потеряна (видимо, при откате неудачного edit-а). В итоге фильтр `КореньИнструкции В (&МассивКорневыхГрупп)` остался в тексте запроса, но параметр не устанавливался — 1С падала с ошибкой при первом же выполнении запроса (а раньше пользователь не дошёл до этой ветки, потому что bugfix 2.29 ещё не дошёл до публикации).

**Эффект:** все формы альбома (`АльбомПроцессов`, `СобратьДокументАльбомаПоПоддереву`, прямой вызов `СобратьДокументАльбомаПоГруппам`) падали с ошибкой `ВыполнитьПакет`.

**Решение:** восстановлена установка параметра по условию `Если МассивКорневыхГрупп <> Неопределено Тогда Запрос.УстановитьПараметр("МассивКорневыхГрупп", МассивКорневыхГрупп); КонецЕсли;`. Версия расширения осталась `2.30.0` — это технический hotfix, упущенный при публикации bugfix 2.30.

**Урок:** при многоэтапных правках с откатами проверять компиляцию И выполнение запроса сразу после каждого edit-а, а не только в конце — параметр `МассивКорневыхГрупп` был в запросе, и проверка компиляции проходила, но runtime падал. Также полезно добавлять интеграционный smoke-test в `ГКСИ_ЗагрузитьДанныеУзлов` при первом изменении сигнатуры — это бы поймало пропавший параметр сразу.
